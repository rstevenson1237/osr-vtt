## DEC-068 — `MapBackground.locked` is a stored per-background flag, not a client-side mode

**Closed 2026-08-17** — agent default under Default-and-notify, surfaced at this batch's
gate. Reversible: the field is additive and a migration that drops it is trivial.

- **Question.** IN-061 asks for backgrounds to be "marked locked or unlocked on the asset
  page". Where does that mark live — a stored field on each `MapBackground` document, or a
  per-viewer client toggle like `MapToolController.mapMode`?
- **Default.** A **stored field**: `MapBackground.locked?: boolean`, absent ⇒ unlocked,
  written through a new `setBackgroundLocked(roomId, mapId, bgId, locked)` on the shared
  contract (RULE-001). Schema **v27**, a migration, and a `.vttcamp` round-trip test
  (RULE-007).
- **Why not a client toggle.** A lock is a statement about the *asset* — "this map's floor
  plan is placed, stop grabbing it" — not about one viewer's current intent. Two referees
  (or the same referee on a second device) must see the same locked set, and a lock that
  evaporates on reload protects nothing on the next session. `mapMode` is a mode; this is a
  property.
- **Impact.** One additive field, one new contract method, one Firestore rule test run
  against the existing `backgrounds` subcollection rule — the per-room member-write model
  already covers the path, so no new boundary (RULE-004 unchanged in substance). The
  renderer ignores the field entirely; only hit-testing reads it.
- **Overridable at WI start** only by a decision that supersedes this one.
