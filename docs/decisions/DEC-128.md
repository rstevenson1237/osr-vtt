## DEC-128 — What does the app do with a `.vttcamp` written by a newer build?

**Closed 2026-10-06** — answered by the user under `/work-item` (IN-072).

- **Question.** `assertSupportedFormatVersion` rejects an archive _older_ than
  `VTTCAMP_FORMAT_VERSION`, but nothing rejects one that is _newer_: a `formatVersion` above
  this build's, or a room `schemaVersion` above `CURRENT_SCHEMA_VERSION`. `migrateRoom` only
  walks forward, so it no-ops and the archive opens. The older build's `RoomSchema` strips
  the fields it does not know on read. In the local build the file is the database
  (RULE-009, RULE-014), so the next autosave writes the campaign back without them; in the
  hosted build the import creates a room that silently lacks them.
- **Recommendation.** **Hard reject**, symmetric with the older-archive case, in both builds,
  before any migration runs. Exports also stamp the exporting build's version in the
  manifest as an optional field, so the error can name both builds.
- **Impact.** A stated guarantee on the `.vttcamp` reader (RULE-014). No room schema change
  and no migration: the manifest field is additive and optional, older builds ignore it,
  and `VTTCAMP_FORMAT_VERSION` stays 2.
- **Alternatives.** (b) Warn, then open: the newer fields are still lost on the next save,
  so the warning does not prevent the loss it describes. (c) Open read-only: safe, but needs
  a new read-only mode for the local build, for a rare case.
- **Answer.** **(a) Hard reject** (user, 2026-10-06). SPEC-062; scheduled as WI-220.
