## DEC-135 — IN-199: how does the token controller take pointer input?

**Closed 2026-10-10** — answered by the user under `/work-item` (IN-199).

- **Question.** IN-199 moves the token layer out of `VectorMapView` (SPEC-068). SPEC-060 §4
  says a seam that takes stage input implements `pointerDown/Move/Up(worldPx): boolean`
  and sits in `wireStagePointerEvents`' ladder, which IN-204 will turn into a loop. Tokens
  do not take stage input: each token's sprite is its own Pixi hit target, and its handler
  stops propagation, so the ladder never sees a click on a token. Does the token
  controller keep its sprite handlers, or join the ladder?
- **Recommendation.** **(a) Keep the sprite handlers in the controller.** The controller
  attaches them when it builds a token's container and owns the click, select, drag and
  drop they do. SPEC-068 §3 states this as a second input shape beside SPEC-060 §4: a seam
  whose hit targets are its own display objects takes their events directly and has no
  ladder branch. Identical outputs; nothing about hit testing, cursors or event order
  changes.
- **Impact.** No stored data, store, rules, layer or testid change. IN-204's router will
  dispatch over every seam except tokens, which it never saw. The protocol gains one
  sentence rather than one exception buried in code.
- **Alternatives.** **(b) Tokens join the ladder.** Drop the per-sprite handlers; the
  controller implements `pointerDown(worldPx)` with a disc hit test (`tokenAtPoint`) and
  takes a branch at the top of the ladder. One protocol for every seam, but hit testing
  changes from Pixi's sprite bounds and z-order to a disc test, the `grab`/`grabbing`
  cursors need re-plumbing, and the Eye/Ping-on-a-token cases move ahead of or behind the
  note dot and collab handlers, so it is not an identical-outputs refactor and the token
  specs become a behaviour check rather than an oracle. **(c) Split it.** Extract the
  sprite lifecycle now and leave the drag in the component until IN-204. Smaller, but the
  drag reads the sprite maps on every move, so the component would reach into the
  controller's internals, which is the coupling the extraction exists to remove.
  **(d) Don't extract.** Close IN-199 with no work item; the largest seam stays in the
  component, untestable without a browser.
- **Answer.** **(a) — keep the sprite handlers in the controller** (user, 2026-10-10).
  SPEC-068 stands as written.
