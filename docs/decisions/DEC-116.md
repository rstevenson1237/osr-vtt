## DEC-116 — The room password is removed, and a join secret is out of scope

**Closed 2026-09-23** — answered by the user under `/work-item` (IN-165). **Retires the
Postponed entry "Room `password` field. Stored, unenforced, dormant."**

- **Question.** The create form writes an optional password in plaintext onto the room
  document (`firebase-store.ts`), readable by every signed-in user (RULE-012), and nothing
  checks it. Remove it, or keep it dormant?
- **Answer.** **Remove it** (user, 2026-09-23): the form field, `Room.password` in the schema
  and both stores' `createRoom` input; a room-doc migration (next schema version) deletes any
  stored value; `.vttcamp` import drops the key. **A join secret is out of scope**: rules
  cannot check one without a trusted writer (RULE-010), and the room id is the capability
  (RULE-012). Reopening it needs a RULE-010 amendment first.
- **Impact.** RULE-007: migration, migration test, `.vttcamp` round-trip test. A room whose
  referee never reopens it keeps its stored value until they do (room-doc migrations run on
  open). No rules change. The comments citing `Room.password` as a precedent
  (`upload-containment.ts`, `campaign-store.ts`) are reworded.
- **Alternatives.** Stop writing but keep the field (stored plaintext stays readable); keep it
  dormant.
