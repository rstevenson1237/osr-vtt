## DEC-119 — Token portraits may be stored as small images in Firestore

**Closed 2026-09-23** — answered by the user under `/work-item` (IN-187). **Narrows the
Postponed entry "In-app image uploads"**: Storage uploads stay postponed exactly as written;
portraits gain a Firestore route that needs neither Storage nor Blaze.

- **Question.** Uploads are gated on Blaze (SPEC-034). A 256×256 WebP portrait is a few KB and
  a Firestore document holds 1 MB. Store small images in Firestore instead — for what, and
  written by whom?
- **Answer.** (user, 2026-09-23) **Portraits only.** A `rooms/{roomId}/images/{id}` collection
  of `{ bytes (base64 WebP), mime, w, h }`, resized client-side to at most 256×256. A new ref
  kind **`img:<id>`** is accepted wherever a portrait ref is (`portraitRef`, token
  `imageRef`), so no field changes type. **Any member may write**; rules enforce per-write
  containment only — `mime == 'image/webp'`, `w`,`h` ≤ 256, `bytes.size()` ≤ ~100 KB, path
  shape, membership. Backgrounds and handouts stay URL-only.
- **Impact.** RULE-004 (rules + rule tests), RULE-001 (new store methods in the contract
  suite, all three stores; `LocalStore` keeps images in the `.vttcamp`, RULE-014 round-trip).
  RULE-010 §1: no aggregate quota is possible; any client-side cap is friction and is labelled
  so. **Open check for the executor:** RULE-004 enumerates the rules' boundaries; if a size /
  mime containment rule on Firestore is read as a new boundary rather than RULE-010 §1's
  per-write containment, stop and log a standalone RULE-004 amendment before shipping rules.
- **Alternatives.** Portraits plus 1024 px handouts (~300 KB cap); referee-only writes;
  keeping all images URL-only.
