## DEC-105 — CI parallelism is a shard per job, not workers inside one job

**Closed 2026-09-18** — agent default under the `/work-item` chain (IN-143). Notified at the
WI-143 gate; overridable there.

- **Question.** A pull request waits 28–35 minutes, nearly all of it in `test-emulators`, where
  ~100 Playwright flows run at `workers: 1`, `fullyParallel: false` behind one emulator. Two
  ways to make that concurrent: raise Playwright's worker count inside the existing job, or
  shard the suite across several jobs that each bring their own emulator.
- **Answer.** **Shard across jobs** — a CI matrix of `--shard=i/N` (N = 4), each shard running
  its own `firebase emulators:exec`, exactly as the single job does today.
- **Why.** It changes the schedule and nothing else. Each shard is the job that already works,
  given a quarter of the specs; the emulator is already per-job, so there is no new question
  about what two concurrent suites do to one emulator's state, and a shard that goes red is
  reproduced locally with one `--shard` flag. Workers inside one job put four browser contexts,
  four Vite requests and four sets of emulator writes through the resources of a single runner,
  which is also where today's flakiness (`retries: 2`) already lives.
- **Why not both, now.** `fullyParallel` is the bigger win per runner-minute and remains
  available afterwards — every spec creates its own room, so the isolation argument is probably
  sound. It is a change to how the tests interact with shared state, and it should be made
  against a suite whose wall-clock is already fixed and whose flake rate is visible at
  `retries: 1`, not bundled with the change that makes both measurable.
- **Impact.** `.github/workflows/ci.yml` gains a matrix; `apps/web/package.json`'s `test:e2e`
  and the root `test:all:emulators` learn to pass a shard through; `playwright.config.ts` keeps
  `workers: 1` and drops `retries` to 1. Four emulator downloads per run instead of one, all
  cache hits. No test file changes, no testid moves (RULE-005 untouched).
- **Overridable**: yes, at the WI-143 gate — including the value of N, which is a tuning
  number rather than a decision.
