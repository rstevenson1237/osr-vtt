## DEC-133 — IN-201: how does the hex controller keep the axial boundary?

**Closed 2026-10-10** — answered by the user under `/work-item` (IN-201).

- **Question.** IN-201 moves hex authoring out of `VectorMapView` (SPEC-066). The
  controller owns the axial boundary RULE-006 draws: square-lattice code must never be
  reached from a hex map. Today each hex function starts with `if (!hexGrid) return`. What
  keeps that boundary once the code is a controller?
- **Recommendation.** **(a) Construct it only on hex maps.** The component holds `null` on
  a square map, so the boundary is whether the object exists, not a guard in each method.
  The grid kind is fixed at creation and the component already opens the hex
  subscriptions on this same test, once. Measure, the one reader that needs both spaces,
  is handed `hex?.hexAt ?? null` (SPEC-066 §2).
- **Impact.** No stored data, store, rules, layer or testid change; identical outputs.
  Call sites in the component become `hex?.…`. A future hex tool cannot forget the guard,
  because there is no guard to forget. The composers read `hex?.tiles ?? []` instead of a
  plain array.
- **Alternatives.** **(b) Always construct it, keep the guards.** A verbatim move of
  today's per-function `if (!hexGrid)` checks into the class. The smallest diff, but the
  boundary stays a branch each new method must repeat. **(c) Don't extract.** Close
  IN-201 with no work item; about 330 lines (230 plus WI-188's hex fog) stay in the
  component and remain untestable without a browser.
- **Answer.** **(a) — construct it only on hex maps** (user, 2026-10-10). SPEC-066 §2
  stands as written; WI-228 is scheduled.
