## DEC-070 — The Assets panel keeps add / lock / Fit / remove and loses "Adjust on map"

**Closed 2026-08-17** — agent default under Default-and-notify, surfaced at this batch's
gate. Reversible: the bridge is one field on `MapToolController`.

- **Question.** IN-062 makes the ordinary Select tool the way a background is picked up.
  What then happens to `background-adjust-{id}` and the
  `MapToolController.selectedBackgroundId` bridge it drives — the mechanism SPEC-038 §3
  used to arm the canvas gesture?
- **Default.** Both are **retired**. The Assets panel keeps the four things that are
  genuinely about *which* images a map has — add, lock/unlock, **Fit**, remove — and stops
  owning *where* an image is. Canvas selection replaces the bridge: Select picks a
  background the same way it picks any other object, and `selectedBackgroundId` becomes
  ordinary canvas selection state rather than a cross-activity channel.
- **Why.** The bridge existed only because the gesture had no other way to know which of
  several images to move, and it cost a main-view switch on every adjust (`shell.mainView =
  'map'` inside `selectForAdjust`). With Select doing the picking, keeping it would mean two
  selection mechanisms for the same object, disagreeing whenever the panel and the canvas
  were both used.
- **Impact.** `background-adjust-{id}` is retired and `backgrounds.spec.ts`'s assertions on
  it move to a canvas gesture in the same PR (RULE-005). A new `background-lock-{id}`
  testid takes its place in the row. The panel's `selectForAdjust` and its
  `shell.mainView` write both go.
- **Overridable at WI start**: WI-085 may keep a "show me this one on the map" affordance if
  the panel reads as inert without it — but as navigation, not as the arming of a gesture.
