## DEC-063 — Background transform is GM-only; the alignment grid shows while a background is selected

**Closed 2026-08-11** — agent default under Default-and-notify, surfaced at this batch's
gate. Reversible: both are UI-level gates, neither is baked into the stored shape from
DEC-062.

- **Question.** DEC-062 fixes the storage shape for multiple backgrounds but leaves two UI
  questions open: who may move/resize a background image, and exactly when does the
  translucent-yellow grid overlay (IN-053) appear during a resize?
- **Default.** Background management is GM-only, matching every other background control
  today (Session config's Change/Remove, and `MapsPanel`'s map management, both already
  gated `isGM`) and the SPEC-016 rationale that keeping it off the canvas "avoids accidental
  drags" — a per-viewer canvas drag on a shared asset is a bigger footgun than the existing
  GM-only picker. The alignment grid shows **whenever a background is selected**, not only
  while the pointer is actively dragging a resize handle — a referee needs to see the result
  after releasing, to check the match before deselecting, not just mid-gesture.
- **Impact.** No new store-level permission boundary (RULE-004 is untouched — this is a
  client-side UI gate, the same kind `MapToolbar`'s `isGM` checks already are, not a rules
  change). The grid overlay reuses the existing grid-line geometry and the theme's map-grid
  colour token at reduced opacity; no new render primitive.
- **Overridable at WI start**: WI-081 may adopt a different pair of answers if the referee
  workflow turns out to want it (e.g. any room member with map-write access, matching the
  "map tools are not referee-only" ratification in DEC-001) — but that would itself be a new
  decision, since it changes who may write to the new subcollection.
