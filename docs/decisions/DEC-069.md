## DEC-069 — Every existing background migrates to **locked**

**Closed 2026-08-17** — answered by the user at this batch's gate (option (a) of two).

- **Question.** When `MapBackground.locked` (DEC-068) ships, what does the v26→v27
  migration write for backgrounds that already exist?
- **Answer.** **Locked.** Existing placements are migrated to `locked: true`; only a
  newly added background starts unlocked.
- **Why it matters more than it looks.** Most placed backgrounds are fitted to the whole
  grid — that is what "Add" produces when the natural size can't be read, what **Fit**
  produces on demand, and what the v22→v23 fold gave every upgraded room. Under IN-062 an
  unlocked background is grabbable by Select anywhere inside its rect, so migrating
  existing full-grid images to *unlocked* would mean every Select click on the entire map
  grabs the background instead of the geometry under it. Locked-by-migration keeps
  present-day behaviour exactly and makes moving an image an opt-in.
- **Impact.** The migration is a backfill, not a transform: no coordinate is touched, so
  nothing visibly moves. New backgrounds deliberately do **not** inherit the migration's
  answer — a referee who has just placed an image wants to position it.
- **Consequence for the docs.** `README.md` → "Background management" must say plainly that
  an upgraded room's images arrive locked, or the first referee to try dragging one after
  the upgrade will file this as a bug.
