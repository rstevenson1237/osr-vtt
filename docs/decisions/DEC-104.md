## DEC-104 — The git tag is the version; `package.json` stops pretending to be one

**Closed 2026-09-18** — agent default under the `/work-item` chain (IN-149, closing IN-070 and
IN-073). Notified at the WI-147 gate; overridable there.

- **Question.** A user running a packaged local build has no way to say which build they have,
  and the project has no way to ask: `package.json` has read `0.0.0` since the first commit, no
  build stamps anything, and there is no release artefact to number. SPEC-042 §4.5 left this
  open. What is the identifier, and who writes it?
- **Answer.** **The git tag.** A `v*` tag on `main` is what produces a release; the workflow
  passes it to the build as `VITE_APP_VERSION`, and the app shows that string. `package.json`'s
  `version` stays `0.0.0` and is documented as meaningless — nothing reads it, nothing bumps it.
- **Why.** One source of truth that is already unique, already immutable, already the thing a
  GitHub release is named for, and already what a user is looking at when they download the zip.
  Every alternative needs the tag *anyway* and adds a second place to forget.
- **Why not bump `package.json` and derive the tag from it.** It is the conventional npm answer
  and it is the wrong shape here: this is a private, unpublished workspace of four packages, so
  a version bump is a commit whose only purpose is to be a commit, and the two can disagree
  between the bump and the tag. The failure mode — a release whose zip says `0.4.1` and whose
  tag says `v0.4.2` — is exactly the drift IN-044/045/046 keep raising about documents.
- **Why not a commit SHA.** It is precise and unquotable. "I'm on `a3f91c2`" is a fine bug
  report from a developer and an unreasonable thing to ask of the audience local mode exists
  for. The stamp may carry the short SHA *beside* the tag; it is not the identifier.
- **Impact.** A `VITE_APP_VERSION` define in `apps/web/vite.config.ts` with a dev-marker
  fallback, one render site, and the release workflow. No schema, no store, no rules, no
  `.vttcamp` field — `VTTCAMP_FORMAT_VERSION` is a separate number with a separate job
  (RULE-014), and nothing here makes an archive's compatibility a function of the app version.
- **Overridable**: yes, at the WI-147 gate. Reversing it later costs one define and one
  workflow input.
