# DEC-096 — How is a side-mode initiative slot keyed?

- **Question.** IN-130: `initiativeSlotId()` keys a **side**-mode slot by bare `groupId`, and
  `firestore.rules` allows a non-GM write to `sharedRoll/current/slots/{slotId}` only when
  `slotId.split(':')[0] == request.auth.uid`. So a player pressing their card's die during a
  side-mode Call for Initiative writes `slots/{groupId}` and is denied, although
  `initiative-call.ts`'s own contract says a player-owned group means "a human will stage the
  slot". Side is the **default** mode, so this is the default path.

  The obvious fix does not survive contact with the rules. A side slot's id (a `groupId`) and an
  ordinary shared roll's slot id (a bare `uid`) are **indistinguishable opaque strings** to a
  Security Rule. Telling them apart needs a `get()` on the group doc — a billed read on every
  slot write, which is precisely what the existing rule comment says the prefix check exists to
  avoid. Widening the rule to "any non-prefixed id" would let player A write player B's slot,
  which is the one boundary this rule enforces and which a rule test pins. So the id's **shape**
  has to change, not just the permission.

  **(a) Namespace the side slot**: `side:{groupId}`. The rule gains a clause allowing a member
  to write any slot whose prefix is the literal `side`. **(b) Uid-prefix it**:
  `{uid}:{groupId}`, so the rule is untouched. **(c) Accept the status quo**: only the referee
  ever stages in side mode.

- **Recommendation.** **(a).** It is the only option that preserves what side mode *means*.

  - **One slot per side.** A side is one tracker row and takes one number; Workflow 2 says "the
    first die roll a player triggers is registered as that group's initiative roll". Under (a)
    the slot id is a property of the **side**, so whoever stages first fills it and there is
    exactly one. Under (b) the id carries the *stager's* uid, so a side holding two
    player-owned tokens produces **two slots for one row** — both roll, and applying has to
    invent a tie-break that no spec states.
  - **The rule stays a pure string comparison.** `slotId.split(':')[0] == 'side'` costs the
    same as the uid check beside it: no `get()`, no billed read, nothing fetched to decide a
    write. RULE-010's "no trusted writer" is untouched, and RULE-008 already puts this inside
    the trust model — a member who can clobber a side's staged die is no more dangerous than one
    who can move another player's token, which tokens being member-writable already allows.
  - **`applySharedRollToInitiative` barely moves.** Its side branch looks up `side:{refId}`
    instead of `refId`; the individual branch's three-candidate list is untouched.
  - **Nothing durable is migrated.** `sharedRoll/current` is a transient staging doc that
    `openSharedRoll` clears on every call. A stale doc written under the old keying resolves or
    is replaced; no `.vttcamp` carries one, and RULE-007 is not engaged.

- **Impact.** `firebase/firestore.rules` changes, so the work ships rule tests (RULE-004) —
  a member may write `side:{groupId}`, a member still may not write another member's bare-uid
  slot, and the GM may still write anything. `initiativeSlotId` gains the prefix;
  `applySharedRollToInitiative`'s side lookup follows it; `stageTargetFor`'s owner check must
  stop reading `slotOwnerUid('side:g1')` as a uid. **IN-132 reads whichever scheme wins**, so
  the two are ordered: this first.

  The slot vocabulary grows a third shape — bare uid, `{uid}:{tokenId}`, `side:{groupId}` — and
  `slotOwnerUid`/`slotTokenId` are now ambiguous on the third unless they learn the prefix. That
  is the cost, and it is why the prefix is a reserved literal rather than a free string.

- **Alternatives.** **(b)** is rejected for the two-slots-per-side problem above: it keeps the
  rules file untouched, which is its only real merit, and it buys that by breaking "one number
  per side". **(c)** is rejected because it contradicts a contract already written down in
  `initiative-call.ts` and makes that module's player-owned-group detection dead code — and
  because the project owner's stated workflow has players rolling their own initiative.

  Also considered and not taken: a `get()` on the group doc inside the rule (a billed read per
  slot write, for a boundary RULE-008 says we do not need), and dropping side-mode player
  staging in favour of individual mode (a mode change is not a fix).

- **Answer.** **(a)** — namespace the side slot as `side:{groupId}` and widen the rule on the
  literal prefix (user, 2026-09-15, as recommended). Specified as **SPEC-050 §1**, scheduled as
  **WI-134**.
