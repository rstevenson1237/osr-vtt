## DEC-130 — IN-113: where do token rings draw once each token is one container?

**Open** — asked of the user under `/work-item` (IN-113), 2026-10-06.

- **Question.** IN-113 makes each token one `PIXI.Container` (SPEC-063). Rings and
  collapsed-group count badges then need a stacking rule when tokens overlap. Today rings
  mostly sit above all token art, but only by creation order: a later token can cover an
  earlier one's ring.
- **Recommendation.** **(a) Rings on top.** Ring and count badge stay children of their
  token's container (they move with it) but render in one Pixi `RenderLayer` above all
  token art (Pixi ^8.19 has it). A selected token's ring stays visible under a crowd, and
  the creation-order accident goes away.
- **Impact.** No stored data, rules, store or testid change. Visible: under (a) rings and
  count badges are always on top; under (b) an overlapping later token covers the ring of
  the one beneath. PNG export must include the render layer (SPEC-063 §4).
- **Alternatives.** **(b) Plain stacking**: ring inside the container in its own order;
  simplest code, rings can be covered. **(c) Keep today**: close IN-113 with no work item;
  WI-118's drag re-sync stays the mechanism and every future per-token drawing must
  remember it.
