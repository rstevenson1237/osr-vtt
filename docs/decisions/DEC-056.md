## DEC-056 — The big documents become indexes over per-entry files, rather than being trimmed

**Closed 2026-08-07** — agent default under Default-and-notify, surfaced in WI-069's
completion summary. Reversible: the per-entry files concatenate back in index order.

- **Question.** `SPEC.md` (1711 lines), `DECISIONS.md` (1694) and `PLAN-COMPLETED.md`
  (1972) are too large to read whole on a metered allocation. The audit that prompted
  WI-069 proposed **archiving the dead parts** — superseded specs, closed decisions —
  into `docs/archive/`. Is that the right cut?
- **Recommendation.** **No — split by entry instead.** Archiving trims a fraction of a
  file that is still read whole; splitting means the file is never read whole at all.
  `SPEC.md`'s superseded set is two specs out of thirty-four, so the archive cut would
  have removed ~6% of one on-demand file.
- **Impact.** Every id is now addressable at a derivable path (`docs/spec/SPEC-nnn.md`,
  `docs/decisions/DEC-nnn.md`, `docs/completed/WI-nnn.md`), and the indexes are 86, 405
  and 110 lines. Cross-references of the form "`DECISIONS.md` → Closed, DEC-001" had to be
  repointed. The cost is more files and a `git log` that no longer shows one document's
  whole history in one path.
- **Alternatives.** (a) The proposed archive cut — rejected as above, and it additionally
  required either disabling the RULE-020 hook or amending RULE-020, for a smaller gain.
  (b) Split, but write the extracted text under `docs/archive/` — rejected: RULE-020 calls
  that directory the immutable reconciliation reference for the _original_ pre-split
  documents, and these files are live, editable content. (c) Do nothing and rely on the
  read-by-section rule alone — that rule does most of the work, but a 1700-line file
  invites being read whole by any agent that forgets it.
- **Answer.** Split by entry, under `docs/spec/`, `docs/decisions/` and `docs/completed/`.
  Nothing under `docs/archive/` was written or edited, and the guard hook stayed armed
  throughout.
