## DEC-113 — Hex fog is a `revealed` flag on `HexTile`, painted by a Reveal tool

**Closed 2026-09-23** — answered by the user under `/work-item` (IN-192).

- **Question.** Fog is square-lattice only, so a hex crawl has no unexplored state. How is a
  revealed hex stored, and how does the referee reveal one?
- **Answer.** (user, 2026-09-23) **`HexTile` gains optional `revealed: true`** (next schema
  version). Absent = hidden. Revealing an empty hex creates a tile doc carrying only the flag;
  hiding it again removes the flag, and a tile left with no fields is deleted. **No backfill**:
  hex fog follows the map's existing `fog.enabled`, which is absent (off) on every hex map
  today, so nothing hides until the referee turns it on. A **Reveal / Hide hex tool** paints
  by click or drag, committing one batched write on release (RULE-003), with **Reveal all**
  and **Reset** as square fog has.
- **Impact.** RULE-007 (migration, migration test, `.vttcamp` round-trip). A new hex-space
  consumer (RULE-006): it reads axial keys only and never reaches a square-lattice consumer.
  As with square fog, hiding is client-side under the trust model (RULE-008); it is not a
  `gmPrivate` boundary.
- **Alternatives.** A separate `hexReveals` collection; one `revealedHexes` array on the map
  doc (bounded by the 1 MB document limit); a checkbox in `HexTilePanel` instead of, or beside,
  the tool.
