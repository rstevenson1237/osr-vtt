## DEC-134 — IN-205: who owns the selection once three seams write it?

**Open** — raised 2026-10-10 under `/work-item` (IN-205). Blocks WI-229.

- **Question.** IN-205 moves the Select gesture out of `VectorMapView` (SPEC-067). Since
  WI-181 the selection it writes has four mutually exclusive slots (vertex handles,
  objects, tokens, background), written from three seams: the Select gesture, the token
  layer (IN-199) and the background controller (WI-227). Today each writer keeps the
  exclusion by clearing the other three by name, in five places. Once those are separate
  controllers, none can name another's variables. Where does the selection live?
- **Recommendation.** **(a) A shared `MapSelection` model plus a `SelectionController`.**
  A small state class holds the four slots; each writer method empties the others, so the
  exclusion lives in one place. The component builds it first and hands it to every seam
  that selects. The gesture (pick, drag, lasso, rotate, delete) is a separate SPEC-060
  controller over it (SPEC-067 §2–§3).
- **Impact.** No stored data, store, rules, layer or testid change. One test-only readout
  (`selection-count`) becomes `$derived` and so stops going stale after a token click.
  IN-199 and IN-204 are handed a settled selection, so this item runs before both, which
  reverses WI-171's "IN-205 last". WI-227's background pick is repointed at the model.
- **Alternatives.** **(b) The `SelectionController` owns all four slots.** One class
  instead of two, but the token layer and background controller would depend on the whole
  gesture just to say "I picked something". **(c) Verbatim move.** Handles, objects and the
  gesture move; tokens and background keep their own slots and the gesture is handed
  `clearTokens`/`clearBackground` callbacks. The smallest diff, but the exclusion stays
  spread over every writer and each later extraction adds callbacks. **(d) Don't extract.**
  Close IN-205 with no work item; about 330 lines stay in the component, untestable
  without a browser.
