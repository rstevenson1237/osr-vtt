## DEC-062 — Multiple backgrounds are a subcollection; `GameMap.background` narrows to colour-only

- **Question.** IN-053 asks for multiple background images, each independently movable and
  resizable with a locked aspect ratio. `GameMap.background?: { ref: string } | { color:
  string } | null` is one field, an image ref or a colour, with no position or size. What
  storage shape replaces it?
- **Recommendation.** A new sparse subcollection, `rooms/{roomId}/maps/{mapId}/backgrounds/
  {bgId} = { ref, x, y, w, h, order }`, geometry in lattice units per RULE-006 — the same
  pattern `floorRegions` already uses for edit-locality and per-document writes. `x, y, w, h`
  is the placed rect in the map's coordinate space; `order` breaks stacking ties for
  overlapping images (`layers.background` paints in `order`). `GameMap.background` narrows
  to `{ color: string } | null` only — a solid colour is not an image and stays exactly what
  it is today: the renderer's clear colour (`setBackgroundColor`), not a layer, per SPEC-029
  §2's standing note. The two are compatible: a colour still shows through anywhere no
  background image covers it.
- **Impact.** Schema bump to **v23** (RULE-007): a migration moves an existing `{ ref }` into
  the first `backgrounds` document, sized to the full map grid so nothing visibly moves for
  an existing room. `.vttcamp` export/import round-trips the new subcollection the same way
  it already round-trips `floorRegions` and `symbols`. New `CampaignStore` methods —
  add/update/remove/reorder a background — go into the contract suite against both
  `MemoryStore` and `FirebaseStore` (RULE-001). `firestore.rules` needs a rule (and a rule
  test, RULE-004) for the new subcollection path — the existing per-room member-write model
  extends to it with no new boundary. `exportPng`'s background-colour compositing gotcha
  (SPEC-029 §2) is unaffected; a background *image* extract now has to iterate the
  subcollection instead of reading one field.
- **Alternatives.** (a) An array field on `GameMap` itself — no subcollection, simpler
  migration, but every background edit (a single drag) rewrites the whole map doc, which
  RULE-003's write-discipline reasoning argues against for anything that could be dragged
  interactively. (b) Keep exactly one background and add a transform to it — smaller change,
  but drops the "multiple" half of the request outright; declined in favour of the full
  ask.
- **Answer.** User, 2026-08-11 — subcollection, chosen as recommended; solid colour stays on
  `GameMap.background`.
