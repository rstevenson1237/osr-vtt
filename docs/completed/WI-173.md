# WI-173 — One home for per-map configuration

**Closed 2026-09-23.** From IN-157 (`INT-UX-05`). **Investigation — a placement proposal,
no production code changes** (RULE-015). Model target `sonnet`, run on `sonnet`; effort
`high`.

Built by reading the three surfaces IN-157 names — `SessionActivity.svelte` (Session
settings), `AssetsActivity.svelte` + `MapsPanel.svelte` + `BackgroundsPanel.svelte`
(Assets), and `MapToolsSheet.svelte` → `MapToolPalette.svelte` → `MapToolbar.svelte` (Map
tools) — plus the schema they read and write (`packages/shared/src/types.ts`,
`schemas.ts`, `campaign-store.ts`) and the e2e specs that pin their current shape
(`session-config.spec.ts`, `backgrounds.spec.ts`).

## 1. What is actually stored where

The schema already answers half the question. `GameMap` (`types.ts:168`) carries `grid`,
`gridSettings`, `measure` and `fog` directly — all four are **per-map fields**, each with
its own `CampaignStore` setter (`setMapGridDimensions`, `setMapGridSubdivide`,
`setMapMeasurement`, `setMapFogEnabled`) that patches the map document, not the room
document. `RoomSettings` (`types.ts:298`) has no `grid`/`measure`/`fog` fields at all —
they were moved off it before this investigation, per the comment at `types.ts:141` ("see
`GameMap` for grid/background/measure, moved off `Room`"). `SessionActivity.svelte`'s own
comment agrees: `// ---- Grid & measurement (per map, Master Plan v2, R17.3) ----`
(line 192). The data has known its home for a while; the UI has not followed.

`MapToolController`'s `snapMode`, `exportMaxLayer` and per-tool simplify tolerance
(`map-tool-controller.svelte.ts:185,260,269`) are the opposite: `$state` fields that live
only in the current client's memory, reset on reload, never written to `GameMap` or
anywhere else. They are not configuration in IN-157's sense — they are how one client is
using a tool right now, same category as which tool is selected.

This is the fact the rest of the proposal turns on: **grid, cell size, half-grid,
measurement and fog are the same kind of thing — persisted, per-map, GM-set, synced to
every client. Snap/simplify/export are a different kind of thing — ephemeral,
per-client, reset on reload.** "Find the one home" is really two questions with two
different answers, and conflating them is what produced three surfaces.

## 2. The precedent already in the codebase

Assets already absorbed two per-map concerns out of Session settings, and both moves
left their reasoning in place as comments:

- `AssetsActivity.svelte:31-34` — *"Maps moved here from Session settings: which maps a
  session has is a question about its assets, and it sits naturally beside the room
  list, which is scoped to a map. The active map's **backgrounds** followed them
  (SPEC-038 §5), for the same reason and out of the same Session settings."*
- `BackgroundsPanel.svelte:18-24` — background images and the solid colour are "managed
  here, beside `MapsPanel`'s per-map management, because which images a map shows is a
  question about its assets."

Fog has its own history in the other direction: `SessionActivity.svelte:616-618` — *"The
on/off switch is a per-map session setting, not a drawing tool — it moved here out of
the Map tools sheet (playtest feedback), which now carries only the fog **authoring**
controls."* That move was never "Session settings is fog's home"; it was "fog is
configuration, not a drawing action" — the same axis this proposal turns on, applied one
surface earlier. Moving fog again, into Assets, extends that reasoning rather than
reversing it: Map tools keeps the authoring controls (Fog carve modes, Reveal all /
Reset fog) exactly as that comment intends, because those *are* drawing actions.

Grid/measurement/fog were left behind in Session settings only because SPEC-038 (the
backgrounds work) scoped itself to backgrounds. Nothing about them argues for Session
settings over Assets; everything that already moved argues the other way.

## 3. The proposal

**One home for persisted per-map configuration: the Assets activity**, as a new panel
sitting between `MapsPanel` and `BackgroundsPanel` — after the map is picked, before its
backgrounds are placed, since `fitBackgroundToGrid` already depends on the grid
dimensions being meaningful. It would fold in the two sections currently in
`SessionActivity.svelte`:

- **Grid & measurement** (`session-grid-w/h/cellsize/apply/error`,
  `grid-subdivide-toggle`, `measure-per-square/unit/apply`) — unchanged content and
  hex-aware label (`measureIsHex` picks "Per hex"/"Per square", SPEC-049 §2).
- **Fog of war** (`fog-enabled-toggle`) — unchanged content and hint text.

No store or schema change: `setMapGridDimensions`, `setMapGridSubdivide`,
`setMapMeasurement` and `setMapFogEnabled` are already map-scoped `CampaignStore` calls
callable from anywhere holding `roomId`/`map.id`, exactly as `BackgroundsPanel` already
calls map-scoped setters. `AssetsActivity` already threads `map: GameMap | null` and
`isGM` down to `BackgroundsPanel`; the new panel needs the same two props plus `roomId`,
already in scope. This is a relocation of markup and its local `$state` drafts, not new
plumbing.

**Map tools sheet is unchanged.** Snap mode, simplify tolerance and the PNG export
max-layer picker stay on `MapToolbar`, where the tool they parameterize already lives.
They were never mis-homed by the same test that flags the other four — they are not
`GameMap` fields — so "find the one home" resolves them by leaving them alone, not by
moving them a third time.

### Why this is Deceptive, not Simple

`session-grid-w`, `session-grid-h`, `session-grid-cellsize`, `session-grid-apply` and the
`session-grid` section id are read directly by `session-config.spec.ts` (the grid-set
assertions and the Gate 13 section-nav list) and by `backgrounds.spec.ts`'s
`setSmallGrid` helper. RULE-005 fires the moment those move. This matches IN-157's own
classification note (`INTAKE.md`): *"each resulting move is its own Deceptive intake
item."*

`grid-subdivide-toggle`, `measure-per-square`, `measure-unit`, `measure-apply` and
`fog-enabled-toggle` carry no `session-` prefix and can keep their ids as-is; only the
four `session-grid-*` ids and the `session-grid`/`session-fog` section ids need renaming
(e.g. to `mapconfig-grid-*` or similar — the executing item picks the convention,
matching `background-*`'s precedent of dropping the stale surface name rather than
keeping it). `session-config.spec.ts`'s Gate 13 `sectionIds` list also loses
`session-grid` (and never had `session-fog` in it — that section already isn't
nav-tested), which is itself an assertion that has to move with the panel.

### One finding raised, not fixed

`README.md`'s Session settings section (around "Grid & measurement") states
`room.settings = { theme, measure: { perSquare, unit }, grid: { subdivide },
defaultPlayerGroup }`. That shape is stale: `RoomSettings` (`types.ts:298`) has no
`measure` or `grid` field today — both are `GameMap` fields, per §1 above. This predates
IN-157 and is independent of where the UI lives; it is not fixed here (this investigation
changes no file), and is raised as an intake item below rather than folded into the move
it happens to sit next to.
