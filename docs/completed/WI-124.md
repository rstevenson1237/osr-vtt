# WI-124 — The hex/square boundary

**Spec:** SPEC-047 §11 · **From:** IN-121, IN-124, IN-128 · **Agent:** `claude-code` ·
**Model:** `sonnet` · **Effort:** S · **Closed:** 2026-09-11

## Changes made

- `apps/web/src/lib/shell/map-tool-controller.svelte.ts` — `setHexMap` now carries two
  more consequences alongside the existing active-tool fallback:
  - **Entering** (`on: true`) calls `this.setSnapMode('hex')` after the existing
    `isHexTool` check, so the Snap selector no longer renders blank on a mode
    (`'full'`, whatever a square map last left it at) the hex palette's `SNAP_MODES`
    doesn't offer. Goes through `setSnapMode` rather than writing `snapMode` directly,
    so the band width carries along with it (SPEC-028 §7's existing coupling).
  - **Leaving** (`on: false`) now falls the active tool back to `'pan'` when it holds a
    hex-only tool (`hexSymbol`, `road`, `river`, `hexLabel`, `hexTerrain`) — none of
    which has a `TOOL_GROUPS` entry, so the square palette would otherwise show no
    button active while one stayed armed on a map with no `HexPoint` space to write
    into. Checked via `groupForTool(this.activeTool)` returning `undefined`, the mirror
    of the `isHexTool` check entering already does. Also resets `snapMode` to the
    square default (`'full'`) via `setSnapMode`.
  - `groupForTool` added to the import from `../map/tool-groups`.
- `apps/web/src/lib/map/tool-groups.ts` — `'eye'` removed from `HEX_TOOL_IDS`. The Eye
  stays an unmodified `TOOL_GROUPS` `view`-group member (same testid, same cursor, same
  behaviour on every square map) but is no longer part of the hex crawl's palette
  subset, since a hex map has no walls and no carved floor for it to answer a question
  about. Doc comments on both `HEX_TOOL_IDS` and `setHexMap` updated in place to record
  the new snap-mode and Eye-exclusion behaviour.
- Test updates in the same two files' suites:
  - `apps/web/src/lib/map/tool-groups.test.ts` — the `HEX_TOOL_IDS` equality assertions
    drop `'eye'`; a new test pins that the Eye is still a `view`-group member
    (`groupForTool('eye')?.id === 'view'`) but not `isHexTool`; the "no lattice-writing
    tool survives" test's subset check is adjusted to exclude Eye from the expected
    `TOOL_GROUPS ∩ isHexTool` set.
  - `apps/web/src/lib/shell/map-tool-controller.test.ts` — the "leaves an already-active
    view tool alone" case drops `'eye'` (renamed to "hex-palette view tool"); new cases
    added: entering a hex map with the Eye active now falls back to Pan; entering
    selects `'hex'` snap and leaving returns to `'full'`; leaving a hex map with any of
    the five hex-only tools active falls back to Pan.

## Visible behavior changes

- Opening a hex map's Snap selector immediately shows **Hex** selected, instead of
  rendering blank until a referee picks a mode themselves.
- The Eye button no longer renders in a hex map's View row at all (`MapToolbar`'s
  `toolSubset` is `HEX_TOOL_IDS`, which the Eye no longer belongs to) — it is
  unchanged on every square map. If a referee somehow entered a hex map with the Eye
  active, entering now falls it back to Pan instead of leaving it armed with no button
  showing it active.
- Leaving a hex map while a hex-only tool (Symbol, Road, River, Label, Terrain) is
  active now falls the active tool back to Pan instead of leaving it armed with no
  corresponding button on the square palette.

## How to verify

- `pnpm verify` (lint + typecheck + unit) — green.
- Manually: open a hex map — the Map tools rail's Snap selector should read **Hex**
  immediately, with no blank state. The View row should show Pan/Measure/Ping but not
  Eye. Arm the hex Symbol/Road/River/Label/Terrain tool, then switch to a square map (or
  leave the hex map) — the palette should show Pan active, not a hex-only tool with no
  visible button. On a square map the Eye button is unchanged.
