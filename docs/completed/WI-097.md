# WI-097 — Bevelled edges: one body group past the value range, `bodyGroupIndex`

**Spec:** SPEC-045 §4 · **From:** IN-082 · **Decision:** DEC-079 · **Model:** `opus` ·
**Effort:** L · **Closed:** 2026-09-03

Real dice have no sharp edges; the generated set did, and with `flatShading` that read as a
faceted gem. SPEC-045 §3's normal map (WI-095) supplied the edge highlight without touching
geometry, but not the **silhouette** — a d6's corner against a light background stayed
geometrically sharp — so §4 was held until §3 had shipped and been looked at, and until §5
(WI-096) made die-to-die contact reachable so `hullPoints` could be judged against it.

Every value face is now inset **in its own plane** by a constant width, and the band that
opens up is filled with an edge strip per edge and a corner patch per vertex. That geometry
carries no value, so all of it goes into one additional material group past the value range
(DEC-079). Nothing that iterates `0 … faceCount-1` changed.

## Changes made

- **`apps/web/src/lib/dice/geometry.ts`**
  - New bevel section: `BEVEL` (0.022, stated in **world** units — post-`SCALE`, because a
    shape's own unit-vertex space is not shared: the cube's face spans 2 and the
    icosahedron's triangle about 1, so one unit-space width would give the d6 a hairline
    and the d20 a chamfer half its face), `BEVEL_MAX_FRACTION` (0.22, a ceiling on the
    bevel as a fraction of a face's inradius so no future retune can collapse a facet),
    `facePlaneNormal`, `edgeInwardNormals`, `insetFace` and `faceInradius`.
  - `insetFace` offsets every boundary edge inward by exactly `width` and takes the
    corners where adjacent offset edges meet, rather than scaling the polygon toward its
    centroid — that is what makes the bevel a **constant width** all the way round. On a
    regular polygon the two agree; on the d10's kite a centroid scale would run from a
    hairline along the short edges to several times that along the long ones.
  - `facePlaneNormal` (Newell) is a **separate vector from the face's locator**. A locator
    is the centroid direction, and for a face that is not centro-symmetric — the d10's
    kites — the centroid is not the foot of the perpendicular from the die's centre. The
    locator keeps its definition; the inset needs the true plane, or a bevelled kite stops
    being flat.
  - `edgeInwardNormals` settles its sign against the face centroid, never against the
    winding order: the tetrahedron's four faces wind **inward**, the trapezohedron's ten
    alternate, and the rest wind outward. Nothing downstream ever depended on that and the
    bevel does not start to.
  - `buildDieGeometry` restructured into three passes — planes and inset corners; the
    value faces (groups `0 … faceCount-1`, UVs projected from the inset corners so the
    glyph keeps its margin inside the facet actually drawn); then the body (edge strips,
    corner patches) as one group. `faceGlyphUp` is still asked about the **original**
    face, so no bevel-width change can rotate a numeral.
  - **`computeVertexNormals()` is gone; the `normal` attribute is authored.** A facet's
    triangles get their own flat normal (bit-for-bit what `computeVertexNormals` produced,
    so faces are unchanged); each bevel corner gets the normal of the value face it was
    inset from, so a strip interpolates from one face's normal to its neighbour's and a
    smooth-shaded body material reads it as a rounding rather than as two more flat
    facets per edge. Every authored normal agrees in sign with its own triangle's winding
    — the invariant `DoubleSide` lighting rests on, given the winding disagreement above.
  - `DieGeometry` gains **`bodyGroupIndex: number`** (always `faceCount`), so the
    convention is stated in the type rather than re-derived by arithmetic at each call
    site. `hullPoints`' doc comment now records the measured recession and why the hull
    is not inset.
- **`apps/web/src/lib/dice/textures.ts`**
  - New `bodyMaterial(theme, face, variant)`: untextured `MeshStandardMaterial` in the
    same colour the face texture paints its background, `flatShading: false` against the
    face materials' `true` — the per-material split DEC-079 chose this structure for.
    Cached per `(theme, face colour)` in its own `bodyCache`, cleared by
    `clearDiceMaterialCache`.
  - This is the one place a die's colour is a `material.color`, which is not an exception
    to the module's rule so much as the case the rule was never about: `color` misleads by
    _multiplying_ a `map`, and there is no map here.
- **`apps/web/src/lib/dice/scene.ts`**
  - `buildMesh` appends `materials[g.bodyGroupIndex]` via a new `bodyMaterialFor` helper;
    a dropped die gets a clone to dim, tracked in `tintDisposables` (material only — the
    body owns no texture). Both the d4 composite branch and the atlas branch reach it.
  - Top-of-file doc comment records that the materials array is one entry longer than the
    value count and that this is the only place the extra group is visible.
- **`apps/web/src/lib/dice/geometry.test.ts`** — the old "one group per face" assertion is
  replaced by SPEC-045 §4's binding test (value groups `0 … faceCount-1` with matching
  `materialIndex`, body one past at `bodyGroupIndex`, `locators.length` still the value
  count, groups tiling the buffer with no gap or overlap), plus three more: every value
  facet stays in its original face's plane; every bevel vertex is inside the collider hull
  and the recession is under 10% of the circumradius; every authored normal is unit length
  and winding-consistent. `facesOf` and the corner-alignment test now slice to the value
  groups, since neither recovery means anything on the body group.
- **`apps/web/src/lib/dice/textures.test.ts`** — new `bodyMaterial` describe block pinning
  the seam: the body's colour equals, component for component, what an `SRGBColorSpace`
  `CanvasTexture` sample of the same hex decodes to (including that
  `THREE.ColorManagement.enabled` is on, which is the load-bearing half), the d100 `tens`
  shade follows its faces, `flatShading` is `false`, and the material carries no map.
- **`README.md`** — new bevel bullet in Dice (II.6) covering the group layout, the
  `flatShading` split and the authored normals, the seam, the `hullPoints` decision and
  the triangle cost; the quality-bar bullet's `flatShading: true` is qualified as
  per-material.
- **`docs/spec/SPEC-045.md`** — §4 annotated with the two judgements it deferred, both now
  made; status → **Completed** (all five sections shipped). **`SPEC.md`** row updated.
- **`PLAN.md` / `PLAN-COMPLETED.md` / `INTAKE.md`** — WI-097 closed and IN-082 moved to
  §1.2.

## The two judgements SPEC-045 §4 deferred

Both were made by looking, in a headless render (the project's own `three`, served by
Vite, screenshotted with the pre-installed Chromium) — the same method WI-094 used.

- **The seam is clean**, and it was checked first as §4 requires. `THREE.Color` parses a
  hex as sRGB into the linear working space and the face's `CanvasTexture` carries
  `SRGBColorSpace`, so the identical hex reaches the identical linear triple
  (`0x3f5fb0` → `0.049707, 0.114435, 0.434154` both ways). No ring appears where bevel
  meets face at any magnification tried. A unit test pins it so a colour-management
  regression cannot land quietly.
- **`hullPoints` stays the un-bevelled cloud** — §4's default, not its escape hatch. The
  recession is at most **9.4% of the die's own radius**: d4 0.0415, d8 0.0352, d20 0.0256,
  d6 0.0250, d10 0.0187, d12 0.0161 world units, against radii 0.44–0.58. A **face**-first
  contact — the resting case — has **no gap at all**, because the inset happens in the
  face's own plane and never moves it. The exposure is a corner-first contact, and the
  worst case the physics can reach was rendered directly: a d4 balanced apex-down on a d6
  at exactly the hull distance. At the renderer's own camera that is about four pixels on
  a die ninety across; it only resolves into a visible sliver at ten times that
  magnification, and an apex-down tetrahedron is not a resting state. Insetting the hull
  would have traded that for contact-solver interpenetration in the common face-first
  case, which is the direction §4 calls unsafe.

## Visible behavior changes

- **Dice have rounded edges and corners.** Every shape's silhouette is bevelled: a d6's
  corner against a light background is no longer geometrically sharp, and the edge catches
  the key light as a smooth rounding rather than a hard facet junction. The value faces
  themselves are unchanged — same plane, same crisp flat shading, same incised numerals.
- **Numerals sit fractionally smaller** relative to the die, because the UV projection now
  fits the numeral square to the inset facet rather than the original face, keeping the
  same margin inside the facet that is actually drawn. A few percent; the glyph's
  orientation, position and family are untouched.
- Nothing else: no change to values, to the face→value remap, to how a landed face is
  read, to die colour, to the throw, or to any control.

## How to verify

- `pnpm verify` — lint + typecheck + unit. `apps/web/src/lib/dice/geometry.test.ts`
  carries SPEC-045 §4's binding test and the three structural guards; `textures.test.ts`
  carries the seam.
- `pnpm verify:all` — the above plus the rules/store/e2e suites against the emulator,
  including `dice-overlay.spec.ts`.
- By eye: roll any die from the tray. The edges read as rounded, the bevel is the same
  colour as the face with no ring at the join, and the numeral is unchanged.

## Deviations

- **`computeVertexNormals()` replaced by an authored `normal` attribute** — required to
  unblock the work item rather than chosen. §4 and DEC-079 both specify the `flatShading`
  split as the payoff of the one-extra-group structure, but `flatShading: false` is inert
  over a buffer of duplicated per-triangle vertices: every vertex of a triangle already
  carries that triangle's own normal, so smooth shading interpolates a constant. Authoring
  the attribute is the only way the specified split produces a smooth bevel. Facet normals
  are unchanged by construction and a test pins that every normal stays winding-consistent.
- **SPEC-045 marked Completed and its `SPEC.md` row updated.** §4 was the last of the five
  sections; leaving the spec Active would have misreported it. No section text was changed
  beyond §4's annotation.
- The gate's last standing constraint — "the user having looked at WI-095's result" — was
  taken as cleared by the user starting this item. WI-095 and WI-096 had both landed.
