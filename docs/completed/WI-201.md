# WI-201 — Disconnected → read-only room

SPEC-058, DEC-121. Single unit (Shape A). IN-219 (absorbs IN-215). Supersedes WI-186
(executed 2026-09-26, reverted — the persistent Firestore cache serialised listener
re-subscribes and stalled the map view's remount by ~4.7 s).

## Changes made

- `packages/shared/src/store/campaign-store.ts` — new interface method
  `subscribeConnection(cb: (connected: boolean) => void): Unsubscribe` (RULE-001),
  documented against SPEC-058 §1.
- `packages/shared/src/store/firebase-store.ts` — implements it by reading RTDB
  `.info/connected` via `onValue`.
- `packages/shared/src/store/memory-store.ts` — implements it by firing `cb(true)` once
  (`queueMicrotask`) and never again; `LocalStore` inherits this unchanged, so the local
  build never reports disconnected (RULE-009).
- `packages/shared/src/store/campaign-store.contract.ts` — a `subscribeConnection` case
  in the "single-value docs" describe block: fires once, `true`, against a running
  backend. Unsubscribe is not independently re-tested, the same documented reason
  `subscribeAuth`'s own case gives: no safe way to force a second connectivity change on
  a client the rest of the suite shares.
- `apps/web/src/lib/shell/connection-debounce.ts` (new) — `ConnectionDebounce`: a plain
  class (not a `.svelte.ts` rune store, so its timing is testable with a fake clock with
  no Svelte runtime involved) that turns a raw `connected` reading into a debounced
  `disconnected` signal — locks only after `false` holds continuously for 2 s, unlocks on
  the first `true` with no delay.
- `apps/web/src/lib/shell/connection-debounce.test.ts` (new) — six cases against
  `vi.useFakeTimers()`: no lock on `true`; locks at exactly the delay boundary; a blip
  before the delay cancels the pending lock; unlocks immediately once locked; a repeated
  `false` while already locked doesn't re-fire `onChange`; `dispose()` cancels a pending
  timer.
- `apps/web/src/lib/components/RoomShell.svelte`:
  - Subscribes to `store.subscribeConnection` in `onMount` (unconditionally — harmless on
    the local build, since `MemoryStore`/`LocalStore` always report `true`), feeding a
    `ConnectionDebounce` whose `onChange` writes `disconnected: boolean` (`$state`).
  - A dev-only override (`window.__setConnectionOverride`, gated on
    `import.meta.env.DEV`, so it never reaches a production build) lets a test force the
    reading, since the Firebase Emulator Suite has no way to drop just one browser
    context's connection (SPEC-058 §3).
  - `onGlobalKey` returns early when `disconnected` — a `keydown` on `window` reaches
    every listener regardless of any element's `inert` state, so this is the half of the
    lock `inert` alone can't cover.
  - The markup: everything the joined-room view renders (both the mobile and desktop
    layouts, every quick sheet, the Log/Session modals, the dice overlay, the map-change
    notice, and every dialog) now sits inside one `<div class="room-content" inert={disconnected} data-testid="room-content">`
    wrapper (`display: contents`, so it changes nothing in the layout while connected). A
    **Disconnected — reconnecting…** banner (`data-testid="connection-banner"`), with a
    lobby link (`connection-banner-lobby`), renders as that div's sibling — the one thing
    left interactive while locked. `connectionDebounce.dispose()` added to `onDestroy`.
  - `disconnected`/`connected` CSS: `.room-content { display: contents; }` and
    `.connection-banner { position: fixed; top: 0; … }`.
- `apps/web/tests/e2e/connection.spec.ts` (new) — drives the dev-only override end to
  end: connected on join; a `false` reading inside the 2 s window shows no banner and no
  lock; past the window the banner appears, `room-content` carries `inert`, and `?`
  (which normally opens the shortcut sheet) does nothing; the lobby link stays visible and
  reachable; a `true` reading clears the banner and the lock immediately, and `?` works
  again.
- `README.md` — "Room load, creation and version" (SPEC-054 §§2, 10, 11) gains a
  **Disconnected** paragraph describing the whole mechanism (`subscribeConnection`,
  `ConnectionDebounce`, the `inert` wrapper, the dev-only override) and names the
  WI-186 revert as the reason the persistent cache isn't there instead.

## Visible behavior changes

On the hosted build: a client that loses its connection for 2 continuous seconds sees a
**Disconnected — reconnecting…** banner across the top of the screen. Everything else on
screen freezes at its last snapshot — no click, focus, or keystroke reaches it — except
the banner's own link back to the lobby. The lock lifts the instant the connection is
reported back, no delay. A drop shorter than 2 s (a blip) shows nothing. The local build
is unaffected: it never shows the banner and never locks. Firestore was already on the
SDK's default memory cache (the persistent cache from WI-186 was reverted before this
item began) — this item does not touch that; it adds the connection signal and the lock,
nothing about caching.

## How to verify

- `pnpm verify:all` — green (lint, typecheck, unit, rules, store, and the full e2e
  battery, including `connection.spec.ts` and `backgrounds.spec.ts`).
- `pnpm --filter @osr-vtt/shared test:unit` covers the `subscribeConnection` contract
  case against `MemoryStore`; `pnpm test:store` (inside `firebase emulators:exec`) covers
  it against `FirebaseStore`.
- `cd apps/web && npx vitest run src/lib/shell/connection-debounce.test.ts` — the 2 s
  debounce, in isolation.
- `pnpm test:all:emulators` (or `pnpm --filter @osr-vtt/web exec playwright test
  tests/e2e/connection.spec.ts` inside `firebase emulators:exec`) — the banner/lock, end
  to end.
- Manually: open a room, then in the browser console run
  `window.__setConnectionOverride(false)` — the banner appears after ~2 s and the shell
  stops responding to clicks and keys; `window.__setConnectionOverride(true)` clears it
  immediately. (Dev server only — `import.meta.env.DEV`.)

## Deviations

- **The banner's "reachable" control is only the lobby link, not also "Sign out"** as
  DEC-121 point 3 said. `AccountControls` (the only place "Sign out" exists in this app)
  shows it solely for a Google-linked identity — an anonymous player or referee sees "Save
  identity" instead, and both actions need a live network call, which is exactly what's
  missing while genuinely disconnected. Reusing it inside the banner would offer a control
  that cannot work in the state it is offered for, or need popups the disconnected state
  makes pointless. The lobby link is the one action that works client-side, with no
  network, matching the room-not-found banner's own precedent (`room-not-found-lobby`).
  This is a scoped-down reading of the DEC-121 text, not a RULE-015 exception — no code
  outside the approved item was touched.
- **SPEC-058 §3's "local-build e2e asserts the banner never appears" is not built.** This
  repo has no Playwright project that drives a local-build dev server — `vite build
  --mode local-build` is a static build, not something `playwright.config.ts`'s
  `webServer` can point at — so there is no local-build e2e harness for such a spec to
  join. The guarantee is instead proved at the contract-suite level: `MemoryStore`
  (which `LocalStore` inherits from unchanged) is pinned to fire `subscribeConnection`
  once with `true` and never again, which is the actual mechanism that keeps the local
  build from ever locking. Building a local-build e2e harness from scratch is out of this
  item's scope; if it's wanted, it is its own intake item.
- No RULE-015 Deviations-budget or unblock fixes were used — no fix outside the approved
  item's own files was made.
