## WI-080 — Multiple backgrounds: the `backgrounds` subcollection, schema v23 + migration, `.vttcamp` round-trip, `firestore.rules` + rule tests, new `CampaignStore` contract methods

SPEC-038 §§1–2, from IN-053, DEC-062. §§3–5 (the transform UI, the alignment
grid, and the move into the Assets activity) are WI-081 and are not in this
change.

**Changes made.**

- `packages/shared/src/types.ts` — `CURRENT_SCHEMA_VERSION` 22 → **23**. New
  `MapBackground` interface (`id`, `ref`, `x`, `y`, `w`, `h`, `order`) —
  `rooms/{roomId}/maps/{mapId}/backgrounds/{bgId}`, geometry in lattice units
  as floats (RULE-006), `order` lowest-painted-first. `GameMap.background`
  narrows to `{ color: string } | null`: a solid colour is not an image and
  stays the renderer's clear colour.
- `packages/shared/src/schemas.ts` — new `MapBackgroundSchema` (`w`/`h` must be
  positive; nothing is `.int()`, since lattice units are floats).
  `GameMapSchema.background` drops the `{ ref }` arm, so an image ref on a map
  doc is now a parse error rather than accepted-and-ignored.
- `packages/shared/src/converters.ts` — `mapBackgroundConverter`, the same
  id-strip/reattach shape as `mapSymbolConverter`.
- `packages/shared/src/migrations/index.ts` — the **v22 → v23** entry (a room-doc
  no-op, like its four predecessors: both halves live on `maps/{mapId}`
  documents, which `migrateRoom` never sees) plus `foldLegacyMapBackground`, the
  document half: it moves a pre-v23 `background: { ref }` into one background
  sized to the full map grid (`x: 0, y: 0, w: grid.w, h: grid.h, order: 0`) and
  clears the field. Idempotent and version-agnostic — it keys off the field, not
  off a stored version — and returns its input by reference when there is
  nothing to fold.
- `packages/shared/src/store/campaign-store.ts` — `backgrounds` joins
  `EXPORTED_MAP_COLLECTIONS` (so the generic export / import / `deleteRoom` /
  `deleteMap` loops cover it) and `BATTLE_MAP_SOURCE_COLLECTIONS` (a battle map
  shares the source's lattice space, so a rect means the same thing on both).
  Five new interface methods — `subscribeBackgrounds`, `addBackground`,
  `setBackgroundTransform`, `setBackgroundOrder`, `removeBackground` — plus
  `migrateMapBackgrounds(roomId)`, the write half of the fold. `setMapBackground`
  is **gone**: it pointed the narrowed field at an asset ref.
  `setMapBackgroundColor`/`removeMapBackground` stay and now concern the colour
  alone.
- `packages/shared/src/store/memory-store.ts`,
  `packages/shared/src/store/firebase-store.ts` — both implementations.
  `MapBucket` gains a `backgrounds` collection; `MemoryStore.addBackground`
  validates through `MapBackgroundSchema` exactly as the converter does on the
  Firebase side. Both `migrateMapBackgrounds` implementations read the map docs
  **raw** (no converter), for the reason `ensureActiveMap` does: the schema now
  strips the very field the fold exists to rescue.
- `packages/shared/src/store/campaign-store.contract.ts` — four new tests
  (place/move/reorder/remove; several independent backgrounds on one map, where
  editing one leaves the other alone; images and a colour coexisting, and
  clearing the colour not clearing the images; the fold, including idempotence).
  The suite takes a third parameter, `seedLegacyMapBackground`, because a
  pre-v23 map doc is by definition no longer expressible through the interface.
  The old `setMapBackground` test is replaced; the colour test now swaps colour
  for colour instead of colour for image.
- `packages/shared/src/store/memory-store.test.ts`,
  `packages/shared/src/store/firebase-store.contract.test.ts` — each supplies its
  seeding hook (a direct `setDoc` into the backing collection; a raw
  `updateDoc` against the emulator).
- `packages/shared/src/portability/vttcamp.ts` — `foldMapBackgrounds` applies the
  fold to every map on import, on both the current-shape and the pre-v11
  legacy-adoption branches; a folded document gets the fixed id
  `legacy-background` (the module is pure, and the id only has to be unique
  within one map's collection). `collectAssetRefs` now scans each map's
  `backgrounds` collection instead of the map doc's `background.ref`.
- `firebase/firestore.rules` — `maps/{mapId}/backgrounds/{backgroundId}`:
  `read: signedIn()`, `write: isMember(roomId) || isGM(roomId)` — the existing
  per-room member-write model, no new boundary (SPEC-038 §1). The referee-only
  management gate (DEC-063) is a UI gate, as `MapsPanel`'s is.
- `packages/shared/src/rules/firestore.rules.test.ts` — a `backgrounds` block:
  member places/moves/removes, GM places, non-member denied, any signed-in
  client reads.
- `apps/web/src/lib/components/VectorMapView.svelte` — SPEC-038 §2. One sprite
  per background in `layers.background`, keyed by document id, each positioned
  and scaled to its own stored rect (`x*cellSize`, `w*cellSize`, …) and added in
  `order` (ties broken by id, so every client stacks identically); the
  `bgLoadSeq` guard now covers the whole pass. `applyBackgroundColor` handles the
  clear colour on its own. The single `bgSprite`, and the "absent background
  falls back to the starter map" branch, are gone.
- `apps/web/src/lib/components/shell/SessionActivity.svelte` — the
  `session-background-*` block keeps every testid and keeps setting **one**
  background, now through the new methods: Change places one image across the
  whole grid (replacing what was there), a colour clears the image it placed,
  Remove clears both. It reads `subscribeBackgrounds` for its readout.
- `apps/web/src/lib/components/RoomShell.svelte` — a GM-gated, latched, once-per
  room-open `migrateMapBackgrounds` effect, next to `ensureActiveMap`'s adoption
  and for the same reasons.
- Tests: `packages/shared/src/migrations/index.test.ts` (the v22→v23 no-op and
  five `foldLegacyMapBackground` cases), `packages/shared/src/schemas.test.ts`
  (the map doc now rejects an image ref; a `MapBackgroundSchema` block),
  `packages/shared/src/portability/vttcamp.test.ts` (fixtures moved to the v23
  shape; identity round-trip over several placed backgrounds with fractional
  rects; a v22 archive's background folded on import; re-import folds nothing
  twice).
- `README.md` — the layer table's `background` row, the Background bullet in
  II.7 (the storage shape, the colour/image split, where the fold runs), the
  battle-map copy list, and the export note. `PLAN.md`/`PLAN-COMPLETED.md`/
  `INTAKE.md` bookkeeping.

**Visible behavior changes.**

- A map can hold several background images at once, each with its own position
  and size; they paint in `order` over the map's solid background colour, which
  shows through anywhere no image covers. Nothing in this change *places* a
  second one — Session config still sets one — but the renderer and the store
  carry any number, which is what WI-081 needs.
- An existing room's single background is folded, once, into a full-grid
  background document the first time a referee opens the room. It keeps
  rendering; if its image's native pixel size was not exactly the grid, it is
  now stretched to the grid rather than drawn at native size. A pure migration
  cannot load an image to measure it, and the full grid is the rect SPEC-038 §1
  and DEC-062 both specify.
- A map document that carried **no** `background` field at all (a room predating
  WI-073) used to render the bundled starter map as a fallback; it now shows
  bare rock, like every map created since WI-073 retired that default. Nothing
  is folded for it, because there is no ref to fold.
- Session config's Background section looks and behaves as before — same
  testids, same one-background semantics.

**How to verify.**

- `pnpm verify` — lint, typecheck, unit. The migration, schema, and `.vttcamp`
  round-trip tests are here.
- `pnpm verify:all` — adds the Security Rules suite (the new `backgrounds`
  block) and the store contract against `FirebaseStore` on the emulators, plus
  the Playwright e2e (`session-config.spec.ts` Gate 19 still drives the
  Background section end to end).
- In the app: Session config → Background → Change background… → Starter map;
  the image covers the grid. Open a room whose map was created before this
  change as the referee — its background is still there, and
  `maps/{mapId}/backgrounds` now holds one document while `background` on the
  map doc reads `null`.

**Deviations.**

- **`migrateMapBackgrounds` is a store method, and the contract suite grew a
  seeding hook.** Neither is named in DEC-062, which lists add/update/remove/
  reorder. The v22→v23 migration has a document-creating half that `migrateRoom`
  structurally cannot do (it sees the room doc alone), and RULE-001 forbids a
  component reaching past the store to do it. Making it a sixth store method is
  what keeps the fold inside the abstraction; the contract suite then needs a
  way to set up a pre-v23 document, which the interface itself no longer
  expresses — hence the third parameter.
- **Session config's background controls were rewired rather than left alone.**
  Narrowing `GameMap.background` removed the method they called, so they could
  not keep compiling untouched. They were re-pointed at `addBackground` /
  `removeBackground` with every `session-background-*` testid and every visible
  behaviour preserved (RULE-005), rather than being retired early — SPEC-038 §5
  retires them in WI-081, together with their Assets-activity successor and the
  e2e assertions that move with it.
- **IN-053 stays in `INTAKE.md` §1.1, marked *In progress*, rather than moving to
  §1.2.** The intake item spans WI-080 and WI-081; it is not closed until the
  transform UI lands, so moving it to Closed now would misreport it. Its
  disposition column records which half has landed.
- **Nothing else.** The alignment grid, on-canvas selection, drag/resize, and the
  Assets-activity UI are SPEC-038 §§3–5 and stay in WI-081.
