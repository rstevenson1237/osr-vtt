## 2. Three constraints that decide the order

### 2.1 `renderAll` has no inputs, and 42 callers

`renderAll` (3,585–3,765) reads free variables from **every** seam: `hexTiles`,
`hexSymbols`, `hexLines`, `hexCollecting`, `hexGrid` (`HexAuthoring`); `regions`, `walls`,
`doors`, `activeDrag`, `selectedHandles`, `selectedObjects`, `lasso`, `hoverHandle`
(`SelectionGesture`); `selectedBackground` (`BackgroundGesture`); `measureDrag`,
`measureHexDrag`, `livePings` (`CollabPresenter`); `editingLabelId`, `noteDotRoomIds`
(`LabelTooltip`); `dragStart`/`dragCur`/`dragStartRaw`/`dragCurRaw`/`collecting`/`eye`
(stroke state). The 42 call sites distribute as: pointer dispatch 13, `onMount`
subscriptions 11, the effect block 4, hex/label/collab 7, floor and fog commits 3, Select 2,
the Eye timer 1.

So **every extraction is blocked on the same thing**: move a seam's state into a module and
`renderAll` can no longer see it, so the module has to be imported back in — which is a
worse shape than today, because the cycle is now explicit and the render pass depends on
eight modules instead of on itself.

The fix is small and mechanical, and it is the plan's first structural item: give
`renderAll` an **explicit input object** composed from per-seam render slices, and give each
seam a `requestRender()` callback instead of a direct call. Two constraints on it, both
already documented in the file and both easy to break:

- `renderAll` **must not write reactive state** (the `strokeMeasure` doc comment, 499–586):
  several `$effect`s call it, and assigning a fresh object there re-invalidates them every
  frame — `effect_update_depth_exceeded`. The input object must therefore be built by the
  caller or by a plain function, never by a `$derived` that `renderAll` itself writes back
  into.
- The `strokeMeasureText_` / `snapCellText_` / `snapBandText_` mirrors are assigned **only**
  on the pointer path (`syncMeasureReadout`), never from `renderAll`, for the same reason.

This item is also what makes WI-193 (per-layer dirty tracking, SPEC-057 §4.2) a small
change rather than a rewrite: a single `requestRender()` funnel is the place a dirty-layer
mask goes. If WI-192 comes in over budget and WI-193 is built, the two should be decided
together at WI-193's gate.

### 2.2 Every `data-testid` is in the markup — so the Playwright suite is a free oracle

All 39 live between lines 3,821 and 3,996. No extraction proposed here moves one, so
**RULE-005 is satisfied by construction** and every item below can be verified by running
the existing e2e suite unchanged. That is the whole safety argument for a refactor with no
unit tests behind it, and it is why §4 orders the pure-helper item first: it is the one
that starts building the unit tests the later items will want.

### 2.3 Five work items are already scheduled against this file

WI-178 – WI-181 (undo, then multi-token select) and WI-192 (the render benchmark) all land
in `VectorMapView.svelte` before anything raised here could. `PLAN.md` is explicit that a
re-ordering is a new gate, not a change made inside those items, so this plan **schedules
itself behind them** and takes two consequences:

- **Undo is not an extraction item.** WI-178 already lifts the stack out of this file
  (SPEC-056 §2.1). Those 21 lines are spoken for.
- **`SelectionGesture` is an extraction item, but it goes last.** WI-181 (SPEC-056 §3)
  rewrites the Select gesture to add multi-token selection, Shift-click, a tokens-win lasso
  and set drag. Extracting those 313 lines first would be rewriting the same code twice and
  would collide head-on with the larger of the two changes. The right move is the reverse:
  WI-181 lands, and *then* the settled gesture is extracted — which is why it is raised as
  IN-205 at the bottom of §4 rather than near the top by size.

## 3. Three extraction shapes, and which code takes which

The repo already has all three and they should not be mixed.

1. **Pure module (`map/*.ts` + `*.test.ts`).** A function of its arguments, no Pixi, no
   store, no reactivity — the shape of `background-transform.ts`, `battle-map.ts`,
   `tool-groups.ts`. Unit-testable the day it lands. `displayState`, `displayOverlayState`,
   `annotationsWithLiveStroke`, `objectHighlightBBox`, `latticeThreshold`,
   `resolvePingsForRender`, `hexLinePreview`, `backgroundRect`/`liveBackgroundRect`/
   `nativeAspect`, `tokenRadiusPx`, `revealedAt`, `isAway` are all already this shape — thirteen
   functions in all — and are simply sitting in the wrong file.
2. **Reactive controller (`map/*.svelte.ts`, a class with `$state` fields).** The
   `MapToolController` / `DialogService` / `ShellState` shape. For a seam that owns private
   mutable state plus a slice of the Pixi scene: constructed in `onMount` with `{ engine,
   store, roomId, mapId, requestRender }`, torn down in `onDestroy`, exposing a render
   slice and a `handlePointerDown/Move/Up` that returns whether it consumed the event —
   which is exactly the protocol `handleCollabPointerDown`/`handleHexPointerDown`/
   `handleNoteDotPointerDown` already use (2,467–2,570). The seams are not being invented;
   the interface is already there, undeclared.
3. **Stays in the component.** Props and context, the subscription block, the `mapCtrl`
   mirror effects, `renderAll`'s composition, the readout markup and the CSS.

## 4. The plan

Ten items, ordered. Nine are new intake items (`INTAKE.md` IN-197 – IN-205); the tenth,
IN-113, was already logged. Each keeps its own work item, one controller per work item, as
IN-172 required. Classifications are recommendations for triage, made conservatively per
`CLAUDE.md` — "touches but does not redefine" is not a Deceptive trigger, but a 766-line
move that changes who owns a Pixi sprite map plausibly sits on both sides.

"Lines out" is **net**, in this order: IN-198 lifts the pure functions out first, so the
controller items below it are correspondingly smaller than their §1.1 seam totals.

Of IN-198's 190 lines, 74 belong to no seam (`displayState`, `displayOverlayState`,
`latticeThreshold`, `PICK_PX`) and 116 are lifted out of items 4–8 ahead of them
(`resolvePingsForRender`, `annotationsWithLiveStroke`, `objectHighlightBBox`,
`hexLinePreview`, `backgroundRect`, `liveBackgroundRect`, `nativeAspect`, `tokenRadiusPx`,
`revealedAt`, `isAway`). That is the one place two items touch the same lines on purpose:
IN-198 only ever *removes* code the later item was going to move anyway, so it shrinks
those diffs instead of competing with them.

**Why this order and not seam-size order.**

- **IN-198 first** because it is the only item with no prerequisite, it is pure gain at
  zero risk, and it produces the file's *first* unit tests — which every item after it
  borrows credibility from. `displayState` and `displayOverlayState` in particular are 64
  lines of drag-preview substitution that has never had a test and is exercised on every
  pointer-move of a Select drag.
- **IN-197 second** because §2.1: nothing else can move cleanly until it has.
- **IN-203, IN-202, IN-200 next**, smallest first, as the shakedown run for the controller
  protocol. `LabelTooltipController` is the gentlest: it owns four `$state`s, two of which
  already back markup, and its pointer hook (`handleNoteDotPointerDown`) is already written
  in the target shape. If the protocol is wrong, it is wrong on 166 lines rather than 766.
- **IN-200 carries a warning.** IN-067, IN-068 and IN-069 — three untriaged Deceptive
  candidates from the WI-083 investigation — all sit in exactly these lines. Extracting
  first means writing them twice. Triage should schedule them with the extraction or ahead
  of it.
- **IN-201 after WI-188.** Hex fog (SPEC-056 §9) adds `HexTile.revealed` and a Reveal/Hide
  hex tool to the same lines, with a schema bump behind it. Same argument as IN-200.
  RULE-006 also binds here: the axial-space boundary is precisely what this controller
  would own, and a mistake in it is a coordinate-space mistake, not a layout one.
- **IN-113 before IN-199.** These are two different changes to the same 783 lines and the
  order matters. IN-113 changes what the `tokens` layer *contains* — five parallel maps
  become one container per token — which is a Pixi-layer-composition change and Deceptive on
  its own terms. IN-199 changes only *where the code lives*. Doing IN-199 first means
  extracting five sprite maps and a drag handler that reads them, then immediately
  rewriting all of it; doing IN-113 first means IN-199 extracts a shape that is already
  final. IN-113's own record already names the three things that depend on the present
  shape (the sprite carries the pointer handlers, the disc's z-order comes from insertion
  order, and `export-layers.ts` walks these objects) and none of them gets easier by
  extracting first.
- **IN-204 near-last** because it is the residual. `wireStagePointerEvents` is a 145-line
  if-ladder of `if (handleXPointerDown(...)) return;`, and every item above removes one of
  its branches into a controller that owns it. Extracted first, the router would have to
  import every seam it dispatches to; extracted last, it dispatches over a list of
  controllers the component already holds, and the ladder becomes a loop. The 319 lines of
  `onPointerDown`/`Move`/`Up` shrink the same way.
- **IN-205 last, and hard-blocked on WI-181** — see §2.3. WI-181 rewrites this gesture to
  add multi-token selection, Shift-click, a tokens-win lasso and set drag. Extracting first
  would be rewriting the same 313 lines twice, and the extraction would collide head-on
  with the larger of the two changes. Landing WI-181 first means IN-205 extracts a settled
  gesture.

## 5. What is deliberately not extracted

- **`renderAll` itself.** It is the composition root, not a seam. It shrinks by delegation
  (IN-197) and by whatever WI-193 decides, never by being moved.
- **The 18-effect `mapCtrl` mirror block** (174 lines). Not a seam: it is 18 independent
  one-way mirrors from this component's state out to the shared controller. It shrinks on
  its own as each controller takes its own mirrors with it. Extracting it as a unit would
  produce a module whose only job is to know about everything.
- **The readout markup** (176 lines). WI-167 (SPEC-055 §3) already puts it behind
  `VITE_E2E_READOUTS`. Two items in the same lines is the mistake §4 avoids elsewhere.
- **The subscription block** (157 lines). The 14 listeners are the component's lifetime,
  and IN-173/WI-184's `collectionOf<T>` is the item that shortens them — on the
  `FirebaseStore` side, not here.
- **Tool state, stroke state, the floor/fog/door commits** (≈ 430 lines). This is what the
  vector editor *is*. Extracted, the component would be a shell around a module that still
  needed the engine, the store, the lattice and the tool — i.e. the same file under a
  different name.

## 6. The honest end state

Ten items, ≈ 2,360 lines moved, ≈ 1,900 left after glue. To go further than that the
question stops being "which controller" and becomes **"is this one component?"** — and it
has a defensible answer either way, which is why it is raised as a question here rather
than scheduled as an item. The candidates, if it is ever asked: the 275 lines of readout
markup and CSS as a `MapReadouts.svelte` child (blocked behind WI-167), and the split of
"the Pixi host" from "the vector editor" as two components over one engine. Both are larger
than anything in §4 and neither is required by INT-AR-01, which asked for an extraction
plan, not a component split.

The number worth holding the plan to is not the line count, though. It is this: **0 unit
tests reach this file today.** Item 1 alone takes thirteen pure functions into a module
with a test file; items 3–10 each land a controller that can be constructed with a fake
engine and driven without a browser. If the ten items land and the file is 1,900 lines with
a hundred unit tests under it, INT-AR-01 is answered. If it lands at 1,900 lines with zero,
the lines moved but the problem did not.
