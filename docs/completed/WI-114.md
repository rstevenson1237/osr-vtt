# WI-114 — Letter assignment reads the field instead of parsing the ref

**Spec:** SPEC-048 §3 · **From:** IN-109 · **Model:** `sonnet` · **Effort:** S–M
**Gate cleared:** user, 2026-09-08 · **Completed:** 2026-09-09

Phase 2 of 4 of the token-letter programme. `usedGroupLetters` stops parsing
`/^gen:disc:([A-Z]+):/` out of `Token.imageRef` and reads `Token.letter` instead — the
field WI-113 landed and backfilled. WI-115 draws the letter over art next, and only then
does WI-116 clear the refs and delete the `gen:` branch.

## Changes made

**Assignment mechanism (`apps/web/src/lib/tokens/labels.ts`)**

- `usedGroupLetters` reads `token.letter` in place of `CREATURE_GEN_RE.exec(token.imageRef)`.
  The three exclusions the old regex gave for free are now an explicit predicate: a
  seat-owned token, a token with no `letter`, and a `letter` that fails a new
  `PLAIN_UPPERCASE_RUN_RE` (`/^[A-Z]+$/`) check — covering hand-typed labels and the
  migrated pre-v28 `a1`/`a2` refs.
- `defaultCreatureRefs` is renamed **`defaultCreatureBatch`**, returning
  `{ letters, color }` instead of building `gen:disc:` refs — a letter is stored data now,
  not a ref fragment. `nextCreatureLetters` and `creatureBatchColor` are unchanged.

**The two "Add creature" call sites (`EncounterBoard.svelte`, `VectorMapView.svelte`)**

Both still need a `gen:disc:` ref for `imageRef` — retiring that ref is §5's job, not
this one's — so both now: call `defaultCreatureBatch` for the letters/colour, build each
ref with `buildGenTokenRef(letter, color)` (unchanged output), and additionally write the
assigned `letter` and the batch colour onto each created token.

**Tests (`apps/web/src/lib/tokens/labels.test.ts`)**

`creatureToken` now takes a `letter` and sets both it and a matching `gen:disc:` ref, so
`nextCreatureLetters`'s suite reads as data rather than a ref parse; a new case pins the
"no letter" exclusion and another pins the "not a plain uppercase run" exclusion
(`a1`, an emoji) as its own case, replacing the old three-in-one ref test. The
`creatureDisplayName`/`creatureLabel` fallback tests build a raw-ref, letterless token
directly, since that fallback is about `imageRef`, not `letter`. The renamed
`defaultCreatureBatch` test asserts the returned `{ letters, color }` shape.

**Docs** — `README.md`'s v30 paragraph under "Tokens, assets & theming" is corrected (§3
has landed, so assignment no longer parses the ref); "Creature names and symbols" gains a
paragraph describing the new predicate, the rename, and the two call sites' additional
writes.

## Visible behavior changes

None. A generated creature still shows the same `gen:disc:` disc it did before — the ref
is still built and still written to `imageRef` — and letter assignment still hands out
the lowest unused uppercase letter per group, restarting at A. What changed is where the
already-visible letter is read from.

## How to verify

- `pnpm verify` — lint, typecheck and unit, green.
- `pnpm verify:all` — the above plus rules, store contract and the full e2e suite against
  the emulator, green (see Deviations for the one failure found and fixed along the way).
- Targeted: `pnpm --filter @osr-vtt/web exec vitest run src/lib/tokens/labels.test.ts`.
- By hand: as GM, use a group's "+" to add a second batch of the same creature name to an
  existing group in one sitting (no reload in between) — the new batch continues the
  letter sequence rather than restarting at A, which is the case a stale ref-parse or an
  unwritten `letter` field would get wrong.

## Deviations

1. **Both "Add creature" call sites were changed to also write `letter`/`color`, not just
   read them.** SPEC-048 §3 describes the read side only; §5 is where the request expects
   writers to change. But the moment `usedGroupLetters` stops reading the ref, a batch
   created without a `letter` field would be invisible to the very next batch's
   assignment until the once-per-room-open migration (`migrateTokenLetters`) catches up
   on the next room-open — a real regression a referee could hit by adding two batches to
   one group in the same sitting. Writing `letter` (and the batch colour) alongside the
   still-written ref keeps §3's own promise — "behaviour unchanged, mechanism changed" —
   true within a single room-open, not just across one. This is squarely inside what §3
   needs to be correct, not a pull-forward of §5's ref retirement: the ref is still built
   and still the thing that resolves to art.
2. **The batch colour is converted through `genColorHex` before it is written.**
   `Token.color` is validated hex (`HEX_COLOR_RE`); `creatureBatchColor`/`genColorToken`
   produce an `hsl(...)` paint value, the same one baked into the ref. Writing it
   unconverted failed schema validation on every generated batch and was caught by
   `encounter-board-v2.spec.ts`'s named-batch e2e test (zero cards created, `pnpm
   verify:all` red). Both call sites now run it through `genColorHex` — the same
   conversion `backfillLetterFromRef` uses — and omit the field on the rare `null` (an
   unconvertible override, which the migration also just leaves absent).
