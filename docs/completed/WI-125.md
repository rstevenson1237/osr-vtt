#### WI-125 — An `.svg` token renders instead of a black square

**Changes made.**

- `apps/web/src/lib/components/VectorMapView.svelte` — `loadTokenTexture` now checks the
  loaded `HTMLImageElement`'s `naturalWidth`/`naturalHeight` after `loadImageElement`
  resolves. A zero-size image (an SVG with no usable intrinsic size — no `width`/`height`
  and, per the empirical check below, none the browser's default-replaced-element
  fallback resolves either) is thrown into the same `catch` that already handles a
  CORS-blocked/failed load: `brokenImageIds` gets the token, the broken-image texture and
  badge are used, and a warning is logged. Previously this image reached
  `PIXI.Texture.from(img)` directly, which does not reject a zero-size source — it uploads
  an untextured quad to WebGL, which renders as a black square instead of either the art
  or the existing broken-image indicator. The check is local to `loadTokenTexture`
  (not `loadImageElement` itself, which `BackgroundsPanel.svelte` also uses for a
  different, unscoped surface — RULE-015).
- `apps/web/tests/e2e/token-image-load.spec.ts` — added a third case reproducing the bug:
  a saved URL asset pointing at an SVG served with `width="0" height="0"`, added as a
  token, asserting `broken-token-count` becomes `1` instead of the token silently
  rendering as a black square.
- `PLAN.md` — status notes for this work item's execution (to be removed per step 7 below).

**Visible behavior changes.** A token whose image resolves to a zero-size SVG (pasted by
URL, or a bundled asset lacking `width`/`height`) now shows the existing broken-image
placeholder and badge, and increments the broken-token count, instead of rendering as a
solid black square with no indication anything is wrong. A normal SVG with usable
intrinsic dimensions (including one with no `width`/`height`/`viewBox` at all, which
Chromium's own default-replaced-element sizing gives 300×150 rather than zero) is
unaffected and still renders as before.

**How to verify.**

- `pnpm verify` — lint + typecheck + unit, green.
- `pnpm --filter @osr-vtt/web exec playwright test token-image-load` (against the Firebase
  emulators) — all 3 cases in `token-image-load.spec.ts` pass, including the new
  IN-119/WI-125 case.
- Manually: Assets → By URL → save a URL to an SVG served with `width="0" height="0"`
  (or any SVG whose decoded size is zero) → Add creature → place it. The token shows the
  broken-image badge and the "broken token" count increments, rather than a black square.

**Deviations.** The intake analysis (`INTAKE.md` IN-119) described the reproduction as
"an SVG with no intrinsic `width`/`height`" giving `naturalWidth` 0. Checked empirically
against this repo's own Chromium build (`/opt/pw-browsers/chromium`): an SVG with no
`width`/`height`/`viewBox` at all does **not** yield a zero-size image here — it falls
back to the CSS default replaced-element size, 300×150 — so it isn't a working
reproduction in this engine. An SVG with explicit `width="0" height="0"` does yield a
verified zero-size `HTMLImageElement`, so the e2e reproduction and the fix's guard
(`naturalWidth === 0 || naturalHeight === 0`) are built around that shape instead, which
is the same failure mode the intake's root-cause analysis describes (a zero-size image
uploaded to WebGL as an untextured quad) and covers it without narrowing the fix. No
other change to scope.
