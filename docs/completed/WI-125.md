#### WI-125 — An `.svg` token renders instead of a black square

**Changes made.**

- `apps/web/src/lib/components/VectorMapView.svelte` — `loadTokenTexture`:
  - Checks the loaded `HTMLImageElement`'s `naturalWidth`/`naturalHeight` after
    `loadImageElement` resolves. A genuinely zero-size image (e.g. an SVG with explicit
    `width="0" height="0"`, which has no content `drawImage` could recover) is thrown into
    the same `catch` that already handles a CORS-blocked/failed load: `brokenImageIds`
    gets the token, the broken-image texture and badge are used, and a warning is logged.
  - **Follow-up, same PR:** the loaded image (once past the zero-size check) is no longer
    handed to `PIXI.Texture.from` directly. It is first rasterized onto a fixed-size
    (256×256) offscreen `<canvas>` via `drawImage` (new `rasterizeTokenImage` /
    `TOKEN_ART_RASTER_PX`), and the texture is built from that canvas instead. This covers
    a second, more common failure the `naturalWidth === 0` check does not catch: an SVG
    with a `viewBox` and real content but no `width`/`height` attributes reports a
    *nonzero* `naturalWidth` in Chromium (a CSS default-object-size fallback), yet its own
    WebGL `texImage2D` can still reject it outright (`INVALID_VALUE: texImage2D: bad image
    data`, logged only to the console, never surfaced as a JS exception our
    `try`/`catch` can see) — leaving the sprite an untextured black square with no warning
    at all. A canvas is always a well-defined WebGL texture source, so rasterizing first
    sidesteps the disagreement between the DOM's reported size and what the GPU will
    accept.
- `apps/web/tests/e2e/token-image-load.spec.ts` — two new cases:
  - A saved URL asset pointing at an SVG served with `width="0" height="0"`, added as a
    token, asserting `broken-token-count` becomes `1` (the genuinely-empty case).
  - A saved URL asset pointing at a `viewBox`-only SVG with real content and no
    `width`/`height` attributes, asserting `broken-token-count` stays `0` and no
    `token image failed to load` warning is logged (the real-world, nonzero-`naturalWidth`
    failure this follow-up fixes).

**Visible behavior changes.** A token whose image resolves to a genuinely zero-size SVG
now shows the existing broken-image placeholder and badge instead of a solid black
square. A token whose image is an SVG with real content but no `width`/`height`
attributes (only a `viewBox`, optionally sized via inline `style`) now **renders its
actual artwork** instead of a black square — this is the more common real-world shape
(confirmed against a live user-reported asset) and previously failed silently with no
error visible anywhere in the app, only a browser-console WebGL warning. Any image that
already rendered correctly (PNG, JPEG, or an SVG with `width`/`height` attributes) is
unaffected.

**How to verify.**

- `pnpm verify` — lint + typecheck + unit, green.
- `pnpm --filter @osr-vtt/web exec playwright test token-image-load` (against the Firebase
  emulators) — all 4 cases pass.
- Manually: Assets → By URL → save a URL to a `viewBox`-only SVG with no `width`/`height`
  attributes → Add creature → place it. The token now shows its actual art. Repeat with
  an SVG served `width="0" height="0"` and confirm the broken-image badge appears instead.

**Deviations.**

- The intake analysis (`INTAKE.md` IN-119) described the reproduction as "an SVG with no
  intrinsic `width`/`height`" giving `naturalWidth` 0. Checked empirically against this
  repo's own Chromium build: a bare `<svg>` with no `width`/`height`/`viewBox` at all does
  **not** yield a zero-size image — it falls back to the CSS default replaced-element
  size, 300×150 — so it isn't a working reproduction in this engine. An SVG with explicit
  `width="0" height="0"` does yield a verified zero-size `HTMLImageElement`, so the
  zero-size guard and its e2e case are built around that shape.
- **Follow-up, same PR, at the user's request after reviewing the first pass.** The
  shipped `naturalWidth === 0` guard turned out not to cover the user's own real-world
  case: a live GitHub-Pages-hosted SVG (`viewBox="0 0 1024 1024"`, sized via inline
  `style`, no `width`/`height` attributes) still rendered black on the map despite
  reporting a nonzero `naturalWidth`, confirmed via the browser console
  (`WebGL: INVALID_VALUE: texImage2D: bad image data`) and by direct testing in this
  session (identical `PIXI.Texture.from(img)` behavior reproduced against the exact
  reported asset; `ctx.drawImage(img, 0, 0, W, H)` onto a canvas was verified to recover
  real pixel content from the same file). CORS was checked and ruled out — the asset's
  response carries `Access-Control-Allow-Origin: *`. The canvas-rasterization change
  above was added to the same PR (not split into a separate work item) since it is the
  same function, the same bug report (IN-119), and the same open, unmerged PR.
- No other change to scope. `ALLOWED_UPLOAD_CONTENT_TYPES` remains untouched.
