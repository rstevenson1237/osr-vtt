# WI-187 — UVTT import → a new map of imported walls and doors

SPEC-056 §8, DEC-112. Single unit (Deceptive). IN-186.

## Changes made

- `packages/shared/src/portability/uvtt.ts` (new) — `parseUvtt(input)`, a pure parser
  from a Universal VTT file's text (or parsed JSON) to `{ grid: {w, h}, walls, doors }`.
  Grid = `resolution.map_size` rounded up to whole cells (min 1×1). Walls = every step of
  every `line_of_sight` and `objects_line_of_sight` polyline, `source: 'imported'`,
  blocking sight and movement; zero-length steps dropped. Doors = each `portals` entry,
  `bounds[0]`/`bounds[1]` → `a`/`b`, `type: 'single'`, `closed: false` → `open`, else
  `closed`. Every point is `point − resolution.map_origin` (absent origin = `0,0`),
  floats; `pixels_per_grid`, `image`, `lights` and `environment` are never read
  (RULE-006). Any structural failure throws `UvttParseError` with a readable message.
- `packages/shared/src/portability/uvtt.test.ts` (new) — 14 cases: the bundled
  `sample-dungeon.dd2vtt` (10×10 grid, one wall `5,0→5,7`, one closed door `5,7→5,8`,
  nothing scaled by its 70 px/grid); origin subtraction with floats, fractional size
  rounding, polyline splitting, zero-length drop, `objects_line_of_sight`, an open
  portal; absent collections; eight rejection cases.
- `packages/shared/src/index.ts` — re-exports `portability/uvtt.js`.
- `apps/web/src/lib/map/import-uvtt.ts` (new) — `importUvttMap(store, roomId, name,
  text)`: parses first (a parse failure throws before any write), then `createMap`
  (square), `setMapGridDimensions` (file size, default cell size), `setWalls` in
  batches of `UVTT_WALL_BATCH` = 400, one `setDoor` per portal. Existing store methods
  only; the active map is not changed. `uvttMapName(fileName)` names the map from the
  file.
- `apps/web/src/lib/map/import-uvtt.test.ts` (new) — against `MemoryStore`: the sample
  lands as a new square map with the right grid, wall and door, active map unchanged; a
  2×400+3-wall file lands in three `setWalls` calls with unique ids; a bad file throws
  and adds no map; `uvttMapName`.
- `apps/web/src/lib/components/shell/MapsPanel.svelte` — an **Import UVTT** file control
  (`maps-import-uvtt`, new testid) beside "+ New map"/"+ New hex crawl"; on success the new
  map opens in the inline rename; on failure `maps-import-uvtt-error` shows the file name
  and reason. Head row now wraps with a gap.
- `apps/web/tests/e2e/uvtt-import.spec.ts` (new) — a broken file shows the error and adds
  no row; the sample adds a row opened for rename as `sample-dungeon`.
- `README.md` — "Walls, doors, LoS": the `imported` source names its writer; "Map
  management": the Import UVTT paragraph (mapping, ignored parts, write sequence).
- `PLAN.md`, `PLAN-COMPLETED.md`, `INTAKE.md` — WI-187 closed, IN-186 moved to §1.2.

## Visible behavior changes

- The Maps manager (Assets) has an **Import UVTT** button. Picking a `.dd2vtt`/`.uvtt`
  file adds a new square-grid map sized from the file, holding its walls and doors, and
  opens its name for editing. The file's image and lights are not imported. The room's
  active map does not change — switch to the new map with "Switch to this map".
- A file that is not a Universal VTT map shows "Couldn't import <file>: <reason>" under
  the buttons and adds nothing.

## Deviations

- **Not "one batch".** SPEC-056 §8 says the writes go "through existing store methods in
  one batch". The existing methods cannot do that: `setWalls` and `setDoor` are separate
  collections with no shared batch method, and a single `setWalls` is one Firestore
  batch, capped at 500 writes, which an ordinary exported dungeon exceeds. Adding a
  multi-collection batch method would be a new store method (RULE-001) the gate did not
  approve. So the import is a sequence — `createMap`, `setMapGridDimensions`, `setWalls`
  in ≤400-segment batches, `setDoor` per portal. The part of "one batch" the spec's last
  sentence depends on is kept: parsing completes before the first write, so a file that
  fails to parse writes nothing. A network failure mid-sequence can leave a partial
  imported map, which the referee deletes from the same panel. If atomicity is wanted,
  that is a new intake item for a store method.
- **The file picker also accepts `.df2vtt` and `.json`** — the same format under the
  other exporters' extensions; the parser decides, not the extension.
- **The new map is not made active; it opens in the inline rename**, matching "+ New map"
  — SPEC-056 §8 does not say, and DEC-112's "nothing existing is overwritten" reads most
  naturally as not switching every player's view.
- No RULE-015 unblock or Deviations-budget fixes were used.
