# WI-168 — One `snapFor` resolver (identical outputs)

SPEC-055 §4. Part of **Batch 3** (WI-166, WI-167, WI-168, WI-169) — one pull request,
one combined summary.

## Changes made

- `packages/shared/src/map/snap-for.ts` (new) — `snapFor(kind, mode, point, options?)`
  dispatches to `snapTokenPosition` (`kind: 'token'`, `SnapMode`, world-pixel space) or
  `snapPoint` (`kind: 'tool'`, `VectorSnapMode`, lattice-unit space). It calls the
  existing functions rather than re-implementing their math, so outputs cannot drift;
  `options` carries `snapTokenPosition`'s `cellSize`/`size`/`hexSize` for `'token'` or
  `snapPoint`'s `attract` for `'tool'`.
- `packages/shared/src/map/snap-for.test.ts` (new) — asserts `snapFor` matches
  `snapTokenPosition`/`snapPoint` exactly for every mode, with and without a hex map /
  vertex attraction (20 cases).
- `packages/shared/src/index.ts` — exports `./map/snap-for.js`.
- `apps/web/src/lib/components/VectorMapView.svelte` — the three callers
  (`snapTokenPosition` ×2 for the drag-drop and on-map-drag paths, `vectorMap.snapPoint`
  ×1 for `toLatticeSnapped`) now call `snapFor('token', …)` / `snapFor('tool', …)`.
  `snapCell`, `snapCellCenter`, `snapAngle`, `snapScalar`, `snapSpan` (different snap
  semantics — cell-floor, angle, span — not "resolve a raw point") are unchanged.
- `README.md` — "Tools" and "Map ⇄ character sheet" note the `snapFor` call shape.

## Visible behavior changes

None. `snapFor` dispatches to the same functions with the same arguments; every existing
snap behaviour (cell/half/hex/free token placement, tool vertex attraction) is
unchanged.

## How to verify

- `pnpm --filter @osr-vtt/shared exec vitest run src/map/snap-for.test.ts` — 20/20 pass.
- `pnpm test:unit` — green.
- Manually: drag a token on a square map (cell/half/free via Alt/Shift), drag one onto a
  hex map, drag a character portrait from the quick sheet onto the map, and free-snap a
  Wall/Door near an existing vertex — all snap exactly as before.
