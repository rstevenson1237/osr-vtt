# WI-038 — Hex crawl: axial coordinates, schema, migration

**Spec:** SPEC-030 §1 · **From:** IN-011 · **Agent:** `claude-code` · **Model:** `opus` ·
**Effort:** high · **Closed:** 2026-08-13

The first implementation item of the Hex Crawl series, and the one WI-037's rule
amendment was the gate on: it builds SPEC-030 §1's coordinate space and the schema that
declares a map to be in it. Nothing renders a hex map yet — that is WI-039.

## Changes made

- **`packages/shared/src/map/hex/axial.ts`** (new) — the axial hex space, pure and
  store-free, the hex-grid sibling of `map/vector/`. `Axial { q, r }` (deliberately not
  the lattice's `Point { x, y }`, so mixing the two spaces is a type error rather than a
  silently wrong map) and `HexPixel { x, y }` for the far side of the render boundary;
  `HEX_ORIGIN`, `AXIAL_DIRECTIONS` (six, clockwise from north), `axialAdd`/`Subtract`/
  `Equals`, `axialNeighbor` (index wraps) / `axialNeighbors`, `axialDistance` (cube
  distance in axial terms — hex steps, not lattice steps), `axialKey`/`parseAxialKey`,
  `axialRound` (cube rounding), and the render-boundary conversions `hexMetrics`,
  `axialToPixel`, `pixelToAxial`, `hexCorners`. **Orientation is fixed flat-top** — a
  property of the render boundary, so a constant here and stored nowhere.
- **`packages/shared/src/map/hex/index.ts`** (new) + **`src/index.ts`** — re-exported
  under its own **`hexMap`** namespace beside `vectorMap`, so an import site says which
  coordinate space it is asking for (RULE-006).
- **`packages/shared/src/map/hex/axial.test.ts`** (new, 26 tests) — origin at the map
  centre and symmetric about it; a type-level assertion that `Axial` is not a `Point`;
  neighbours (six, distinct, mutual, one step apart in axial *and* in pixels); distance
  checked against a greedy walk of the grid; key round-trip incl. negatives, id legality,
  no `-0`, and rejection of non-integer pairs; the multiplier scaling linearly and never
  reaching a coordinate; pixel round-trip; picking by point-inside-hex (corner insets and
  just-past-an-edge); cube rounding vs naive per-component rounding, plus a brute-force
  nearest-centre sweep of the plane; corners at exactly `size`, flat-topped, and shared
  pairwise with each neighbour.
- **`packages/shared/src/types.ts`** — `CURRENT_SCHEMA_VERSION` 23 → **24**. New
  `GameMap.hex?: HexGridConfig` (`{ size }` — the hex circumradius), whose **presence is
  the map's grid kind**; new `MapGridKind` and the `mapGridKind(map)` / `isHexMap(map)`
  accessors (derived, never stored beside `hex`, because two fields could disagree and
  one cannot); `DEFAULT_HEX_GRID_CONFIG = { size: 48 }`; `createDefaultGameMap` takes a
  third `gridKind` argument defaulting to `'square'` and seeds `hex` only for `'hex'`.
- **`packages/shared/src/schemas.ts`** — `HexGridConfigSchema` (`size` positive) and
  `GameMapSchema.hex` optional, so the field survives the Firestore converter.
- **`packages/shared/src/migrations/index.ts`** + **`index.test.ts`** — the **v23 → v24**
  step: a no-op on the room doc, like v21→v22 and v22→v23, because the field lives on a
  `maps/{mapId}` document `migrateRoom` never sees. Unlike v22→v23 there is no document
  half either — absence already means "a square-grid map", and backfilling `hex` would
  re-declare an existing dungeon's coordinate space and orphan every polygon on it. Two
  tests: the walk is an identity plus the stamp, and it invents no `hex` anywhere.
- **`packages/shared/src/store/campaign-store.ts`**, **`memory-store.ts`**,
  **`firebase-store.ts`** — `createMap(roomId, { name, gridKind? })`. The kind defaults
  to `'square'`, so every existing caller is unchanged, and it is fixed at creation:
  there is no setter, because switching it would re-declare what every stored coordinate
  on the map means.
- **`packages/shared/src/store/campaign-store.contract.ts`** — the RULE-001 contract test
  for that signature, green against both `MemoryStore` and `FirebaseStore`: the default
  stays square, a hex map persists `DEFAULT_HEX_GRID_CONFIG` through the converter,
  `mapGridKind` reads both back correctly, and the square `grid` rides along unchanged.
- **`packages/shared/src/portability/vttcamp.test.ts`** — RULE-007's `.vttcamp`
  round-trip: a hex map and a square map in one archive both come home exactly as they
  went in, with `hex` neither dropped from the one nor leaked onto the other. The
  existing ordinary-map round-trip's version pin moves 23 → 24.
- **`README.md`** — new "Hex-grid maps — the second coordinate space" subsection under
  Map system → Data model (the field, the accessors, why `grid.w`/`h`/`cellSize` are not
  its geometry, the `hexMap` namespace, fixed flat-top orientation, `axialKey` as both
  document id and §1's pill label, that square-lattice consumers must not be reached from
  a hex map, and that the kind is fixed at creation). The "one coordinate space" preamble
  now points at it.
- **`docs/spec/SPEC-030.md`** — status "specified, not built" → "partly built", and a
  §1 note recording what landed and what still needs a renderer.
- **`PLAN.md`**, **`PLAN-COMPLETED.md`**, **`INTAKE.md`** — ledger moves (WI-038 out of
  §2, into PLAN-COMPLETED §3; IN-011's status cell updated — the intake row stays open,
  WI-039 – WI-041 are still ahead of it).

## Visible behavior changes

**None.** No UI reaches any of this: a hex map has no renderer, no terrain, no contents
and no quick sheet yet, and the Maps manager has no way to ask for one —
`createMap({ gridKind: 'hex' })` is the only producer and nothing in `apps/web` calls it.
Every existing map, and every map a referee creates today, is square-grid and behaves
exactly as before. New rooms are stamped `schemaVersion: 24`.

## Deviations

- **`GameMap.hex` carries the grid kind; there is no `gridKind` field.** The approved
  item names "schema" without fixing the field. A stored `gridKind` next to a stored
  `hex` gives two sources of truth that can disagree, so presence-is-the-kind follows the
  `battle?` precedent (SPEC-029 §3) and the kind is *derived* by `mapGridKind`. Nothing
  in the spec or in RULE-006 distinguishes the two spellings.
- **`createMap` gained an optional `gridKind`** — a store-contract change (RULE-001)
  beyond a literal reading of "schema". Without a producer the field could not be shown
  to persist through the Firestore converter, which is exactly what the schema half owes;
  it ships with contract coverage against both stores. The UI producer belongs to WI-039,
  which is the item that can show the result.
- **`axialToPixel`/`pixelToAxial`/`hexCorners`/`hexMetrics` are included**, though
  rendering is WI-039's. They are the render-*boundary* conversions RULE-006 names as
  part of defining a coordinate space, and they are what the round-trip and picking tests
  assert the space against; WI-039 consumes them rather than defining them.
- **RULE-006's "a square-lattice consumer must not be reached from a hex map" is
  documented, not enforced at runtime.** There is no reachable path to enforce yet — no
  UI creates a hex map, and the store↔geometry bridge (`subscribeVectorScene`) takes a
  `mapId`, not the map document, so guarding there would mean an extra read for a case
  that cannot occur. The type split (`Axial` vs `Point`) carries it statically for now;
  the consumers' own work items (WI-039 – WI-041) are where the branch belongs.
