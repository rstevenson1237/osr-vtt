# WI-094 — Die proportion: retune `SCALE` and the d10 aspect to the stated ordering

**Spec:** SPEC-045 §2 · **From:** IN-080 · **Model:** `sonnet` · **Effort:** S ·
**Closed:** 2026-09-02

`SCALE` multiplies each shape's own vertex table, and only five of the six shapes are
normalized to circumradius 1 — the cube (`d6`) is built at radius √3, uncorrected. Reading
the old table (`d4: 0.56, d6: 0.45, d8: 0.52, d10: 0.55, d12: 0.56, d20: 0.56`) as if every
entry were a shared circumradius made the stated defect ("the d4 is not the largest die")
look like the whole story; measuring the shapes' *actual* circumradius (`scale × unit-shape
radius`) shows the cube was the real outlier — at 0.45 × √3 ≈ 0.78 it was already the
largest object in the set, well past `d20`. Both are the same root cause (`SCALE` treated
as circumradius when the underlying shape isn't unit-normalized) and both are fixed by the
same retune.

## Changes made

- **`apps/web/src/lib/dice/geometry.ts`** — `SCALE` retuned to
  `{ d4: 0.44, d6: 0.271, d8: 0.5, d10: 0.533, d12: 0.545, d20: 0.58 }`, chosen so real
  circumradius (`scale × unit-shape radius`) follows SPEC-045 §2's ordering
  (`d4 ≤ d6 < d8 < d10 ≈ d12 < d20`): ~0.44, ~0.47, 0.50, ~0.535, 0.545, 0.58. The table's
  comment is rewritten to state the circumradius relationship explicitly, including the
  cube's √3 and the d10's ring-vertex ~1.004, rather than implying every shape is
  unit-normalized. `apexZ` (0.85) and the derived `ringZ` are unchanged — the existing
  "shorter than wide" test already holds a comfortable margin (height ÷ width 0.85), and a
  headless render (rendered locally with the project's own `three` dependency and Playwright
  Chromium, against `docs/mockups/dice-reference.png`) showed no spike or squat reading at
  this value, so the "may have overshot" note in SPEC-045 §2 is resolved as "no further
  change needed" rather than moved.
- **`apps/web/src/lib/dice/geometry.test.ts`** — new test
  `orders the set by circumradius: d4 ≤ d6 < d8 < d10 ≈ d12 < d20 (SPEC-045 §2)`. It computes
  each die's real circumradius as the farthest `hullPoints` vertex from the die's centre
  (post-scale, so it measures the same footprint the renderer and the Rapier collider both
  use), not the raw `SCALE` entry, and asserts the full chain plus a ≤5% `d10`/`d12` gap for
  "≈".
- **`docs/mockups/dice-preview.html`** — its own `SCALE` table (the SPEC-020-established
  tuning surface, a separate copy of the same shape math) retuned to
  `{ d4: 0.49, d6: 0.3, d8: 0.56, d10: 0.59, d12: 0.61, d20: 0.64 }` — each entry is the new
  app value divided by the tool's default "Die scale" slider (0.90), so the mockup reproduces
  the shipped circumradii at its own defaults, the same relationship its previous values held
  for five of the six dice.
- **`README.md`** § "Dice (II.6)" — the `SCALE.d10` aside is dropped from the numeral-axis
  bullet (it no longer targets "matched to the d20"), and a new bullet states the
  circumradius convention, why the cube needs a distinct correction, and the current `SCALE`
  values.
- **`PLAN.md` / `PLAN-COMPLETED.md` / `INTAKE.md`** — ledger moves.

## Visible behavior changes

Every generated die changes on-screen size. The `d6` shrinks substantially (it was reading
as the largest die in the set by a wide margin; it is now the second-smallest, just above
`d4`); `d4` also shrinks; `d8`, `d10`, `d12` and `d20` each move by smaller amounts to hold
the stated ordering, with `d20` now clearly the largest die and `d10`/`d12` close together.
No face count, material group, `locators`, `hullPoints` count, face→value remap or
`topFaceIndex` behavior changes — only each die's uniform scale factor.

## Deviations

- **The mockup's tuning surface couldn't be used live in this sandbox.** `dice-preview.html`
  loads `three.js` from `cdnjs.cloudflare.com`, which this sandbox's egress policy blocks. In
  its place, the actual by-eye check was done with a scratch render (the project's own `three`
  dependency, served locally, screenshotted headlessly with the pre-installed Playwright
  Chromium) reproducing the same shape-building code and the retuned `SCALE` table, compared
  against `docs/mockups/dice-reference.png`. `docs/mockups/dice-preview.html` itself was still
  updated (see Changes made) so it stays a faithful preview of the shipped values for a future
  session that does have CDN access.
- **`pnpm install` was required** (no `node_modules` present at session start) to run
  `pnpm verify` and to get a local `three` build for the by-eye check above; this is normal
  session setup, not a scope change.
