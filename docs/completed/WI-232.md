# WI-232 — Hosted builds get a real version

**Closed 2026-10-17.** From IN-233. **Workflow-only, no application code change** (SPEC-062
§2–§3). Model target `haiku`, run on `haiku`; effort `—`.

---

## Changes made

- `.github/workflows/deploy.yml`: both hosting build steps (`deploy-hosting` and
  `deploy-pages`) set `VITE_APP_VERSION: ${{ github.sha }}`. The full commit SHA is passed
  rather than a shortened one; the step needs no shell and the SHA is what identifies a build.
- `README.md`: one sentence beside the Session settings version footer, saying the deploy
  workflow sets `VITE_APP_VERSION` to the commit SHA and a local `pnpm dev` run shows `dev`.
  This is the only present-day text that described the version a hosted build reports.
- `vite.config.ts`'s `'dev'` fallback is unchanged, so local development still reads `dev`.

## Visible behavior changes

- A hosted build's Session settings footer shows the commit SHA instead of `dev`.
- A `.vttcamp` exported from a hosted build records that SHA in `exportedBy`, so the
  "made by a newer version" message (SPEC-062 §2) names a real build.
- The Pages build (`deploy-pages`) and the Firebase Hosting build (`deploy-hosting`) both
  carry the SHA. Local builds and the release workflow are unaffected.

## How to verify

- `pnpm verify` — docs check, lint, typecheck and unit suites all green.
- The workflow YAML parses (checked with a YAML loader after the edit).
- The deploy itself proves the build-time value: the next push to `main` builds both hosting
  targets with `VITE_APP_VERSION` set to that commit's SHA. The footer on the hosted site
  should show the SHA of the deployed commit.

## Deviations

None. The change is confined to the workflow and the one README sentence the work item named.
No application code, test, schema or store contract changed.
