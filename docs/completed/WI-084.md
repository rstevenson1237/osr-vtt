# WI-084 — `MapBackground.locked`: schema v27, the lock migration, `setBackgroundLocked`, the Assets-panel toggle

**Spec:** SPEC-039 §1 · **From:** IN-061 · **Decisions:** DEC-068 (absent ⇒ unlocked),
DEC-069 (migrate existing backgrounds locked), DEC-063 (GM-only) · **Agent:**
`claude-code` (`opus`) · **Effort:** high · **Closed:** 2026-08-18

The first link of the WI-084 → WI-085 → WI-086 chain: the stored field, its migration, its
store method and its control. Nothing on the canvas reads `locked` yet — Select does not
pick a background up until WI-085 — so this work item adds the property and the way to set
it, and changes no gesture.

## Changes made

**Schema and types**

- `packages/shared/src/types.ts` — `CURRENT_SCHEMA_VERSION` 26 → **27**; `MapBackground`
  gains `locked?: boolean`, documented as absent ⇒ unlocked (DEC-068), stored rather than
  per-viewer, and with the reason `addBackground` writes it explicitly.
- `packages/shared/src/schemas.ts` — `MapBackgroundSchema.locked: z.boolean().optional()`.

**Migration (RULE-007)**

- `packages/shared/src/migrations/index.ts` — a v26 → v27 step (a no-op on the room doc,
  like every step since v21: the field lives on a `maps/{mapId}/backgrounds/{bgId}`
  document) plus the document half `lockLegacyBackground(data)`, which writes
  `locked: true` on any background document not already carrying a boolean `locked`, and
  returns an already-stated one **by reference**. Version-agnostic and idempotent in
  exactly the way `foldLegacyMapBackground` is: it keys off the missing field, not off a
  stored version.
- The invariant that makes that safe: `addBackground` now writes `locked: false`
  explicitly on every new image, so *absence* can only ever mean "written before v27". A
  background a referee later unlocks is never re-pinned.

**Store contract (RULE-001)**

- `packages/shared/src/store/campaign-store.ts` — `setBackgroundLocked(roomId, mapId,
  backgroundId, locked)` added to the interface; `addBackground`'s doc records the
  `locked: false` default; `migrateMapBackgrounds`' doc now covers both doc-level
  migrations it runs.
- `packages/shared/src/store/memory-store.ts` and `firebase-store.ts` — implement
  `setBackgroundLocked`, default `locked` to `false` in `addBackground`, and extend
  `migrateMapBackgrounds` to sweep every map's `backgrounds` collection and pin any
  document with no stated lock. The v22→v23 fold now writes its folded image **locked**
  directly, so an upgraded room's full-grid placement is pinned in the same pass. The
  Firebase sweep reads the collection raw and unconverted, because the *absence* of
  `locked` is the signal being read.
- `packages/shared/src/store/campaign-store.contract.ts` — a fourth seeder parameter,
  `seedUnlockedBackground` (a pre-v27 document is no longer expressible through the
  interface), plus two new contract tests: `setBackgroundLocked` pins and releases and
  syncs to a second client; `migrateMapBackgrounds` locks a pre-v27 background, leaves a
  stated lock alone, and does not re-pin one the referee has since unlocked. The existing
  `addBackground` assertion now expects `locked: false`, and the fold assertion expects
  `locked: true`.
- `packages/shared/src/store/memory-store.test.ts`, `firebase-store.contract.test.ts` —
  wire the new seeder for both implementations.

**Portability (RULE-014)**

- `packages/shared/src/portability/vttcamp.ts` — `lockLegacyBackgrounds`, applied to every
  map on import **after** `foldMapBackgrounds` (so a pre-v23 archive's folded image is
  locked too), on both the current and the legacy `<v11` branch. Returns the maps by
  reference when nothing needs pinning, keeping the round-trip identity path untouched.

**Security rules (RULE-004)**

- `packages/shared/src/rules/firestore.rules.test.ts` — a test that `locked` rides the
  existing `backgrounds` boundary: a room member may set and clear it, a non-member may
  not. `firebase/firestore.rules` is unchanged — the field adds no boundary.

**UI**

- `apps/web/src/lib/components/shell/BackgroundsPanel.svelte` — a per-row
  `background-lock-{id}` toggle beside Fit and Remove (GM-only with the rest of the panel,
  DEC-063), reading `🔒 Locked` / `🔓 Unlocked` with `aria-pressed`; `addBackground` places
  new images with `locked: false`.

**Tests and docs**

- `packages/shared/src/schemas.test.ts`, `migrations/index.test.ts`,
  `portability/vttcamp.test.ts` — unit coverage for the field, the v26→v27 step,
  `lockLegacyBackground` (including that a non-boolean lock counts as absent), the
  `.vttcamp` round trip with locks in both directions, and the pre-v27 archive upgrade.
  The `currentSnapshot()` fixture and the `schemaVersion` guard move to v27.
- `apps/web/tests/e2e/backgrounds.spec.ts` — Gate 19 now asserts a new image starts
  unlocked, that the toggle pins it, that a second GM client sees the same state without
  reloading, and that unlocking works.
- `README.md` — "Background management" gains the Lock/Unlock bullet and the
  `background-lock-{id}` testid; the map-model "Background" entry documents `locked`, the
  backfill, and why `addBackground` states the flag.

## Visible behavior changes

- **Assets → Backgrounds**: every placed image now has a lock toggle in its row, reading
  `🔓 Unlocked` or `🔒 Locked`. New images start unlocked; every image that existed before
  this change is migrated locked.
- Nothing else changes yet. `locked` has no consumer on the canvas — no gesture reads it
  until WI-085 teaches Select to pick an unlocked background up — so map tools, the
  existing "Adjust on map" flow and the drag/resize handle behave exactly as before,
  whatever an image's lock says.
- Rooms upgrade silently on the referee's next room-open (`migrateMapBackgrounds`, already
  called once per room-open by `RoomShell`).

## How to verify

- `pnpm verify:all` — lint, typecheck, unit, rules, store contract (both `MemoryStore` and
  `FirebaseStore`) and Playwright against the emulator.
- In the app: open a room as referee → **Assets** → place a background → its row reads
  `🔓 Unlocked`; click the toggle → `🔒 Locked`, and a second referee tab shows the same
  without reloading.
- Migration: open a room created before this change; every background it already had reads
  `🔒 Locked`. Unlock one, reload the room, and it stays unlocked.
- Portability: export a `.vttcamp` and re-import it; lock states come back unchanged.

## Deviations

- **The contract suite gained a fourth parameter.** `defineCampaignStoreContract` now takes
  `seedUnlockedBackground` alongside `seedLegacyMapBackground`, for the same reason the
  third exists: once `addBackground` states `locked` on every write, the pre-v27 shape the
  backfill rescues cannot be produced through the interface, and the contract would have no
  way to set up the case RULE-007 requires it to prove.
- **The v22→v23 fold now writes `locked: true` itself** rather than relying on the v26→v27
  sweep that runs immediately after it. Both orderings reach the same stored state; writing
  it at the fold makes an upgraded room's pinning explicit at the point the document is
  created, and avoids depending on read-after-write ordering inside `migrateMapBackgrounds`
  on the Firebase side.
- **`lockLegacyBackground` treats a non-boolean `locked` as absent** (and therefore pins
  it). Not specified either way; it keeps the function's "the field, not the version, is
  the signal" property honest against a hand-edited document.
- SPEC-039 §1's retirement of "Adjust on map" and the `selectedBackgroundId` bridge is
  **not** in this change: `PLAN.md` assigns it to WI-085, which is the item that replaces
  the flow it belongs to. Left untouched here rather than removing a control with no
  successor yet.
