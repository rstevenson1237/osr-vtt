# WI-178 — Undo: one stack per client

SPEC-056 §2.1, DEC-108. Single unit (Deceptive). IN-166, IN-184.

**Changes made**

- `apps/web/src/lib/shell/undo-controller.svelte.ts` (new) — `UndoController`, a room-level
  service wrapping the existing generic `UndoStack<Op>` with an `Op` of closures
  (`{ undo, redo }`) rather than a data shape, so pushers with different op types
  (`VectorEditorOp`, `MapRoomOp`) share one history without sharing a type. Exposes
  reactive `canUndo`/`canRedo`, `push`, `undo`, `redo` and `clear`.
- `apps/web/src/lib/map/undo.ts` — `UndoStack` gains `clear()` (discards both the undo and
  redo arrays); `apps/web/src/lib/map/undo.test.ts` covers it.
- `apps/web/src/lib/shell/undo-controller.test.ts` (new) — unit coverage: flag reflection,
  undo/redo calling the right closure, two different pushers sharing one ordered history,
  and `clear()`.
- `apps/web/src/lib/context.ts` — new `UNDO_KEY` context symbol, alongside `MAP_TOOL_KEY`.
- `apps/web/src/lib/components/RoomShell.svelte` — instantiates one `UndoController` per
  room instance and provides it via `UNDO_KEY` (same lifetime as `MapToolController`). The
  existing active-map `$effect` (already guarded to fire only on a real `mapId` change)
  now also calls `undoCtrl.clear()`, so the stack is cleared on every viewed-map change,
  not only incidentally by `VectorMapView`'s `{#key}` remount.
- `apps/web/src/lib/components/VectorMapView.svelte` — the local `UndoStack<VectorEditorOp>`
  is gone; `applyOp`/`undo`/`redo` now push/pull through the shared `undoCtrl` from context.
  `mapCtrl.canUndo`/`canRedo` (what `MapToolbar` reads) are now mirrored from
  `undoCtrl.canUndo`/`canRedo` via a `$effect`, the same pattern `rotatableSelection`
  already uses.
- `apps/web/src/lib/components/shell/RoomsPanel.svelte` — its own local
  `UndoStack<MapRoomOp>` and `canUndo`/`canRedo` locals are gone; `applyOp`/`undo`/`redo`
  push/pull through the same shared `undoCtrl`, and the Undo/Redo buttons' `disabled`
  bindings read `undoCtrl.canUndo`/`canRedo` directly.
- `README.md` → "The selection model" (SPEC-037) — new paragraph documenting the shared
  per-client stack, its ownership (`UndoController`/`RoomShell`), that both the canvas and
  the Keys sheet push onto it, and that it is cleared on every viewed-map change.

**Visible behavior changes** — Ctrl+Z on the map canvas now also undoes an edit just made
in the Keys (map-room) quick sheet (rename/renumber/reorder/delete), and the Keys sheet's
own Undo/Redo buttons now walk back a canvas edit too — one ordered history instead of two
independent ones. Switching the viewed map now explicitly clears that history (previously
this happened only as a side effect of the map canvas remounting; the Keys sheet's own undo
history used to survive a map switch, since it lived in a component that does not remount on
one — it no longer does).

**How to verify** — `pnpm verify` (lint/typecheck/unit) and `pnpm verify:all` (adds
rules/store contract suites and the full Playwright e2e suite against the emulators,
including `rooms-manager.spec.ts`'s undo/redo assertions) both green. Manually: as referee,
rename a Keys-sheet room, then draw on the canvas and press Ctrl+Z twice — the canvas edit
and then the rename both undo, in that order; switch the active map and confirm Ctrl+Z (and
the Keys sheet's Undo button) are both disabled (nothing left in the stack).

**Deviations** — none.
