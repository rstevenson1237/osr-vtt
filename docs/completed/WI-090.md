# WI-090 — Investigation: packaging and distributing a local build

**Spec:** SPEC-042 · **From:** IN-066 · **Decision:** DEC-027 (findings become intake
items, not edits) · **Agent:** `claude-code` (`sonnet`) · **Effort:** medium ·
**Closed:** 2026-08-18

Ran now that WI-089 has landed a real local runtime to package. Built the actual
`local-build` bundle and the actual hosted bundle, grepped both, zipped the local bundle,
unzipped it into a fresh directory to simulate a downloaded release, built a real
standalone launcher with no installed dependency, served the unzipped bundle with it, and
drove the result in headless Chromium (console, page-error and network capture) through
campaign creation, session render, and a manual `.vttcamp` save/round-trip — then
constructed a `.vttcamp` with an inflated `schemaVersion` and opened it live to test the
one question that can't be answered by reading code. SPEC-042 §4's five questions, answered
below; the full evidence and new intake items are logged in `INTAKE.md`'s "Findings from
the IN-066 packaging investigation" section (SPEC-042 §4 / IN-066).

**1. The launcher.** Tested three candidates against "no new runtime dependency the user
must install first": `npx serve`/`http-server` (needs Node+npm already on the machine —
fails the constraint for a non-developer); a documented one-liner (`python3 -m
http.server` — zero artefacts but inconsistent across platforms, "most friction" as the
spec predicted, and unavailable on stock Windows); and a Node 22 Single Executable
Application (`--experimental-sea-config` + `postject`), built and run for real in this
session. The SEA binary served the app with **zero** installed dependencies, but its real
size is large: **119 MB raw, 44 MB zipped**, per platform — against a 1.4 MB zipped app.
Recommendation: the SEA binary, built per-platform on GitHub Actions' existing
ubuntu/macos/windows runner matrix (no new build infrastructure), with the size tradeoff
named explicitly rather than discovered later. Only exercised on Linux here; macOS
Gatekeeper and Windows SmartScreen behaviour on an unsigned binary is unverified.

**2. Does the strip actually strip?** Yes, confirmed fresh. `dist-local`: 133 files, 4.4 MB
unpacked / 1.4 MB zipped, **0** matches for `firebase|firestore|osr-vtt|appspot|
identitytoolkit|firebaseio` (files or occurrences), no `.map` files, no `AIza…`-shaped
string. `dist` (hosted, same commit): 179 total occurrences of the same pattern in one
chunk. Main chunk size 3,618.62 kB (local) vs 4,382.65 kB (hosted) — matches WI-089's
measured numbers exactly.

**3. How the release is produced.** Nothing today builds or ships one. `deploy.yml` (push
to `main`) and `ci.yml` (PRs to `main`) never call `build:local`. Recommend a new workflow
on a version-tag push, independent of both — the hosted pipeline is untouched by
construction, not by convention.

**4. What breaks when actually run.** Nothing, in the path that can be driven headlessly:
zip → unzip → serve with the from-scratch SEA launcher → load in Chromium → zero console
messages, zero page errors, zero failed requests, zero requests to any host but
`localhost`. Full create → render → Save → download `.vttcamp` round-trip completed
cleanly on the non-Chromium (manual-save) fallback path. The Chromium-autosave path
(`showSaveFilePicker`) could not be driven headlessly at all — it opens a native OS dialog
outside the DOM that no Playwright input can resolve — which is itself worth naming: that
path has no way to get a headless regression test the way the fallback path does.

**5. Versioning.** A user currently has **no way to know which build they have** —
`package.json`'s `version` is the placeholder `"0.0.0"` in both `apps/web` and the
workspace root, never bumped, and nothing in the built output or UI shows a version,
commit hash or build date. For the reverse compatibility direction: confirmed live, not
just by reading, that opening a `.vttcamp` **newer** than the running build is silently
accepted. `migrateRoom`'s walk is `while (version < targetVersion)` — a `schemaVersion`
*above* the target never enters the loop and the doc returns unchanged. A real archive
with `schemaVersion` patched from 28 to 999 opened cleanly through the live
"Open campaign…" flow: no error, no banner, full session render. The older-archive
direction *is* guarded (`assertSupportedFormatVersion` rejects any `formatVersion` below
`VTTCAMP_FORMAT_VERSION`) — the asymmetry is real.

## Deviations

- **A working Node SEA launcher binary was built and run**, beyond what "findings, not
  edits" might suggest is needed, because SPEC-042 §4.4 ("what breaks when it is actually
  run… on a machine with no toolchain") cannot be answered by reading code — it needs an
  actual zip, served by an actual no-install launcher, in an actual browser. The binary,
  the unzipped bundle copy, and the probe scripts were scratch artefacts in the session
  scratchpad and `/tmp`, not committed, and were deleted after use (RULE-015's "genuinely
  required to unblock" carve-out — WI-083 took the same approach with its scratch
  Playwright repro). `apps/web/dist`, `apps/web/dist-local` and a stray `osr-vtt-local.zip`
  produced while measuring were removed from the working tree before finishing;
  `dist`/`dist-local` are already gitignored.
- **The Chromium-autosave (File System Access) save path was not live-exercised** the way
  the fallback path was — Playwright cannot drive the native OS picker `showSaveFilePicker`
  opens, so only the non-Chromium fallback (file input + download) was driven end to end.
  This is recorded as a finding under Q4 rather than forced, for the same reason WI-083
  recorded rather than forced its unreachable lead.
- **No fifth intake item was logged for the autosave-path headless-testing gap** noted
  under Q4. It is a test-infrastructure observation, not a confirmed product defect, and
  SPEC-042 §4 asked about packaging and release behaviour specifically — logging it as its
  own item would be scope creep past what this investigation was asked to answer.
