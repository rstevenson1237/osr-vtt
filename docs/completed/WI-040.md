# WI-040 — Hex crawl: terrain model and contents icons

**Spec:** SPEC-030 §§2–3 · **From:** IN-011 · **Model:** `opus` ·
**Closed:** 2026-08-14

WI-038 gave a hex map a coordinate space and WI-039 drew it, but every hex was
blank. This is what a hex carries: a terrain kind painted as its own background
colour plus an overlay, and a contents icon standing on it. Model, storage,
Security Rules and renderer — **not** the UI that authors them, which is
WI-041's hex-tile quick sheet (SPEC-030 §5).

## Changes made

**The catalogs (new, pure).**

- `packages/shared/src/map/hex/catalog.ts` — the symbol-catalog pattern SPEC-030
  §2 asks for, for two catalogs. `HEX_TERRAIN_CATALOG` (nine kinds: plains,
  forest, jungle, hills, mountains, swamp, desert, water, tundra, plus
  `unknown`) carries a `#rrggbb` background colour and an overlay `ref`;
  `HEX_CONTENTS_CATALOG` (castle, town, village, fort, tower, temple, ruins,
  cave, camp, danger, plus `unknown`) carries a `ref` alone, because §3 fixes
  the icon at black. `hexTerrainEntry`/`hexContentsEntry` fall back to `unknown`
  rather than throwing, exactly as `symbolCatalogEntry` does. `hexOverlayTone`
  is the "contrasting light/dark tone": a luminance threshold (`colorLuminance`,
  sRGB-weighted) against the terrain's **own** colour, so a re-coloured terrain
  can never be left with the tone its old colour needed — no per-entry stored
  tone to go stale.
- `packages/shared/src/map/hex/catalog.test.ts` — 10 cases: both catalogs carry
  the kinds the spec names, with unique keys and a stable lookup; an unknown
  kind resolves rather than throws; **every catalog terrain's overlay tone is on
  the other side of mid-grey from its own fill**; the three-digit colour form
  expands; an unparseable colour reads as mid-grey.
- `packages/shared/src/map/hex/index.ts` — re-exports it under the existing
  `hexMap` namespace.

**Art (new, original).**

- `apps/web/public/assets/hex/terrain/*.svg` (9), `hex/contents/*.svg` (10),
  `hex/unknown.svg` (1, shared by both catalogs' fallback entries). Hand-written
  SVG, **authored white** rather than the dungeon pack's black: both overlays are
  tinted at the render boundary and a Pixi tint multiplies, so black art could
  not be tinted lighter.
- `apps/web/public/assets/ATTRIBUTION.md` — records them as original works and
  why they are white.

**Storage.**

- `packages/shared/src/types.ts` — `HexTile { id, hex, terrain?, contents? }`,
  and `CURRENT_SCHEMA_VERSION` 24 → **25**.
- `packages/shared/src/schemas.ts` — `HexTileSchema`.
- `packages/shared/src/converters.ts` — `hexTileBody` / `hexTileFromDoc`, a pair
  of **pure helpers rather than a `FirestoreDataConverter`**. A hex tile's
  coordinate *is* its document id, so the id is load-bearing in a way no other
  collection's is, and a `fromFirestore` could only throw on an id that names no
  hex — taking the whole `onSnapshot` down, so one hand-edited document would
  blacken every painted hex. `hexTileFromDoc` returns `null` instead and the
  caller drops it. Being store-agnostic, both stores read through the same code.
- `packages/shared/src/store/campaign-store.ts` — `'hexTiles'` joins
  `EXPORTED_MAP_COLLECTIONS` (so it exports, imports and deletes with the map),
  and three methods join the contract: `subscribeHexTiles`, `setHexTerrain`,
  `setHexContents`.
- `packages/shared/src/store/memory-store.ts` / `firebase-store.ts` — both
  implementations. Firestore's does its read-modify-write in a **transaction**
  (`runTransaction`, imported aliased because the RTDB function of the same name
  was already in scope): whether clearing a field deletes the document depends
  on what else is on it, and that test and the write it decides must not be
  separated.
- `packages/shared/src/migrations/index.ts` + `index.test.ts` — the v24 → v25
  step. A no-op on the room doc like v23 → v24, with no document half either:
  the collection is new, so nothing anywhere moves into it. The bump stamps
  `.vttcamp` archives.
- `packages/shared/src/portability/vttcamp.test.ts` — RULE-007's round-trip:
  three painted hexes (terrain-only, contents-only, both) come home with their
  **ids** intact, negative coordinates included, and do not leak onto the
  square-grid map beside them. The `schemaVersion` assertion moves to 25.
- `packages/shared/src/store/campaign-store.contract.ts` — three contract cases
  (RULE-001), passing against `MemoryStore` and `FirebaseStore` alike: terrain
  and contents are independent writes on one document keyed by its own
  coordinate; a hex may carry either alone, clearing the last field deletes the
  document, and clearing an unpainted hex writes nothing; tiles are per-map and
  negative coordinates round-trip.

**Security Rules (RULE-004).**

- `firebase/firestore.rules` — a `hexTiles/{hexId}` block: `read: signedIn()`,
  `write: isMember(roomId) || isGM(roomId)`. SPEC-030 §3's "any seat may change
  a hex's contents" read literally — the existing member write scope, not a new
  boundary, and unlike `backgrounds` not referee-only in the UI either.
- `packages/shared/src/rules/firestore.rules.test.ts` — four cases: a member may
  paint, repaint and clear; the GM may paint; a non-member is denied; any
  signed-in client may read.

**Renderer.**

- `apps/web/src/lib/map/vector-engine.ts` — `renderHexTiles(tiles, size)` on the
  `VectorMapEngine` interface. Two new containers: `hexTerrainGraphics` +
  `hexTerrainSprites` at the **bottom of `floor`** (terrain is the ground, so
  grid lines draw over it) and `hexContentsSprites` on **`overlay`** (an object
  standing on it, so it draws over the grid). Each painted hex contributes one
  closed path to a single `Graphics` — the first per-region fill this renderer
  has had — plus a tinted sprite, cached per tile id across redraws like the
  door/symbol sprites. Exported `hexTerrainArtPx`/`hexContentsArtPx` so the art
  fit is unit-testable without a canvas. No pan/zoom redraw: painted hexes are a
  finite set of stored documents in world space, not an unbounded plane.
- `apps/web/src/lib/map/vector-engine-hex.test.ts` — three cases: both art boxes
  stay inside the hex's own boundary (half-diagonal < inradius), the contents
  icon is smaller than the terrain overlay, and both scale with the hex.
- `apps/web/src/lib/components/VectorMapView.svelte` — `hexTiles` state, a
  `subscribeHexTiles` subscription **opened only for a hex map** (a square map
  has no axial coordinates for these documents to be keyed by, so it is one
  listener it never opens), and `renderHexTiles` in `renderAll` beside the grid
  it shares a multiplier with.

**Docs.**

- `README.md` — a "Terrain and contents" subsection under "Hex-grid maps"; the
  layer table's `floor` and `overlay` rows now name the hex sources; the
  "square-lattice consumer" bullet points at painted hexes instead of calling
  them unbuilt.
- `docs/spec/SPEC-030.md` — status line, plus §2 and §3 build notes recording
  what landed and that the authoring UI is WI-041's.
- `PLAN.md` / `PLAN-COMPLETED.md` / `INTAKE.md` — WI-040 moved to §3; IN-011's
  disposition now reads "WI-041 open".

## Visible behavior changes

**None yet in the UI, by design.** Nothing in this work item authors a hex tile:
no palette, no click target, no quick sheet. A referee cannot paint a hex until
WI-041 ships the hex-tile quick sheet SPEC-030 §5 calls for.

What *is* observable: a hex map whose `hexTiles` documents exist — written by a
test, an import, or WI-041 — renders them, with each painted hex filled in its
terrain colour under an overlay and its contents icon in black on top, included
in a PNG export like any other `floor`/`overlay` content. A `.vttcamp` archive
of such a room carries them and restores them onto the same hexes. Square-grid
maps are untouched in every respect, including opening one fewer subscription
than a hex map does.

## How to verify

- `pnpm verify:all` — the whole battery. Specifically:
  - `pnpm --filter @osr-vtt/shared test:unit` covers the catalogs
    (`map/hex/catalog.test.ts`), the v24 → v25 migration, and the `.vttcamp`
    round-trip.
  - The emulator-backed contract suite runs the three new hex-tile cases against
    **both** stores (RULE-001), and `firestore.rules.test.ts` the four rule cases.
  - `pnpm --filter web test:unit` covers the art sizing
    (`vector-engine-hex.test.ts`).
- By hand, until WI-041: make a hex crawl with **"+ New hex crawl"** in the
  Assets activity, then write a tile from the browser console through the store
  (`setHexTerrain(roomId, mapId, { q: 0, r: 0 }, 'forest')`) and watch the origin
  hex fill green with a white conifer overlay under its `0,0` pill; add
  `setHexContents(..., 'castle')` and a black castle lands on top. Clearing both
  removes the document and the hex goes blank again.

## Deviations

- **Schema bumped to v25 for a purely additive collection.** RULE-007 governs
  store schema changes, and the precedent is exact: v22 → v23 bumped for the
  `backgrounds` subcollection and v23 → v24 for an additive optional field, both
  no-ops on the room doc, both justified by stamping `.vttcamp` archives. A
  reader could argue a new collection needs no version at all; the bump is the
  conservative reading and costs one no-op migration entry.
- **`hexTileBody`/`hexTileFromDoc` instead of a `FirestoreDataConverter`.**
  Every other collection in `converters.ts` uses a converter. This one cannot,
  for the reason recorded above — the document id is the coordinate, and a
  converter can only throw on an id that names no hex. The pair of pure helpers
  is also what lets both stores share one read behaviour rather than two that
  happen to agree.
- **Contents kinds beyond the spec's list.** SPEC-030 §3 names "castle, town,
  fort, cave, danger, temple, …"; the catalog adds village, tower, ruins and
  camp, and §2's terrain list gains desert, water and tundra past its "…". The
  spec's ellipses invite a usable set; every named kind is present.
- **No draw cap on painted hexes.** `renderHexGrid` has `MAX_HEXES_DRAWN` and
  `MAX_HEX_PILLS` because it draws an unbounded plane every frame. Tiles are a
  finite set of stored documents redrawn only when they change, so a cap would
  only ever hide data a referee deliberately stored.
