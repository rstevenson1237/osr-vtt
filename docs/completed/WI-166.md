# WI-166 — Lazy-load dice renderer and hex art; bundle-size budget in CI

SPEC-055 §§1–2. Part of **Batch 3** (WI-166, WI-167, WI-168, WI-169) — one pull request,
one combined summary.

## Changes made

- `apps/web/src/lib/dice/scene-loader.ts` (new) — the one place that `import()`s
  `dice/scene.ts` (three.js + Rapier WASM). Caches the in-flight promise so every caller
  shares one fetch, and also dynamically imports `dice/textures.ts` in parallel to give
  `clearDiceMaterialCacheIfLoaded` a synchronous peek once loaded.
- `apps/web/src/lib/components/DiceOverlay.svelte` — no longer imports `DiceScene`
  statically. `playRoll()` loads the module (if not already loaded) the first time a
  live roll needs to tumble, then mounts the scene against the existing host element
  and plays that roll. A roll that arrives mid-fetch is not queued — dice authority is
  the seed, so the chip/readout already show the correct result; only the tumble
  animation catches up once the module is ready. `onMount` also awaits
  `diceSceneModuleLoaded()` to mount the renderer as soon as *anything* (a roll, or the
  tray opening) has triggered the fetch, without itself becoming a trigger — see
  Deviations.
- `apps/web/src/lib/components/DiceTray.svelte` — `onMount` fires the same loader
  (fire-and-forget) so the tray opening is the other named trigger (SPEC-055 §1),
  warming the module cache before a roll needs it.
- `apps/web/src/lib/components/RoomShell.svelte` — the theme-change effect's
  `clearDiceMaterialCache()` call (a static import of `dice/textures.ts`, which was
  pulling three.js into the main bundle regardless of whether anyone ever rolls) is
  replaced with `clearDiceMaterialCacheIfLoaded()` from the new loader module — a no-op
  before the renderer has ever loaded.
- `apps/web/src/lib/map/vector/hex-art.ts` (new) — the hex terrain/contents overlay
  baking and sprite-diffing system (`bakeHexClippedArt`, `loadHexClippedTexture`,
  `syncHexArt`, `renderHexTiles`, `renderHexSymbols`), moved out of `vector-engine.ts`
  into its own module behind a `createHexArtRenderer(deps)` factory.
- `apps/web/src/lib/map/vector-engine.ts` — `renderHexTiles`/`renderHexSymbols` now
  `import('./vector/hex-art')` the first time either is called with an actual hex map
  (`size > 0`), caching the created renderer instance for the engine's lifetime. The six
  Pixi containers the module draws into (`hexTerrainGraphics`, `hexTerrainSprites`,
  `hexContentsSprites`, `hexSymbolSprites`) stay created synchronously at their original
  position, so layer order is unaffected — only the baking/diffing code streams in on
  demand. `hexTerrainArtPx`/`hexContentsArtPx` (pure arithmetic, no heavy deps) stay in
  `vector-engine.ts` and are imported back by `hex-art.ts`.
- `scripts/check-bundle-size.mjs` (new) — reads each build's `index.html` for its
  `<script type="module">` entry and asserts its raw byte size is under a budget:
  1,622,100 bytes hosted, 783,600 bytes local (measured size right after §1 and §3
  landed, +10%).
- `.github/workflows/ci.yml` — `static` job gains a `pnpm build:local` step and a
  `node scripts/check-bundle-size.mjs` step, both folded into the existing
  "fail if any step above failed" gate.
- `README.md` — "Dice (II.6)" gets a "Loading" paragraph; "Hex-grid maps" notes the
  lazy-loaded module and its layer-order guarantee; "Test culture (II.9)" documents the
  bundle-size budget and CI's extra steps.

## Visible behavior changes

The dice tumble animation may start a tick after the roll result is already showing (via
the chip/readout) the very first time a room rolls or opens the tray — the seed-derived
result itself is never delayed. A hex map's very first render may show its terrain fill
and overlay art a tick apart rather than together, for the same reason. Neither is
visible to Playwright's fixed-timeout assertions (both were exercised against the real
dev server). No `data-testid` moved. `pnpm build`'s main entry chunk dropped from
~1.65 MB to ~1.47 MB (three.js/Rapier now load in a separate ~2.6 MB chunk, fetched on
demand); `pnpm build:local`'s dropped similarly.

## How to verify

- `pnpm build && pnpm build:local && node scripts/check-bundle-size.mjs` — passes, and
  `dist/assets/scene-*.js` / `dist-local/assets/scene-*.js` (three.js + Rapier) and
  `dist/assets/hex-art-*.js` appear as separate chunks, not inside the main entry.
- `pnpm test:unit` — green (includes `vector-engine-hex.test.ts`, unaffected).
- Manually: open a room, confirm the dice tray/tumble still work after a fresh page
  load; open a hex map, confirm terrain and contents art still render.

## Deviations

The naive lazy-load (fetch on demand, mount inside the same `.then()` that plays the
roll) broke two e2e specs the first time it ran against real Playwright: `scene.mount()`
— `THREE.WebGLRenderer` creation, shader compilation, and a `PMREMGenerator` bake — is
synchronous and, under headless software-rendered WebGL (SwiftShader), genuinely slow.
Baseline paid this cost at `DiceOverlay`'s page-load `onMount`, far from any timed
assertion; deferring it landed that same cost inside a roll's own critical path, and
because it ran inside a promise `.then()` (a microtask, which the browser cannot paint
between — only between macrotasks), it blocked painting for long enough to miss
`shared-roll.spec.ts`'s 8s "the staging panel closes" assertion and
`dice-overlay.spec.ts`'s 8s "the result chip is visible" assertion, even though neither
assertion has anything to do with dice rendering. Root-caused by reverting to the
pre-batch commit in a worktree (passed cleanly) and by reading Playwright's network/trace
capture, which showed the renderer module fully loaded ~2s *before* the roll click in the
failing case — ruling out "still fetching" and pointing at `mount()`'s own synchronous
cost instead.

Fixed within this same item, in the same two files it already changes:
`scene-loader.ts` gained `diceSceneModuleLoaded()`, a promise that settles once
`loadDiceSceneModule()` is triggered by *anyone* without itself being a trigger, and
`DiceOverlay.svelte`'s new `ensureScene()` (a) uses it from `onMount` so the renderer
mounts as soon as the tray-open prefetch (or an earlier roll) makes the module available,
well ahead of a later roll, and (b) defers the actual `mount()` call by one
`setTimeout(0)` macrotask so an already-queued paint (the chip becoming visible) gets a
chance to render first regardless of which path triggered the load. Verified by
re-running `dice-overlay.spec.ts`, `dice-profiles.spec.ts`, `hex-map.spec.ts` and
`shared-roll.spec.ts` (16/16 pass) against the real Firebase emulator, and by re-running
`pnpm verify:all` in full.
