# WI-116 — Retire the `gen:disc:` scheme — writers move to fields, refs cleared

**Spec:** SPEC-048 §5 · **From:** IN-109 · **Model:** `sonnet` · **Effort:** M
**Gate cleared:** user, 2026-09-08 (Phase 4) · **Completed:** 2026-09-09

Phase 4 of 4 of the token-letter programme. The last section removes what WI-113 – WI-115
replaced: writers stop producing `gen:disc:{label}:{colorToken}` refs, `imageRef`/
`portraitRef` are cleared once they are only ever such a recipe, and the ref-resolution
functions that made the scheme work are deleted from `AssetStore`'s public surface. The
deletion is the acceptance test (DEC-087 (a)) — a branch kept alive for old data means the
mechanic was hidden rather than removed.

## Changes made

**`packages/shared/src/store/asset-store.ts`** — `resolveGenTokenRef`, `parseGenTokenRef`,
`buildGenTokenRef` and their private helpers (`GEN_TOKEN_PREFIX`/`RE`, `encodeGenLabel`/
`decodeGenLabel`) are deleted. `renderGenTokenSvg(label, color)` survives, demoted to an
ordinary pure function with no ref involved. New `genTokenDataUri(label, color)` wraps it
as a `data:image/svg+xml` URI — the one thing every remaining `<img>` surface needs.
`BundledAssetStore.resolve`/`FirebaseStorageAssetStore.resolve` drop their `gen:` branch
entirely; a `gen:disc:`-shaped string is now just an ordinary ref (unresolvable, same as
any other path that happens to match no rule).

**`packages/shared/src/migrations/index.ts`** — a private `parseLegacyGenRef` (the same
regex, kept only here) replaces the deleted `parseGenTokenRef` inside
`backfillLetterFromRef`, so a `.vttcamp` archive minted before the retirement still
migrates correctly. New `clearGenTokenRef`/`clearGenProfileRef`: given a document already
carrying `letter`/`color`, drops `imageRef`/`portraitRef` outright (object destructuring,
not a written `undefined`) once the ref is only ever the `gen:disc:` recipe — real art is
returned by reference, unchanged.

**Store wiring** — `firebase-store.ts`/`memory-store.ts`'s `migrateTokenLetters` and
`portability/vttcamp.ts`'s import-side backfill now call the clearing step right after the
existing backfill, in the same write/pass. `LocalStore` inherits the fix from
`MemoryStore` with no override needed.

**Writers move to fields** — `TokenPickerDialog.svelte`'s Generate-default tab no longer
builds a ref (`currentRef` is `''` for that tab unconditionally); `TokenPickerResult`
gains `genLabel` (the customized character field, replacing what used to collapse onto a
shared ref) alongside the existing `genColor`. `EncounterBoard.svelte`/
`VectorMapView.svelte`'s "Add creature" flows write `letter`/`color` fields and omit
`imageRef` entirely for a generated batch (previously always present as a ref);
`defaultCreatureBatch` (`apps/web/src/lib/tokens/labels.ts`) gains an optional
`sharedLetter` argument so a customized character field still gives every token in the
batch the same symbol. `CharacterDock.svelte`'s "My token"/colour-pick flows write
`letter`/`color` via `setTokenLetter`/`setTokenColor`/`setProfileColor` instead of
rebuilding a ref through `parseGenTokenRef`/`buildGenTokenRef`; its preview reads
`profile?.letter`/`color`, falling back to the owned/creature token's own fields, then a
computed default (`seatLetterFor` + the character-colour system) — never a ref. The
character-sheet drag payload (`apps/web/src/lib/tokens/drag.ts`) carries `letter`/`color`
as an alternative to `imageRef`. `apps/web/src/lib/tokens/labels.ts`'s `defaultPortraitRef`
is deleted outright — nothing needs a generated ref any more.

**Surfaces that still need a resolvable image** draw one with `genTokenDataUri` instead
of resolving a ref: `EncounterBoard`'s board-card portrait, and `TokenPickerDialog`'s own
Generate-default preview. `export-layers.ts`'s PNG path needed no change — it extracts the
live Pixi scene graph (`renderer.extract.canvas`), which already includes the letter as a
real `PIXI.Text` object from WI-115's render pass, independent of `imageRef`.

**Docs** — `RULES.md` unaffected. `README.md`'s "Tokens, assets & theming" section is
rewritten: the old "Generated default tokens" ref-scheme bullet becomes "Retired: the
`gen:disc:...` ref scheme", and the v30 bullet's "nothing changes visibly" framing is
replaced with the final field-only state. "Creature names and symbols" drops its stale
"still build a `gen:disc:` ref" and "reads the letter out of the ref, by regex, at v30"
passages. Doc comments that said a code path was "unreachable at v30" (`creatureLabel`,
`apps/web/src/lib/encounter/labels.ts`'s `tokenLabel`, `VectorMapView`'s sprite-texture
sync) are corrected — those paths are reachable now that refs are actually cleared.
`Token.imageRef`/`Token.color` doc comments in `types.ts` are updated to stop describing
the intermediate v30 state.

**Tests** — `asset-store.test.ts` drops every `resolveGenTokenRef`/`parseGenTokenRef`/
`buildGenTokenRef` test and adds coverage for `genTokenDataUri` and for
`BundledAssetStore.resolve` no longer special-casing a `gen:disc:` literal.
`migrations/index.test.ts` adds a `clearGenTokenRef`/`clearGenProfileRef` describe block;
the existing `backfillTokenLetter`/`backfillProfileLetter` tests are untouched (the
backfill itself still doesn't clear — that's the new, separate function's job).
`campaign-store.contract.ts`'s `migrateTokenLetters` test now asserts the ref is cleared
rather than left in place. `portability/vttcamp.test.ts`'s three affected round-trip
tests are updated: a "current, correctly-migrated" lettered token no longer carries a
`gen:disc:` ref in its fixture (one is changed to real art instead, to keep covering "a
token can carry both a letter and real art" per §4), and the v29→v30 import test now
asserts the ref is cleared on the way in. `labels.test.ts` drops the `defaultPortraitRef`
suite and adds a case for `defaultCreatureBatch`'s new `sharedLetter` argument.

## Visible behavior changes

None for a referee looking at an already-open room: a generated token/portrait still
shows the same coloured letter it did, the letter's colour/label logic is unchanged, and
"Add creature"/"My token" still work exactly as before. What is no longer possible is
inspecting a token's `imageRef` and finding a `gen:disc:` string — a letter-only token now
genuinely has no `imageRef` at all, matching what SPEC-048 §1 said `imageRef`'s absence
would mean from the start.

  the once-per-room-open migration backfills `letter`/`color` and clears the refs in the
  same pass, with no visible flicker.

## Deviations

1. **The ref-clearing step was wired into the existing `migrateTokenLetters`/
   `.vttcamp`-import call sites rather than a new schema version.** SPEC-048 §5 does not
   name a schema version for this step, and clearing an already-optional field (made
   optional at v30) is not a shape change RULE-007 requires a version bump for. The
   clearing functions ride the same idempotent, version-agnostic pattern
   `backfillTokenLetter`/`backfillProfileLetter` already use.
2. **`TokenPickerResult` gained a new `genLabel` field, and `defaultCreatureBatch` gained
   a new `sharedLetter` argument**, neither named by the spec text. Before this change, a
   customized character field on the Generate-default tab collapsed a whole "Add
   creature" batch onto one shared `gen:disc:` ref; once the tab stops building a ref at
   all, that customization had nowhere to travel without one of these two additions.
   Without them, typing a custom symbol into "Add creature"'s Generate-default tab would
   have silently stopped working — a real regression the gate's approved scope does not
   call for introducing.
3. **`CharacterDock`'s portrait preview now falls back to the owned/creature token's own
   `letter`/`color` fields**, a read path that did not exist before (a character's
   portrait previously never consulted its token's `imageRef` either). This was needed
   because there is no `setProfileLetter` on the contract (only `setTokenLetter`, added by
   WI-113 for WI-117) — "My token"'s Generate-default customization is written to the
   token, and the sheet has to read it back from there to show it. `ProfileInstance.letter`/
   `color` remain the first-precedence read, so a value the v29→v30 migration or a prior
   customized portrait wrote is never shadowed by the token's own fields.
