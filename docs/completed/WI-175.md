## Method

Every token in `apps/web/src/lib/theme/tokens.css` was paired with the background(s)
it is actually rendered against, found by grepping `apps/web/src` for each `var(--…)`
use as a `color`/`background` declaration (not merely present in a selector). WCAG
2.1 contrast ratios were computed from sRGB relative luminance (the standard
`(L1+0.05)/(L2+0.05)` formula) for every real pair, in both `parchment-dark` (the
`:root` values) and `keyed-blue` (`:root[data-theme='keyed-blue']`). Thresholds:
4.5:1 for normal text, 3:1 for large/bold text (≥ 18.66px, or ≥ 14px bold) and for
non-text UI (icons, borders that alone convey a boundary).

Two tokens that scored badly in a naive "every token vs. every background" pass were
excluded as false positives once their actual call sites were read:

- `--dice-ink-dark` is never compared against the fixed `--dice-face` token in
  practice — `inkFor()` (`apps/web/src/lib/dice/textures.ts:94`) picks it only when
  the *roller's own chosen* face color has luminance > 0.55, so it is always checked
  against the color it will actually sit on, not a fixed swatch.
- `--map-ruler-text` (`tokens.css:81,157`) is read into `MapTheme.rulerText`
  (`map-theme.ts:39,70`) but nothing yet draws with it — WI-164 (drag-distance chip,
  gated, not yet executed) is its first consumer. Flagged below as a build note for
  WI-164 rather than an intake item, since there is no live rendering to audit.

## Findings (logged as IN-211 – IN-214)

1. **IN-211 (most severe).** The presence-chip initial (`SessionTab.svelte`) paints
   `--bg-root` text over a `--group-*` background chosen by seat. Two of the five
   group colors — `--group-records` and `--group-referee`, both aliased to panel
   *border* colors (`--panel-table-line` / `--panel-referee-line`) — are themselves
   close in lightness to `--bg-root`: **1.84:1** and **1.43:1** in `parchment-dark`
   (both near-illegible), **2.97:1** and **3.95:1** in `keyed-blue` (both under the
   4.5:1 a 0.62rem/700-weight initial needs). The same two tokens, used as intended
   (a 1px border against their own `--panel-*-bg`), also read as near-invisible
   dividers in `parchment-dark` (1.32–1.65:1) — one root cause, two symptoms.
2. **IN-212.** `--accent-text` is used as real body/heading text in ten-plus
   components (`AccountControls`, `MarkdownView`, `TensionBar`, `RollSheet`,
   `CharacterSheet`, `SessionTab`, `PresentationToggle`, `MobileTopBar`, …). It holds
   up in `parchment-dark` (10.5–12.1:1) but fails in `keyed-blue`: **3.70:1** on
   `--bg-panel`, **2.88:1** on `--bg-inset` — under AA even for large text in the
   second case.
3. **IN-213.** Two feedback-color pairs dip under 4.5:1 for real text: `--complication`
   / `--failure` against their own `-bg-strong` chip background (`ActionLog`,
   `RollStrip`, `DiceOverlay` all pair them this way) score **3.81:1** / **4.05:1** in
   `keyed-blue` (fine in `parchment-dark`, 5.2–6.7:1); and `--danger` as a text color
   (`EncounterBoard.svelte`'s group-delete button, the one site) scores **3.69:1** on
   `--bg-panel` in `parchment-dark` (fine in `keyed-blue`, 5.44:1).
4. **IN-214.** `--text-dim` on `--bg-panel-alt` — a common secondary-text pairing —
   scores **3.99:1** in `keyed-blue`, under the 4.5:1 normal-text threshold (fine
   everywhere else it's used: 4.89–6.45:1).

No finding touches the `CampaignStore`/`AssetStore` contract, a schema, a security
rule, or a `data-testid`; all four are token-value changes local to `tokens.css` (or,
for IN-211, a possible different token choice for chip text), left for their own gate
per RULE-015.
