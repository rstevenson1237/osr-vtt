## WI-033 — Battle map: `GameMap` schema + migration + `.vttcamp` round-trip

**Spec:** SPEC-029 §3 · **From:** IN-010 · **Closed:** 2026-08-09 · `claude-code`, `opus`,
effort `high`

### Changes made

- **`packages/shared/src/types.ts`** — `CURRENT_SCHEMA_VERSION` 21 → **22**. `GameMap`
  gains an optional `battle?: BattleMapCapture`, and the new `BattleMapCapture` interface
  holds `sourceMapId` plus `rect` (`{ minX, minY, maxX, maxY }`) — the captured region in
  the **source** map's lattice units (RULE-006), whole cells only. The rect is spelled out
  structurally rather than importing `BBox` from `map/vector/types.ts`, keeping `types.ts`
  dependency-free as it is today. Absent `battle` means an ordinary, permanent map.
- **`packages/shared/src/schemas.ts`** — new `BattleMapCaptureSchema`, wired onto
  `GameMapSchema` as `battle: …optional()`. This is load-bearing rather than decorative:
  `gameMapConverter` parses through `GameMapSchema` in **both** directions, and zod strips
  undeclared keys, so an undeclared field would be silently unwritable. `min`/`max` are
  not cross-checked — an inverted rect is a capture-tool bug, not a document to reject on
  read.
- **`packages/shared/src/migrations/index.ts`** — v21 → v22 migration registered. A no-op
  on the room doc, like v17→v18, v19→v20 and v20→v21: the field lives on a
  `maps/{mapId}` document that `migrateRoom` never sees, it is additive, and absence
  already carries the meaning every pre-v22 map has. The comment records where the
  non-no-op half lives (the export strip) and why the bump still earns its keep — it
  stamps `.vttcamp` archives.
- **`packages/shared/src/portability/vttcamp.ts`** — the behavioural half. New
  `isBattleMapDoc` (deliberately lenient: *any* `battle` object marks the doc, so a
  half-written marker still excludes the map) and `withoutBattleMaps`, which drops every
  battle map and re-points `room.activeMapId` when it named one — preferring the battle
  map's own `sourceMapId`, then any remaining map, then dropping `activeMapId` entirely
  (it is optional precisely so `ensureActiveMap` can recover). It returns the snapshot by
  reference when there is nothing to strip, so the round-trip identity path is untouched.
  Applied on both sides of the archive boundary: `snapshotToArchive` runs it first, before
  `collectAssetRefs`, so a battle map's background never reaches the manifest either;
  `archiveToSnapshot` runs it on the `maps` branch as belt and braces against an archive
  another build wrote.
- **`packages/shared/src/schemas.test.ts`** — five `GameMapSchema` cases: the marker
  survives the parse (the zod-strips-unknown-keys trap), an ordinary map has none,
  negative lattice coordinates are accepted, an empty/missing `sourceMapId` is rejected,
  and an incomplete rect is rejected.
- **`packages/shared/src/migrations/index.test.ts`** — v21→v22 no-op test and a
  "does NOT invent a battle marker" test, matching the shape of the v17→v18 pair. The
  full-walk test now asserts `CURRENT_SCHEMA_VERSION` rather than a hard-coded `21`, and
  the "two most recent steps are no-ops" comment becomes four.
- **`packages/shared/src/portability/vttcamp.test.ts`** — a `snapshotMidBattle()` fixture
  (a battle map cut out of `map-1` at rect 4,4–12,10, rendered at half cell size over
  double the cells per SPEC-029 §4, with the room switched into it) and six cases: the
  export drops it and returns the room to its source; the mid-fight export equals the
  before-the-fight export exactly; its background stays out of the manifest; a capture
  without Start leaves `activeMapId` alone; an archive from another build is stripped on
  import; the source map being gone falls back to a remaining map; and the battle map
  being the only map leaves no `activeMapId` key at all. Plus an explicit identity
  round-trip for an ordinary map at v22.
- **`README.md`** — new "Battle maps — a temporary map in the same room (SPEC-029 §3)"
  subsection under Map system, stating plainly that only the schema has landed and the
  export/import strip rule in full.
- **`docs/spec/SPEC-029.md`** — status line moves from "specified, not built" to "partly
  built", naming WI-033 as landed and WI-034 – WI-036 as remaining.
- **`PLAN.md`** — WI-033 row removed from §2; the in-flight status note used during
  execution removed with it.
- **`PLAN-COMPLETED.md`** — WI-033 row added to §3.

### Visible behavior changes

**None.** Nothing writes `GameMap.battle` yet — the capture tool (WI-034), the bounded
render (WI-035) and the Start/Exit quick sheet (WI-036) are what will. New rooms are
created at `schemaVersion` 22 instead of 21, and an older room is walked forward on read
by a migration that changes no field. The one path whose behaviour *would* differ is an
export of a room that contains a battle map, which no build can currently produce.

### Deviations

- **`INTAKE.md`'s IN-010 row was not moved from §1.1 to §1.2.** IN-010 is a Shape A intake
  covering WI-033 – WI-036; three of its four work items are still open, so closing the
  row now would misreport the feature as delivered. `INTAKE.md` itself flags IN-010 as
  "correctly open". It moves when WI-036 lands.
- **No store method was added.** `createMap` still takes `{ name }` only, so nothing can
  yet create a battle map. The work item is scoped to schema, migration and round-trip;
  the creation path (and the RULE-001 contract-suite entry it will need) belongs to
  WI-036, which performs Start. Adding a method here would have been an unused API
  landing a session early.
- **The strip runs on import as well as export.** The spec states the rule as "a battle
  map must never survive an export", which the export-side strip satisfies on its own. The
  import side was added because it is the same function called once more, and because the
  failure it prevents — an archive from another build restoring a temporary map that
  nothing owns, possibly as the active one — is silent and unrecoverable from inside the
  app.
- **One pre-existing failure in `pnpm verify`'s unit sweep.**
  `packages/shared/src/store/account-recovery.emulator.test.ts` fails with
  `auth/network-request-failed` when run without the emulator, because `test:unit` excludes
  only `*.rules.test.ts`. Confirmed unrelated by stashing this change and reproducing it on
  a clean tree; it passes under `verify:all`, which supplies the emulator. Not fixed here —
  out of chain (RULE-015).
