## Visible behavior changes

`pnpm verify` and `pnpm verify:all` now run `pnpm docs:check` first; a mismatch between an
index and what it points at fails the suite immediately, printing each violation instead
of surfacing later as a stale-doc bug report. `pnpm docs:check` is also runnable on its
own.

## How to verify

`pnpm docs:check` exits 0 on the current tree. Introducing a deliberate mismatch (e.g.
flipping `SPEC-029`'s index status to `Completed` while its file still says `Active`) makes
it print one line naming the mismatch and exit 1; reverting the mismatch restores exit 0
(exercised in this session, not left in the tree). `pnpm verify` is green.

## Deviations

The check's first run surfaced three genuine, pre-existing violations, none introduced by
this work item: a silent gap at WI-138 (no record of it exists anywhere in the repository),
and two `INTAKE.md` §1.1 rows (IN-150, IN-151) logged straight to the index during CI
triage without the batch prose section SPEC-052 §1 expects. Since this check ships wired
into `pnpm verify`'s first step, shipping it red for reasons outside this work item would
fail every session's verification from the moment it lands — squarely the kind of thing
RULE-015's "genuinely required to unblock the current work item" exception covers. Fixed
each with the smallest possible structural note rather than any new judgment: a one-line
unbolded annotation in `PLAN-COMPLETED.md` for WI-138 (so it does not itself parse as a
completed-item row), and a short cross-reference section in `INTAKE.md` for IN-150/IN-151
that restates their existing Disposition-cell text rather than adding new rationale. No
application code, schema, rule, or `data-testid` touched by either.
