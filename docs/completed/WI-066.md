#### WI-066 — Blaze upload containment: `storage.rules` + rule tests, client-side friction, deletion, the `[HUMAN]` runbook

**Spec:** SPEC-034 §§2–4 · **From:** IN-037 · **Model:** `opus` · **Effort:** high ·
**Closed:** 2026-08-14

**Changes made.**

_The boundary (§2)._

- **`firebase/storage.rules` (new).** The only boundary in the upload path. Objects match
  `rooms/{roomId}/uploads/{uid}/{objectId}`. `create`/`update` require a signed-in
  uploader writing under their own uid segment, a `players/{uid}` seat in that room (a
  cross-service `firestore.exists`), `request.resource.size <= 5 * 1024 * 1024`, and a
  content type in `image/png|jpeg|webp|gif` — `update` carries the same conditions as
  `create` so an overwrite cannot smuggle past either bound. `delete` is uploader-or-GM.
  A separate recursive-wildcard match grants `read` at `signedIn()` over
  `rooms/{roomId}/uploads/**`, which is also what makes `list` work: a list request is
  evaluated against the _prefix_, not the objects. No catch-all deny block, deliberately —
  Storage denies by default and an `if false` clause does not subtract from what another
  rule allows.
- **`firebase.json`.** Added the `storage.rules` pointer and the storage emulator on port 9199.
- **`packages/shared/src/rules/storage.rules.test.ts` (new, RULE-004).** 26 tests over
  membership, path shape, per-object size at and past the limit, the content-type
  allowlist (including the SVG refusal), overwrite bounds, read/list, and deletion. Runs
  against the Storage **and** Firestore emulators together, because the membership check
  is only meaningful if the seat roster really exists.

_The friction (§3.2)._

- **`packages/shared/src/store/upload-containment.ts` (new).** `MAX_UPLOAD_BYTES` (5 MB),
  `ALLOWED_UPLOAD_CONTENT_TYPES` (no `image/svg+xml`), `MAX_ROOM_UPLOAD_BYTES_SOFT`
  (100 MB), the path build/parse helpers, `buildUploadObjectId`, `checkUpload`,
  `atRoomUploadSoftCap`, `formatBytes`. The soft cap is documented as friction in the same
  words `MAX_ROOMS_SOFT` uses.
- **`packages/shared/src/store/upload-containment.test.ts` (new).** 30 tests. Two of them
  parse `firebase/storage.rules` and assert its size literal and content-type list match
  the TypeScript constants — a `.rules` file cannot import TypeScript, so the copies would
  otherwise drift silently.
- **`apps/web/src/lib/components/shell/AssetsActivity.svelte`.** The Uploads tab gains a
  real body when uploads are live: a per-room usage readout, a file picker gated by
  `checkUpload`, a listing with per-object size and a ✕ (disabled unless you uploaded it
  or are the GM). `uploads-disabled-note` is unchanged and is still what a Spark build
  renders — the tab decides by whether `assets.upload` exists, never by reading an env var.

_Deletion (§4)._

- **`packages/shared/src/store/asset-store.ts`.** `AssetStore` gains `listRoomUploads`,
  `deleteUpload` and `deleteRoomUploads`, and `upload` now takes `{ roomId, uid }` — the
  path shape is part of the boundary, so the store cannot build one without knowing the
  room. Added the free functions `listRoomUploadRefs` / `deleteRoomUploads`, kept free so
  `deleteRoom` does not depend on whichever `AssetStore` a build constructed. Enumeration
  is two levels: Storage has no recursive list and the uploads folder holds a prefix per
  uid. `FirebaseStorageAssetStore.listRoomUploads` also primes the resolve cache, so a
  room's existing uploads become resolvable in a fresh session.
- **`packages/shared/src/store/firebase-store.ts`.** `deleteRoom` sweeps the bucket in the
  same `Promise.all` as the Firestore subcollections, guarded on `client.storage` so it is
  a no-op on Spark.
- **`packages/shared/src/store/room-uploads.emulator.test.ts` (new).** Pins the sweep
  end-to-end against the emulator: a room's objects go, another room's stay, and the
  storage handle exists only when `storageUploads` is set.

_Wiring._

- **`packages/shared/src/firebase-config.ts`.** `FirebaseClientOptions.storageUploads`
  (default off) and an optional `FirebaseClient.storage`; `EmulatorPorts` gains
  `storage: 9199`.
- **`apps/web/src/lib/firebase/client.ts`.** Extracted a `getClient()` singleton and added
  `getUploadStorage()`. **`env.ts`** gains `storageUploads` from
  `VITE_ENABLE_STORAGE_UPLOADS` and a `storageBucket` in the Firebase config.
  **`assets.ts`** now decides by asking `getUploadStorage()` rather than re-reading the
  env var, so the upload path and the delete sweep cannot disagree.
- **`packages/shared/src/store/asset-store.test.ts`.** Reworked the `firebase/storage`
  mock into a path-keyed fake bucket so the room-scoped behaviour is testable.
- **`packages/shared/src/index.ts`.** Exports `upload-containment`.

**Visible behavior changes.** **None in any build that exists today.** Uploads stay off
unless `VITE_ENABLE_STORAGE_UPLOADS=true`, and the Assets → Uploads tab renders the same
disabled note it always did. With the flag on, that tab becomes a working uploader with a
usage readout; nothing else in the app changes either way.

**How to verify.**

- `pnpm verify:all` — lint, typecheck, and the full emulator battery.
- `pnpm test:rules` inside the emulator runs `storage.rules.test.ts` (26) beside the
  Firestore rules tests.
- The sweep: `pnpm --filter @osr-vtt/shared exec vitest run src/store/room-uploads.emulator.test.ts`
  inside `firebase emulators:exec`.
- The drift guard: `pnpm --filter @osr-vtt/shared exec vitest run src/store/upload-containment.test.ts`
  — edit the `5 * 1024 * 1024` in `firebase/storage.rules` and watch it fail.
- By hand: `VITE_ENABLE_STORAGE_UPLOADS=true pnpm dev` against the emulator, then Assets →
  Uploads. Without the flag, the same tab shows the disabled note.

**Deviations.**

1. **`AssetStore.upload`'s signature changed** — `upload(file)` → `upload(file, { roomId, uid })`.
   Unavoidable: SPEC-034 §2 makes the path shape part of the boundary, and a store cannot
   build `rooms/{roomId}/uploads/{uid}/…` without being told which. Nothing called it (the
   only implementation was disabled), so there was no migration. `AssetStore` is not part
   of `campaign-store.contract.ts`, so RULE-001's contract-suite requirement did not
   attach; the new members are covered by `asset-store.test.ts`.
2. **`storageBucket` added to the web Firebase config**, with a
   `${projectId}.appspot.com` fallback. Required to unblock the work: without it
   `getStorage()` throws `storage/no-default-bucket` and no upload can be made at all.
   Caught by the emulator test rather than by review.
3. **The Storage rules test pins its project id to `GCLOUD_PROJECT`** instead of inventing
   one the way `firestore.rules.test.ts` does. The Storage emulator resolves a
   cross-service `firestore.exists` against the project the _emulator_ was started with,
   not the bucket's, so an invented id puts the fixtures in one project and the rules in
   another. The failure mode is nasty enough to be worth the note in three places (the
   test, `README.md`, here): only the `assertSucceeds` cases fail, which reads exactly
   like a too-strict ruleset.
4. **A second emulator-backed unit test** (`room-uploads.emulator.test.ts`) now exists
   alongside `account-recovery.emulator.test.ts`, so `pnpm verify` without emulators
   reports two pre-existing-style failures rather than one. Judged worth it: §4 is a named
   spec section and nothing else proves `deleteRoom` actually calls the sweep.
5. **`getUploadStorage()` added to `client.ts`** rather than letting `assets.ts` call
   `getStorage()` itself, as it did before. Two independent readings of the same env var
   could disagree, and the disagreement that matters is "uploads on, sweep off" — objects
   nothing ever deletes, which is exactly what §4 exists to prevent.
6. **No new `[HUMAN]` work item was logged** for the console steps. SPEC-034 §3.3 asks for
   a _documented_ runbook, which is what shipped; the console work itself belongs to
   whoever decides to go to Blaze, and scheduling it would be a planning act outside this
   session's one work item (RULE-016).
