# WI-215 — An edit to a removed background is a quiet no-op

SPEC-059 §1, DEC-123. IN-067. Model `sonnet`, effort high.

## Changes made

- `packages/shared/src/store/firebase-store.ts` — `setBackgroundTransform`,
  `setBackgroundOrder` and `setBackgroundLocked` now share one private
  `patchBackground`, which wraps the `updateDoc` and treats a `not-found` rejection as
  success. `updateDoc` never creates a missing document, so nothing is resurrected; any
  other rejection (for example `permission-denied`) still propagates.
- `packages/shared/src/store/campaign-store.ts` — the no-op guarantee written on the
  doc comments of the three methods.
- `packages/shared/src/store/contract/room.contract.ts` — new contract test: add, remove,
  then each of the three writes resolves and the background stays absent (a later add is the
  barrier proving nothing was created). It runs against `MemoryStore`, `LocalStore` and
  `FirebaseStore` (RULE-001). `MemoryStore`/`LocalStore` needed no change: their
  `patchBackground` already returned on a missing document.
- `README.md` — "Background management" states the guarantee.
- `PLAN.md`, `PLAN-COMPLETED.md`, `INTAKE.md` — ledger close-out; IN-067 closed.

## Visible behavior changes

A GM whose background is removed by another client mid-drag sees the image disappear and
the release do nothing; the uncaught `NOT_FOUND` error in the console is gone. The same
applies to a Lock or restack click on a just-removed row. No schema, rules or
`data-testid` change.

## How to verify

- `pnpm verify` (docs, lint, typecheck, unit) — green.
- The contract test "a write to a removed background resolves without effect and creates
  nothing", run in the `memory`, `local` and `firebase` (emulator) store suites.
- By hand, two tabs as GM: start dragging a background in one, press Remove on it in the
  other, release the drag — no error, the image stays gone.
