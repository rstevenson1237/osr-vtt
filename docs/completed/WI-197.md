# WI-197 — Investigation: `session-config.spec.ts` Gate 6 CI flake

**Closed 2026-09-23.** From IN-150. **Investigation — findings only, no production code
changes** (RULE-015). Model target `sonnet`, run on `sonnet`; effort `medium`.

Traces the `ensureAuth()` → `subscribeRoom` gating chain behind Gate 6's first test
timing out on a second same-context GM tab (`gm2`) stuck on "Loading room…", per IN-150's
three candidate causes: a pure test-timeout tightening, CI-emulator latency with nothing
to fix in code, or a genuine multi-tab auth-restore race worth hardening.

---

## 1. The chain, as coded

`RoomShell.svelte`'s `onMount` (`RoomShell.svelte:244-246`):

```
myUid = await store.ensureAuth();
unsubs.push(store.subscribeRoom(roomId, (r) => (room = r)));
```

and the render gate (`RoomShell.svelte:552-553`):

```
{#if room === null}
  <p class="loading">Loading room…</p>
```

`room` starts `null` and stays `null` until `subscribeRoom`'s first snapshot arrives —
and `subscribeRoom` is never called until `ensureAuth()` resolves. The two steps are
strictly serial, and nothing between them is timed or logged: the visible "Loading
room…" state is identical whether the wait is 50 ms or a genuine hang. That is the same
gap IN-168 already names for a wrong room id; this investigation only confirms the same
undifferentiated state also covers this test's timeout window (`expect: { timeout: 8_000
}`, `playwright.config.ts:66`).

`gm2` (`session-config.spec.ts:59-61`) is a **new `Page`** in the GM's existing
`BrowserContext` — a fresh JS realm and a fresh `Auth`/`Firestore` client instance, even
though it shares the context's IndexedDB origin storage with `gm`. It does not go through
`signInAsReferee`'s seeding dance (`helpers.ts:513-603`); it relies entirely on
`FirebaseStore.ensureAuth()`'s normal restore path:

```
await this.client.auth.authStateReady();
const existing = this.client.auth.currentUser;
if (existing) return existing.uid;
```

(`firebase-store.ts:202-204`)

## 2. Whether the SDK's restore is genuinely slower for a second tab

Read against `@firebase/auth@1.13.3`'s `IndexedDBLocalPersistence`
(`node_modules/.../dist/esm/index-d90d2ee5.js:8223-8461`, the class the default
`getAuth(app)` picks): the initial read that `authStateReady()` waits on is `_get(key)` →
a single `getObject(db, key)` — one `IDBObjectStore.get()` request, resolved off its own
`success`/`error` events, with **no polling wait and no network round-trip**. The
`_POLLING_INTERVAL_MS = 800` cross-tab poll (`_poll()`, line 8390) exists to catch a
*later* write from another tab and only starts once a listener is registered
(`_addListener` → `startPolling()`); it plays no part in the *first* restore a fresh
`Auth` instance performs, which is exactly what `gm2`'s `onMount` triggers. `_openDb()`
opens `indexedDB.open(DB_NAME, DB_VERSION)` at a fixed version every tab shares, so there
is no version-upgrade block between `gm` and `gm2`'s connections either.

In other words: there is no mechanism in the persistence layer itself that would make a
second, same-context tab's `authStateReady()` routinely take seconds. **The
"genuine multi-tab auth-restore race" candidate IN-150 lists is not supported by the
code** — nothing here would need hardening in `ensureAuth()` or `RoomShell` even if it
were rewritten from scratch.

## 3. What the two known occurrences are more consistent with

- Both timeouts happened on **ordinary CI runs**, not a stress condition: `workers: 1`,
  `fullyParallel: false` (`playwright.config.ts:67-68`) mean this test never runs
  concurrently with another Playwright test, and both occurrences predate any evidence of
  shard-specific load (IN-150's own note: WI-143's sharding was silently broken both
  times, so each was "one ordinary shot at this test," same odds as before WI-143).
- `subscribeRoom` for `gm2` is not just a Firestore listener attach — it is a **cold**
  Firestore client for that page (its own WebChannel/gRPC handshake against the
  emulator), chained *after* the auth restore rather than in parallel with it. Even
  without a code defect, that is three uninstrumented, un-timed-out steps run serially
  (auth restore → listener attach → first snapshot round-trip) inside one fixed 8 s
  budget, on a CI runner also carrying the Vite dev server and three Firebase emulators.
  A CPU-contention spike hitting any one step is enough to blow the fixed budget without
  any step actually hanging.
- WI-143 (`retries` 2 → 1, SPEC-053 §2.3) is on record, in IN-150's own request text, as
  the change that removed the extra retry that used to paper over exactly this kind of
  occasional slow tick — it is not implicated as a new cause, only as the reason this
  flake became visible rather than silently retried away.

Nothing above points at a specific line to change in application code. It points at the
assertion's own budget: `expect(gm2.getByTestId('room-name')).toHaveText(...)` at
`session-config.spec.ts:61` uses the global 8 s default with no override, while this same
helpers file already treats "a second, same-context restore might be slower than the
common case" as expected and budgets for it explicitly elsewhere — `signInAsReferee`'s
own defensive wait uses `{ timeout: 15_000 }` (`helpers.ts:597,601`) for the equivalent
first-restore moment on the GM's *own* tab.

## 4. Finding logged

One new intake item, filed as this investigation's output:

- **IN-208** — give the `gm2` `room-name` assertion at `session-config.spec.ts:61` (and,
  for the same reason, the identical pattern at `session-config.spec.ts:144` in the Gate
  13 test) an explicit `{ timeout: 15_000 }`, matching `signInAsReferee`'s own budget for
  the same kind of restore-then-render wait, rather than the global 8 s default. Recommended
  **Simple** — a test-only timeout number, no production code, no testid, no contract
  touched.

No change is recommended to `ensureAuth()` or `RoomShell`'s gating order: §2 found no
code-level mechanism the SDK's own restore path would need hardening against, and
loosening the assertion's budget is enough to absorb the CI-latency explanation §3
supports.
