# WI-093 — Numeral orientation: the axis-projection + symmetry-snap rule

**Spec:** SPEC-045 §1 · **From:** IN-079 · **Model:** `opus` · **Effort:** M ·
**Closed:** 2026-09-02

Replaces SPEC-020 §5's first-edge rule (`pts[0]→pts[1]`), whose answer came from the order
a hand-written vertex-index table happened to carry, with a rule that depends on the face's
geometry alone. Per DEC-078.

## Changes made

- **`apps/web/src/lib/dice/geometry.ts`**
  - New exported pure function **`faceGlyphUp(pts, normal)`** — the rule. (1) Project the
    die-local `+Y` axis (`GLYPH_REF_AXIS`, the same axis `topFaceIndex` scans) into the face
    plane; fall back to `+X` when the normal is parallel to it. (2) Build the candidate
    directions the face admits — centroid→corner for triangles and pentagons, centroid→edge-
    midpoint for the d6's squares. (3) **Snap:** take the candidate with the greatest dot
    product against the projected axis. An exact tie (a face symmetric about that axis) breaks
    on the in-plane `right = n × up₀`, so the answer never depends on the order the corners
    arrived in.
  - `buildDieGeometry`'s per-face basis block: the `if (faceUp) … else edge` fork collapses to
    `vAxis = override ?? faceGlyphUp(pts, normal)`, with `uAxis = vAxis × n` unchanged for both
    paths (this is what the old code already did on each branch).
  - `Polyhedron.faceUp` doc comment rewritten: it is no longer "an exemption the d10 needs"
    but the declared **override**, applied as given, without the snap.
  - `pentagonalTrapezohedron`'s comment restated against the new rule — a kite offers neither a
    corner nor an edge midpoint on its symmetry axis, which is why it declares its own.
- **`apps/web/src/lib/dice/geometry.test.ts`** — three new `it.each` blocks, plus a `facesOf`
  helper that recovers each face's corners in winding order from the built geometry (fan order
  `[0,1,2] [0,2,3] …`):
  - **The binding test (SPEC-045 §1):** for every shape and every face, all cyclic rotations of
    the corner list give the same `faceGlyphUp` (within 1e-9).
  - d8/d12/d20: exactly one corner of each face sits directly above the centre of the number
    square (`|u − 0.5| < 1e-6`, `v > 0.5`) — the numeral's apex points at a corner.
  - d6/d8/d12/d20: no face's glyph-up leans off the shared `+Y` reference by more than half the
    angle between adjacent candidates (45° / 60° / 36° / 60°) — one family, one axis.
- **`README.md`** § "Dice (II.6)" — the "d10 is exempt from the edge-aligned UV rule" bullet is
  replaced by two: the family rule and its index-order-independence guarantee, then the d10
  bullet restated around `faceUp` as the declared override.
- **`PLAN.md` / `PLAN-COMPLETED.md` / `INTAKE.md`** — ledger moves.

`SPEC-020.md`'s supersession annotation and `docs/decisions/DEC-078.md` were written at the
gate and needed no change here.

## Visible behavior changes

The numerals on the d4, d6, d8, d12 and d20 change rotation within their faces. They now share
one reference axis per die, giving the pole-to-pole swirl a machined die has, in place of a
per-face rotation that fell out of table winding. The d10 is unchanged — it already overrode
the old rule and overrides the new one identically.

**Nothing else moves.** Face count, material groups, `locators`, `hullPoints`, the face→value
remap and `topFaceIndex` are untouched, so the value a die displays cannot change (RULE-013 is
satisfied by construction: the headless sim still runs first and the remap is applied to its
result). No schema, no store method, no security rule, no `data-testid`.

## How to verify

- `pnpm verify` — lint, typecheck and the unit suites. `apps/web` is 430/430 green, including
  the three new orientation tests and the two pre-existing ones this rule had to keep green:
  the d6 axis-aligned UV square and "points every d10 numeral's top at its own kite's apex".
- The binding test alone: `cd apps/web && pnpm exec vitest run src/lib/dice/geometry.test.ts`.
- By eye: `docs/mockups/dice-preview.html`, or roll each die type in the app — every numeral on
  a die should read the same way up relative to the die's own `+Y`, and each triangular or
  pentagonal numeral should point its apex at a corner.

## Deviations

- **A tie-break the spec did not name.** Step 3's "greatest dot product" is ambiguous on a face
  symmetric about the projected axis, and an ambiguity resolved by candidate order would fail
  the binding test — the exact defect being fixed. Ties (within 1e-9) therefore break on the
  in-plane `right` vector, which is itself order-independent. This narrows the rule rather than
  changing it; the d12 test confirms the case is real (its faces sit exactly on the 36° bound).
- **The candidate set is keyed on corner count** (`pts.length === 4` → edge midpoints), not on a
  "is this the d6" test. The d6 is the only shape whose quadrilateral faces reach the rule; the
  d10's kites take the override.
- **Two emulator tests fail in this sandbox**, both pre-existing and unrelated:
  `packages/shared/src/store/{account-recovery,room-uploads}.emulator.test.ts` fail with
  `auth/network-request-failed` when no emulator is running. Confirmed identical on a stashed
  (unmodified) tree.
