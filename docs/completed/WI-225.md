# WI-225 — A stale tab against a newer live room

**Closed 2026-10-12.** From IN-227. **Investigation — findings only, no production code
changes** (DEC-027, RULE-015). Model target `opus`, run on `opus`; effort `high`.

Built by reading `packages/shared/src/converters.ts`, `migrations/index.ts`, `schemas.ts`
(`RoomSchema` and the schemas it nests), every write method in `store/firebase-store.ts`,
`firebase/firestore.rules` for who may write each document, and the `RoomShell.svelte` /
`CombatTracker.svelte` call sites that drive writes without a user action. Line numbers are
from `main` at `5b77085`, where `CURRENT_SCHEMA_VERSION = 35`.

**The short answer is yes.** A tab left open across a deploy keeps writing, and about a
dozen of its write paths send a whole object rebuilt from what its own schemas let through.
Any field a newer build added inside such an object is deleted from the live room by the
next write, and in one case (hex tiles) the whole document is deleted. Nothing in the
current code notices that the room is newer.

---

## 1. Why the stale tab sees a stripped room

`roomConverter.fromFirestore` (`converters.ts:70-76`) runs the raw doc through
`migrateRoom`, then `RoomSchema.omit({ id: true }).parse`. On a doc whose `schemaVersion`
is at or above this build's, `migrateRoom` returns its input unchanged (the `while` loop at
`migrations/index.ts:1110` never runs). `RoomSchema` and every schema it nests are plain
`z.object`s, which **strip** unknown keys at every depth. Every other converter
(`GameMap`, `Token`, `Encounter`, `MapRoom`, walls, doors, macros, tables, …) does the
same, and each `toFirestore` parses again on the way out, so a converted write strips even
if the caller somehow held the extra keys.

Reading a stripped room is harmless in itself. What matters is which writes send the
stripped copy back.

## 2. Write paths, classified

Rules decide who can reach each path: the room doc, map docs, groups and the encounter are
GM-write (`firestore.rules:62`, `:113`, `:120`); seats, profiles and macros are
member-writable.

### 2.1 Destroys newer data: whole objects rebuilt from a stripped read

| Path                                                                                                                                                                                                                                 | Writes                                                                                             | What a newer build's field loses                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `updateProfileTemplate` (`firebase-store.ts:1581`)                                                                                                                                                                                   | the whole `profileTemplate` array                                                                  | any per-field key the editor did not know, on **every** field, on any template edit                                                                                                                  |
| `updateEncounterTemplate` (`:1586`)                                                                                                                                                                                                  | the whole `encounterTemplate` array                                                                | the same, for encounter fields                                                                                                                                                                       |
| `setRollConventions` (`:546`)                                                                                                                                                                                                        | the whole `rollConventions` array                                                                  | any key inside a convention, its `applies` or its bands                                                                                                                                              |
| `writeEncounter` (`:1353`)                                                                                                                                                                                                           | `setDoc` of the whole `encounter/current` doc, no merge                                            | any encounter or combatant key. `CombatTracker.svelte:166-187` writes it **unattended**: the GM-only reconciliation effect fires when a group's `[Active]` flag changes, which a newer tab can cause |
| `setMapMeasurement` (`:1128`), `setMapGridDimensions` (`:954`)                                                                                                                                                                       | the whole `measure` / `grid` sub-object, from the map the UI holds                                 | any key a newer build adds inside them                                                                                                                                                               |
| `upsertMapRoom` (`:1388`), `setWall`/`setWalls` (`:1472`), `setDoor` (`:1504`), `writeDrawing` (`:1549`), `placeSymbol` (`:1368`), `saveMacro` (`:1818`), `upsertTable` (`:1836`), `commitFloorRegions`/`commitFogRegions` (`:1408`) | `collectionOf(...).set` or `.batch` → `setDoc` of the whole doc through its converter (`:255-271`) | any key on that doc, whenever the stale tab edits an existing one                                                                                                                                    |
| `createBattleMap` (`:666`)                                                                                                                                                                                                           | a new map doc copied from the **converted** source map                                             | every newer map-level key, in the copy only. The sub-collections are copied raw (`d.data()`) and survive                                                                                             |

### 2.2 Destroys newer data even without a read

`setMapGridSubdivide` (`:1136`), `setMapFogEnabled` (`:1454`) and `setMapBackgroundColor`
(`:723`) replace a whole sub-object built from one key (`gridSettings: { subdivide }`,
`fog: { enabled }`, `background: { color }`). They would drop a sibling key a newer build
added even if the read path kept it. `setTheme`, `setInitiativeConfig` and
`setDefaultPlayerGroup` show the safe form: dotted paths, so they touch one key each
(`:530-557`).

### 2.3 Deletes a document

`patchHexTile` (`:1047`) and `setHexesRevealed` (`:1003`) read a tile inside a
transaction, rebuild it from four known fields (`terrain`, `contents`, `note`,
`revealed`), and **delete the document** when none of the four is set. A tile whose only
content is a field a newer build added (a hex marker, say) is deleted by a stale tab
clearing a terrain the tile never had, or by fogging it. Every other case rewrites the
tile without the field.

### 2.4 Safe

- **Scalars and dotted paths on the room doc:** `renameRoom`, `setActiveMap`, `setTheme`,
  `setInitiativeConfig`, `setDefaultPlayerGroup`, `transferGM`, `touchRoomActivity`.
- **Profiles:** `setDoc(…, { merge: true })` patches of `{ values: { [fieldId]: v } }`
  deep-merge, so unknown keys on the doc survive.
- **Per-field token and group updates** (`moveToken`, `setTokenSize`, … ; `updateGroup`):
  `updateDoc` of named keys only.
- **Creation writes** (`createToken`, `createGroup`, `addBackground`, `addHexLine`, log
  and roll entries): new docs, so nothing to lose.
- **The collection ledger:** `migrateRoomCollections` (`:934`) returns early when the stamp
  is not behind, and `collectionsNeedMigration` (`migrations/index.ts:794`) treats a stamp
  **ahead** of this build as not behind, so a stale GM tab never re-runs or down-stamps it.
- **Yjs notes:** since WI-223 the transport ships the edit, not the document, and a Yjs doc
  keeps structure it does not understand.
- **`joinRoom`** (`:1144`) rewrites the seat whole, but only from the join gate, which a
  seated tab never shows.
- **The local build:** a newer `.vttcamp` is refused at open (SPEC-062), so there is no
  stale-tab case.

## 3. What a tab can use to detect a newer room

| Signal                       | Where                                                                                                                                                   | Usable?                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `room.schemaVersion`         | written once, by `createRoom` (`:351`) and `importRoom`; nothing re-stamps it                                                                           | **Only for rooms created or imported by the newer build.** A room created at v30 and opened by every build since still stores `30`. Re-stamping it would be wrong, not just a fix: the stored doc _is_ still in its v30 shape, and every reader relies on `migrateRoom` walking it forward from 30 on each read. A re-stamp would skip those steps |
| `room.collectionsMigratedTo` | written to `CURRENT_SCHEMA_VERSION` by the GM tab of every build whose version is above the stamp (`RoomShell.svelte:383-386`, `firebase-store.ts:948`) | **Yes: it is the high-water mark of the newest build whose referee has opened the room.** Every schema bump makes the stamp fall behind, so a newer GM tab always writes it. It is in `RoomSchema`, so the stale tab already receives it in `subscribeRoom`                                                                                        |
| The deployed build's version | `VITE_APP_VERSION`                                                                                                                                      | **Not today.** Only `release-local.yml` sets it; the hosted deploy builds with the literal `'dev'` (`vite.config.ts:31`), so two hosted builds cannot be told apart by version                                                                                                                                                                     |

So `max(room.schemaVersion, room.collectionsMigratedTo ?? 0) > CURRENT_SCHEMA_VERSION` is
a correct "a newer build has been here" test, computable from the parsed `Room` with no
read-path change. Two gaps remain:

1. **A newer player, no newer referee yet.** Room writes are GM-only, so a newer _player_
   tab never stamps. Until a newer referee opens the room, a stale GM tab has no signal.
   The rules let any member write the map sub-collections, but the tools that rewrite
   walls, doors, regions, map rooms and hex tiles are referee tools in the UI, so the
   newer-shaped data a player can create in that window is mostly their own macros and new
   drawings. That UI gating was not traced tool by tool here; treat it as inferred.
2. **A newer build whose room doc no longer parses** (§4). Then the test above never runs,
   because the parse throws before any `Room` exists.

## 4. When the parse fails, the stale tab freezes and keeps writing

If a newer build changes a room field's type or makes a new one required, `RoomSchema.parse`
throws inside `fromFirestore`. `subscribeRoom` (`:383-385`) calls `snap.data()` inside the
`onSnapshot` callback, and the Firestore SDK runs that callback in a `setTimeout`
(`@firebase/firestore` 4.16.0, `__PRIVATE_AsyncObserver.mc`), so the throw becomes an
uncaught error in a timer. The listener is not muted. `RoomShell`'s `room` keeps the last
value that did parse, and every later snapshot throws the same way.

The tab shows no error. It goes on rendering a frozen room and writing from it, through
every path in §2.1 to §2.3. The same holds for every converted collection subscription: a
single doc that fails its schema takes the whole snapshot with it (the comment above
`ProfileInstanceSchema.values` records this for profiles). A detection check that lives
after the parse cannot see this case. It has to run on the raw doc, inside
`fromFirestore`, before `migrateRoom` and the parse, which is a change to the room read
path.

## 5. Options for the fix

| Option                                                                                                                                          | Stops the loss?                                                                                                  | Cost                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **(a) Reload prompt**: a banner, writes stay enabled                                                                                            | **No.** The data loss happens on the next write, which the banner does not prevent                               | Smallest                                                                                                                                                                                     |
| **(b) Read-only**: the room stays on screen and every write is refused                                                                          | Yes                                                                                                              | A guard on every write method in three stores (a `CampaignStore` guarantee, RULE-001), and every control that writes must cope with a refusal. UI that half-works is worse than a clear stop |
| **(c) Hard stop**: the room view is replaced by "This room was updated by a newer version of the app. Reload to continue." with a Reload button | **Yes.** Every write path in §2 is reached from inside the room view, so unmounting it stops all of them at once | One check, one panel, one additive `data-testid`                                                                                                                                             |
| (d) Make writes non-destructive: `.passthrough()` schemas, dotted paths, merges                                                                 | Partly                                                                                                           | Cannot fix the array fields (`profileTemplate` items, encounter `order`), changes every converter's contract, and does nothing for §4                                                        |

## 6. Recommendation for the fix's own gate

**(c), the hard stop, with the check run on the raw room doc before the parse.** Concretely:

- `roomConverter.fromFirestore` reads `schemaVersion` and `collectionsMigratedTo` from the
  raw doc first. When either is above `CURRENT_SCHEMA_VERSION` it returns a marked result
  instead of migrating and parsing, so `subscribeRoom` can deliver a distinct "newer room"
  state. That changes what `subscribeRoom` may deliver, so it is a `CampaignStore` contract
  change (RULE-001) with a case in the contract suite: `MemoryStore` and `LocalStore` hold
  only rooms their own build wrote, and pass trivially.
- `RoomShell` renders the stop panel in place of the room for that state. The message
  follows SPEC-062 §2 ("made by a newer version … update before opening it").
- The panel's text should not promise a version name until IN-233 lands.

That fix is **Deceptive** (the room read path and a store guarantee) and needs its own
design pass, DEC and spec, as this item's block in `PLAN.md` said. It covers IN-229,
IN-230, IN-231 and IN-232 together.

**The main alternative** is a check in `RoomShell` alone, on the parsed `Room`, using the
§3 test. It changes no contract and catches every additive change, which is how every
schema bump so far has been shaped. It does not catch §4. It is a reasonable first step if
the read-path change waits.
