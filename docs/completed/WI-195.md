# WI-195 — Portrait images in Firestore

SPEC-057 §6, DEC-119. Single unit (Shape A). IN-187. Model `opus`, effort xhigh.

## Changes made

- `packages/shared/src/types.ts` — `RoomImage` (`{ id, bytes, mime: 'image/webp', w, h, by }`);
  `CURRENT_SCHEMA_VERSION` 33 → **34**.
- `packages/shared/src/store/room-images.ts` (new) — `ROOM_IMAGE_MIME`,
  `MAX_ROOM_IMAGE_DIMENSION` (256), `MAX_ROOM_IMAGE_BASE64_CHARS` (100,000); `roomImageRef`,
  `parseRoomImageRef`, `roomImageDataUrl`; `checkRoomImage` (friction mirroring the rules).
  Exported from `index.ts`.
- `packages/shared/src/schemas.ts` — `RoomImageSchema` (strict, same bounds as the rules);
  `converters.ts` — `roomImageConverter`.
- `packages/shared/src/store/campaign-store.ts` — `CollabStore` gains `subscribeImages`,
  `putImage` (stamps `by` with the caller's uid; resolves to the id) and `deleteImage`;
  `images` joins `EXPORTED_COLLECTIONS`, so export, import and `deleteRoom` cover it.
- `memory-store.ts` — an `images` bucket and the three methods; `putImage` parses through
  `RoomImageSchema` so it refuses what `FirebaseStore`'s converter refuses. `LocalStore`
  inherits them, and its file carries the images.
- `firebase-store.ts` — the three methods over `collectionOf`; `importRoom` writes `images`
  in batches of 50 (`IMAGE_BATCH_LIMIT`), since 500 documents of up to ~100 KB would exceed
  a commit request's 10 MiB limit.
- `migrations/index.ts` — the v33→v34 step: room-doc no-op, no ledger entry.
- `firebase/firestore.rules` — an `isRoomImage` function and a `match /images/{imageId}`
  block: read `signedIn()`; create = containment and (member with `by == uid`, or the GM);
  update = containment, `by` unchanged, creator or GM; delete = creator or GM.
- Tests: `rules/firestore.rules.test.ts` (12 cases: read, member/GM create, non-member and
  unauthenticated denied, forged `by`, GM import-create, mime, dimensions, the 100,000/100,001
  bytes edge, key set, update, cross-member denial, delete); `store/room-images.test.ts`
  (parses `firestore.rules` and asserts the three constants agree; ref helpers;
  `checkRoomImage`); `contract/collab.contract.ts` (put/see/delete across clients, referee
  delete, bounds refused in every store, export/import round-trip) and
  `contract/listeners.contract.ts` (`subscribeImages`) — both run against `MemoryStore`,
  `FirebaseStore` and `LocalStore`; `portability/vttcamp.test.ts` (images and the `img:` refs
  naming them round-trip identically); `store/local-store.test.ts` (an image survives close
  and reopen of the campaign file); `migrations/index.test.ts` (v33→v34).
- `apps/web/src/lib/room-images.svelte.ts` (new) — `RoomImageAssets`, an `AssetStore` that
  subscribes to the room's images and resolves `img:<id>` to a `data:` URL (a transparent
  placeholder until it arrives or after deletion), delegating every other ref and the
  optional upload members to the build's own store. Tested in `room-images.svelte.test.ts`.
- `apps/web/src/lib/image-resize.ts` (new) — `fitWithin` and `resizeToWebp` (canvas, at
  most 256×256, WebP at falling quality until under the bytes bound; errors a user can read).
- `RoomShell.svelte` — provides `RoomImageAssets` under `ASSET_STORE_KEY` for the room and
  disposes it on destroy.
- `VectorMapView.svelte` — the token texture gate keys an `img:` ref with what it currently
  resolves to, and the sync effect reads it, so a token redraws when its image arrives.
- `TokenPickerDialog.svelte` — an **Images** tab: add from device (resized, then
  `putImage`), a grid of the room's images, remove for the creator or the referee, and a
  note that no room-wide limit is enforced.
- `apps/web/tests/e2e/portrait-images.spec.ts` (new) — picks a PNG in the Images tab, asserts
  it is stored as WebP, and places it as a creature with no broken-image badge.
- Docs: `README.md` ("Portrait images in Firestore" under II.7; v34 in the schema history),
  `docs/spec/SPEC-057.md` (§6 implementation note), `PLAN.md`, `PLAN-COMPLETED.md`,
  `INTAKE.md`.

## Visible behavior changes

- The token picker (Add creature, My token) has a fourth tab, **Images**. A picked file is
  shrunk to at most 256×256, stored in the room, and usable as a token image or portrait by
  everyone at the table, in hosted and local builds alike. The creator or the referee sees a
  × to remove one.
- A `.vttcamp` exported from a room with images now carries them, and imports them back.
- Rooms are created at schema v34; an existing room re-stamps on the referee's next open.
- New testids: `token-picker-tab-images`, `token-picker-image-input`,
  `token-picker-image-error`, `token-picker-images-empty`, `asset-option-image-{id}`,
  `token-picker-image-delete-{id}`. No existing testid moved.

## Deviations

- **Schema bump to v34.** The work item did not name one; RULE-007 asks for a migration on
  any store schema change, and the v28→v29 precedent (a new collection, a no-op step) is
  followed exactly.
- **The referee may create an image under any `by`.** SPEC-057 §6 lists
  `by == request.auth.uid` for create. A `.vttcamp` import into `FirebaseStore` is written by
  the referee and restores each image's original writer, which that rule would deny; the
  `macros` block admits the GM for the same reason. The containment bounds still bind the
  referee. Covered by "lets the GM create under another uid" in `firestore.rules.test.ts`;
  recorded in SPEC-057 §6.
- **The RULE-004 stop condition was read as not triggered.** The bounds are RULE-010 §1's
  per-write containment — content type, size, path shape, membership, which that rule names —
  and hide no information; `storage.rules` has carried the same kind under RULE-004 since
  SPEC-034. The only guard beyond containment is the own-uid `by` check, which is the
  `macros` pattern. No `RULES.md` amendment was made.
- No Deviations-budget fixes, no unblocking changes.
