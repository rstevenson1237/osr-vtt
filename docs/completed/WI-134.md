# WI-134 — A side's initiative slot is keyed `side:{groupId}`

**Spec:** SPEC-050 §1 · **From:** IN-130 (via DEC-096 (a)) · **Model:** `opus` · **Closed:** 2026-09-16

## Changes made

- **`packages/shared/src/types.ts`** — the slot-id encoding gains its third shape.
  `SIDE_SLOT_PREFIX = 'side'` (a reserved literal, not a free string), `sideSlotId(groupId)`
  → `side:{groupId}`, `isSideSlotId(slotId)` and `sideSlotGroupId(slotId)`, all beside
  `characterSlotId` so the encoding keeps one home. `slotOwnerUid` now returns
  `string | null` and answers **`null`** for a side slot — `side` is never read as a uid —
  and `slotTokenId` answers `null` for one, because a groupId is not a tokenId. The
  `SharedRoll.slots` doc comment states the three shapes exhaustively.
- **`packages/shared/src/encounter/initiative-call.ts`** — `initiativeSlotId`'s side branch
  returns `sideSlotId(actor.refId)` instead of the bare `refId`. One slot per side, whoever
  stages it: the id belongs to the side, so a side holding two player-owned tokens still
  yields one number and needs no tie-break.
- **`packages/shared/src/encounter/initiative.ts`** — `applySharedRollToInitiative`'s side
  branch looks up `side:{refId}` first, then the bare `refId`. The bare fallback is kept
  deliberately: `SharedRollReadiness`'s referee-only arbitrary-slot control stages whatever id
  it is handed, including a bare groupId for an ordinary (non-initiative) shared roll that is
  applied to the tracker later.
- **`apps/web/src/lib/dice/roll-or-stage.ts`** — `stageTargetFor` returns the slot
  unconditionally when `slotOwnerUid` is `null` (a side slot): any room member may fill it,
  and the first to press a die does. The owner gate is otherwise unchanged, so Individual
  mode still refuses a die pressed for a character someone else owns.
- **`apps/web/src/lib/components/EncounterBoard.svelte`** — `groupReady` reads
  `slots[sideSlotId(groupId)]`; `isReady` needed no change, since it goes through
  `initiativeSlotId`. `sideSlotId` added to the shared import.
- **`firebase/firestore.rules`** — `sharedRoll/current/slots/{slotId}` gains one clause:
  `isMember(roomId) && slotId.split(':')[0] == 'side'`, alongside the existing own-uid-prefix
  clause. Still a pure string comparison — no billed `get()`. The comment records why a bare
  groupId could not be admitted instead: it is indistinguishable from another member's uid, so
  admitting it would hand every member every other member's slot.
- **`packages/shared/src/rules/firestore.rules.test.ts`** — five new cases in the slots
  describe (RULE-004): a member may write `side:party`; a second member may write the same
  side's slot (seeded as a member in the test, since the fixture seats only one player); a
  non-member may not; a **bare** `party` is denied; and `{otherUid}:side` is denied — the
  prefix is what is admitted, not "contains `side` somewhere". The pre-existing cases —
  another member's bare-uid slot denied, the GM may write any slot — are unchanged and still
  pass.
- **`packages/shared/src/slot-id.test.ts`** (new) — the three shapes build correctly, a side
  slot is recognised only by its prefix (`u1:side` is not one), `sideSlotGroupId` round-trips,
  `slotOwnerUid` never reads `side` as a uid, `slotTokenId` never reads a groupId as a tokenId.
- **`apps/web/src/lib/dice/roll-or-stage.test.ts`** (new) — `initiativeCallOpen`, and
  `stageTargetFor`: no call ⇒ roll; no actor ⇒ roll; a player stages their own side (the
  IN-130 fix); any member may fill a side slot; Individual mode stays owner-gated.
- **`packages/shared/src/encounter/initiative-call.test.ts`** — the side case now expects
  `side:party`, plus a case pinning that two different `ownerUid`s produce the same slot id.
- **`packages/shared/src/encounter/initiative.test.ts`** — the side-mode apply case now stages
  `side:{groupId}` parts, plus cases for the bare-groupId fallback and for `side:` winning
  when both are present.
- **`README.md`** → "Shared rolls" / "Call for Initiative" — the one-line Individual-mode
  sentence is replaced by the three exhaustive slot shapes, who may write each, why `side` is
  a literal, and where the helpers live (RULE-018).
- **`PLAN.md` / `PLAN-COMPLETED.md` / `INTAKE.md`** — ledger moves.

## Visible behavior changes

- **A player can stage their own side's initiative.** In side mode — the default — pressing a
  card's die during a Call for Initiative writes `side:{groupId}` and is now permitted; before
  it wrote `slots/{groupId}` and Security Rules denied it, so the press did nothing.
- A side's READY overlay lights for whichever member staged it, and a side yields exactly one
  number on resolve however many players own tokens in it.
- Nothing else moves: no testid changed (RULE-005), no schema changed, nothing is migrated
  (`sharedRoll/current` is transient and `openSharedRoll` clears it on every call, so
  RULE-007 is not engaged).

## How to verify

- `pnpm verify` — lint, typecheck, unit. `pnpm verify:all` adds the rule tests, the store
  contract suite and Playwright against the emulator.
- The rule clause specifically: `pnpm exec node scripts/firebase-emulators.mjs exec --project
  osr-vtt "pnpm test:rules"`, and look for "lets a member write a side:{groupId} slot".
- In the app: as referee, create two active groups, press **Call for Initiative** in side
  mode, then as a player press a die on a card belonging to one of those groups — the card
  shows READY instead of silently failing.

## Deviations

- **One test rewritten mid-run.** The first draft of "a member may write another side's slot"
  authenticated as `OTHER_PLAYER_UID`, who the shared fixture never seats in the room, so it
  failed on membership rather than on the clause under test. It now seeds that player and
  asserts the real claim — a *second member* may write the same side's slot.
- **The full Playwright sweep did not run locally.** The 99-test suite runs far slower than
  the sandbox's budget allows (about 12 tests in ten minutes), and an early attempt lost its
  dev server mid-run. What did run green locally against the emulator: the rule suite, the
  store contract suite, and the four e2e specs that exercise this path —
  `shared-roll.spec.ts` (including "Call for Initiative fills the tracker rows automatically
  (side mode)"), `encounter.spec.ts` and `combat-modes.spec.ts`. The full sweep runs in CI.
- **`applySharedRollToInitiative` keeps the bare-groupId lookup** as a second candidate. SPEC-050
  §1 says the side branch looks up `side:{refId}`; dropping the bare id outright would have
  broken the referee's existing arbitrary-slot staging in `SharedRollReadiness`, which is
  documented behaviour and outside this item's scope. Both are pinned by tests, `side:` first.
