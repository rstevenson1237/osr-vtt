# WI-174 — Investigation: Yjs transport cost

**From:** IN-177 · **Spec:** — · **Model:** `sonnet` · **Effort:** medium · **Closed:** 2026-09-23

Investigation only — no code changes. The question (INT-AR-05): what does it cost, at
roughly 50 KB of stored Yjs state and 10 edits/second, that "Yjs state is one RTDB node
rewritten whole on every edit"?

## Changes made

No code changes — this work item is an investigation. Findings are logged as new intake
items (below) rather than implemented directly, per the pattern set by WI-171/WI-173.

**Read:** `apps/web/src/lib/collab/yprovider.ts` (`YRoomProvider` — the only place a
`Y.Doc` is wired to `CampaignStore`), `apps/web/src/lib/collab/room-notes.svelte.ts` (the
one shared `room-notes` doc every map room's notes lives in), `apps/web/src/lib/collab/
text-diff.ts` (`applyTextDiff` — the minimal-diff editor into `Y.Text`),
`apps/web/src/lib/components/MarkdownEditor.svelte` (`oninput={emit}` — undebounced,
fires on every keystroke), and `packages/shared/src/store/firebase-store.ts`'s
`subscribeYState`/`mergeYUpdate`/`getYState` (the RTDB transport itself).

**Traced the path an edit takes:**

1. A keystroke fires `MarkdownEditor`'s `oninput` immediately — no debounce.
2. `RoomNotesDoc.set()` runs `applyTextDiff` inside one `doc.transact()`, so the local
   Yjs update is genuinely small: a common-prefix/common-suffix diff, typically single
   digits to low tens of bytes for one keystroke.
3. `YRoomProvider.handleLocalUpdate` hands that small update straight to
   `store.mergeYUpdate(roomId, docName, update)` — one call per keystroke, no batching.
4. `FirebaseStore.mergeYUpdate` runs an RTDB `runTransaction` at
   `rooms/{roomId}/yjs/{docName}`: it reads whatever base64 blob is currently stored,
   decodes it, calls Yjs's `mergeUpdates([current, update])`, and writes the result back
   as one base64 string. `mergeUpdates` returns a **compacted encoding of the full
   combined state**, not a concatenation of history — so its size tracks the size of the
   document's content, not the number of edits ever made. But that also means the value
   written back is (to a first approximation) the *entire* `room-notes` doc — every map
   room's notes, since they all live in one shared `Y.Doc` — not just the one room's
   changed text.
5. Every client's `subscribeYState` listener is a plain `onValue` on that same node. RTDB
   pushes the **entire new node value** to every listener on every write — there is no
   partial/delta read on an RTDB value listener. `Y.applyUpdate` on the receiving end is
   idempotent (a Yjs update doubles as a full-state encoding Yjs can apply directly), so
   correctness holds, but every subscriber — including the editing client's own listener,
   which receives its own write back — downloads the whole blob on every keystroke.

**The gap.** Step 2's local update is tiny (an edit's worth of bytes). Steps 4–5 turn
that into a write and a broadcast sized to the *whole shared document*, not the edit.
At the stated **50 KB** of raw Yjs state (~67 KB once base64-encoded, RTDB has no binary
type — see `bytesToBase64`/`base64ToBytes`), **10 edits/second** — sustained fast typing,
or a paste that `applyTextDiff` still turns into one transaction — means:

- **~670 KB/s** uploaded by the typing client (one ~67 KB transaction write per edit).
- **~670 KB/s downloaded by every other subscriber** to that room's `room-notes` doc —
  the referee and each player's browser context all hold their own `subscribeYState`
  listener (one shared doc, one subscription each, per the design note in `README.md`
  §"Room quick sheet & players' notes"). A 4-seat room sustaining that typing rate is
  **~2.7 MB/s** of RTDB egress for one editor's Notes typing alone, and it scales with
  seats, not with the size of the actual edit.
- The **payload actually needed** per keystroke — the diff `applyTextDiff` computed — is
  on the order of tens of bytes. The observed transport cost is roughly **three orders of
  magnitude larger** than the edit it carries, because the transport always ships full
  state rather than the update that triggered it.

10 edits/second sustained for a full session is not the common case, but two things push
toward it in practice: (a) the shared `room-notes` doc means *any* room's notes editor on
*any* seat adds to the same write stream, so concurrent note-taking across a dungeon
compounds rather than staying per-room; (b) a paste of any size still collapses to one
`applyTextDiff` transaction, so it costs the same one round trip as a keystroke — the
transport cost is per-*edit-event*, not per-character, until the doc itself grows. RTDB
is not billed per-write on Spark (README §II.8), but Spark's RTDB plan does cap monthly
egress — sustaining the rate above for any real stretch of session time is worth checking
against the current Firebase Spark quota page rather than assuming headroom; this
investigation did not fetch that page and does not assert a number that could be stale.

**Two findings, logged as new intake items** (`INTAKE.md` §1.1) rather than implemented
here, per RULE-016 — this session's unit is the investigation, not a fix:

- **IN-209** (proposed Simple) — coalesce local Yjs updates before merging: buffer
  `handleLocalUpdate`'s output for a short idle window before calling `mergeYUpdate`,
  cutting the number of RTDB write/broadcast round trips during a typing burst without
  touching the RTDB path shape, the merge semantics, or any store-contract signature.
- **IN-210** (proposed Deceptive) — stop broadcasting the full merged doc state on every
  edit: change what `rooms/{roomId}/yjs/{docName}` holds (or add a second path) so a
  listener can receive an incremental update instead of the whole document, with periodic
  compaction. This changes the shape of what a `CampaignStore` write does at that path
  (RULE-003) and plausibly the `subscribeYState`/`mergeYUpdate` contract (RULE-001), so it
  is Deceptive rather than Simple, and belongs at its own gate.
