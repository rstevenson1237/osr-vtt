#### WI-104 — The `hex` snap mode and the authored hex palette

**Spec:** SPEC-047 §3 (annotated). **From:** IN-088, IN-090. **Model:** `sonnet`.

**Changes made.**

- `packages/shared/src/map/vector/snap.ts` — `VectorSnapMode` grows a fourth member,
  `'hex'`: `'free' | 'full' | 'half' | 'hex'`. A doc comment states why the square-lattice
  functions in this file (`snapPoint`, `snapCell`, `snapCellCenter`, `snapAngle`,
  `snapSpan`, `snapScalar`) never actually see it: a hex map's own tools resolve `'hex'`
  through `hexMap.snapHexPoint` (SPEC-047 §1) instead, and RULE-006 forbids a
  square-lattice consumer being reached from a hex map. The member exists so the one
  exhaustive `Record<VectorSnapMode, …>` in the codebase has to answer for it.
- `apps/web/src/lib/shell/map-tool-controller.svelte.ts` — `DEFAULT_BAND_WIDTH` gains a
  `hex: 2` entry, with a comment noting the value is never read for a real band (neither
  Corridor nor Path is a hex tool) — it exists only so the `Record` compiles.
- `apps/web/src/lib/map/tool-groups.ts` — `HEX_TOOL_IDS` is now a plain authored array,
  `['select', 'pan', 'eye', 'measure', 'ping']`, in place of
  `TOOL_GROUPS.filter((g) => g.id === 'select' || g.id === 'view').flatMap(…)`. The value
  is unchanged; the mechanism is what changes, per SPEC-047 §3/IN-088 — a filter over the
  square map's own groups can never name a tool (Symbol, Road, River — §4) the square map
  does not have, so it could not have grown to hold them.
- `apps/web/src/lib/components/MapToolbar.svelte` — the unconditional `SNAP_MODES` array
  is replaced by `SQUARE_SNAP_MODES` (Cell/Half/Free, unchanged) and `HEX_SNAP_MODES`
  (Hex/Free), selected by a new `isHexMap` prop through `$derived`. `snapMode`'s existing
  `<select data-testid="map-snap-mode">` reads from whichever set applies — no new
  `data-testid` needed, since it is the same control offering a different option list
  (RULE-005 unaffected).
- `apps/web/src/lib/components/shell/MapToolPalette.svelte` — passes
  `isHexMap={controller.isHexMap}` through to `MapToolbar`, alongside the existing
  `toolSubset` wire.
- `README.md` — two new bullets under "Rendering a hex map"/the hex-tools list: one noting
  `HEX_TOOL_IDS` is now authored rather than derived (content unchanged), one noting
  `VectorSnapMode`'s new `'hex'` member and that no current hex tool shows the Snap
  selector yet.
- `docs/spec/SPEC-047.md` — §3 annotated: DEC-080's original text (2026-09-02) named two
  exhaustive `Record<VectorSnapMode, …>`s, `DEFAULT_BAND_WIDTH` and `snapCursorColors`; by
  the time this item ran, `snapCursorColors` (`vector-engine.ts`) had been refactored to
  take a `'floor' | 'rock' | 'select'` kind instead, so it no longer switches on
  `VectorSnapMode` at all. `DEFAULT_BAND_WIDTH` is the one `Record` that exists and needed
  the new member.
- `docs/decisions/DEC-085.md` (new), `DECISIONS.md`, `INTAKE.md`, `PLAN.md` — see
  **Deviations**: DEC-085 was closed ahead of this item, and its non-hex follow-on work is
  logged as IN-108 rather than folded in here.

**Visible behavior changes.**

**None.** No hex tool currently shows the Snap selector — every tool `HEX_TOOL_IDS`
offers today is Select or a View tool, none of which are in `MapToolbar`'s `SNAP_TOOLS`
list — so a referee sees exactly what they saw before. The palette that will actually use
`'hex'`/`HEX_SNAP_MODES` is SPEC-047 §4 (WI-105), which this item unblocks.

**How to verify.**

- `pnpm verify` — lint, typecheck, unit. Covers the type change compiling everywhere
  `VectorSnapMode` is used, `DEFAULT_BAND_WIDTH`'s existing tests (which iterate
  `Object.values` and so exercise the new `hex` entry automatically), and
  `tool-groups.test.ts`'s existing assertions on `HEX_TOOL_IDS`'s value and order, both of
  which hold unchanged against the authored array.
- By hand: nothing to look at yet, for the reason stated above — no hex tool reaches the
  Snap selector until WI-105 lands.

**What the suite actually did**, since a summary written before verification is a
prediction rather than a record. `pnpm verify` green: `lint`, `typecheck`, `unit` all
passed. `pnpm verify:all` was not run — this item touches no schema, no store contract, no
security rule, and no `apps/web` behaviour reachable from a running app (the `verify`
suite's unit tests already cover every changed line), so there is nothing for the
emulator/e2e half to exercise that `verify` does not already cover.

**Deviations.**

- **DEC-085 was closed before this item's code changed**, under the RULE-015 "genuinely
  required to unblock" exception. PLAN.md flagged, ahead of this item's gate clearing,
  that DEC-085 ("what does a zero-length gesture commit?") was still Open and should be
  answered before WI-104: SPEC-047 §3/§4 add three tools (this item's `'hex'` mode plus
  WI-105's Symbol/Road/River) that would each otherwise have to invent their own
  zero-length-gesture answer, on top of the five accidental ones DEC-085 documents. The
  user approved DEC-085's recommendation as-is (2026-09-04) — one rule in SPEC-028 §2:
  Cell/Half commits one cell, Free commits the tool's own end primitive at its snap anchor
  (nothing for a tool with no governed width) — so the hex tools this programme still owes
  (WI-105) inherit a settled rule instead of a sixth accident. See `docs/decisions/DEC-085.md`.
- **DEC-085's own code and spec consequences are not part of this item, and are not
  implemented here.** DEC-085's Impact section is explicit that moving `corridorPoly`'s
  Free zero-length case from "nothing" to a `bandWidth` square, and rewriting SPEC-028 §2
  to state the rule, is a stated-behaviour change to SPEC-028 (Deceptive) — and the
  Corridor is a square-grid tool untouched by SPEC-047 §3 (RULE-015: one work item, one
  chain). Logged as **IN-108**, which also folds in IN-095's matching Free-indicator fix
  per DEC-085's own note that the two are the same one-line change from opposite
  directions.
- **`snapCursorColors` is not, in current code, a `Record<VectorSnapMode, …>`.** DEC-080
  and SPEC-047 §3 both named it as a second exhaustive map needing a `'hex'` answer; by the
  time this item ran it had been refactored (between 2026-09-02 and now) to take a
  `'floor' | 'rock' | 'select'` kind, unrelated to snap mode. Per `CLAUDE.md`'s precedence
  (present-day code over the specs), nothing was added there — `DEFAULT_BAND_WIDTH` is the
  only `Record` that needed the new member — and SPEC-047 §3 is annotated to say so rather
  than left to mislead the next reader.
